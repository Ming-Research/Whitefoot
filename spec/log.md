# Specification change log

Newest first. One entry per change of the active specification,
`kernel-spec.md`: a `## <date> <title>` heading, `Rules:` naming every rule
added, changed or retired, and a concise `Summary:` of the change and its
selection ground. The form is the design tree log's, with `Rules:` in place of
`Nodes:`. The entry is committed with the change, and `make design-ready`
requires a new entry whenever the active specification changes; it cannot tell
whether `Rules:` names every changed rule. An entry is never edited and a new
one goes first. Blank lines between entries do not matter, and the file merges
with git's union driver, so two branches that each add an entry both keep it.
Older entries also carry an `Owner-approved:` line, a field since retired.

The specification carries no version. An entry's version is its place in this
log: `sh .github/spec-version.sh` prints the active version and `--list` every
entry's. An entry whose title begins `vA.B` names that version (every entry
written under the earlier procedure does, and the entry that starts a major
version does); any other entry is the next minor version after the entry below
it. A new entry names a version only to start the next major version. Cite an
entry by its date and title until it merges and by its version after. An
archive `spec/kernel-spec-<version>.md` marks a milestone: a copy of the active
file added by a change that edits no rule. The earlier procedure archived the
outgoing version with every amendment; git holds the rest of the history.

## 2026-10-23 an implementation that leaves a place unwritten discharges an interface's equality between that place's exit and entry values

Rules: changed FN-1, FN-4

Summary: FN-4 states that an actual's row may be a proper subset of the formal's or `pure`, and that a formal `ensures` is discharged by frame when its normalized comparison is an equality with equal displacements between the exit and entry values of one fragment-integer place P, or of one measure of P, rooted at a reference parameter, and no `writes` path in the actual's declared row overlaps P under the structural and literal separations of OWN-7 and WIN-2 with no assumed inequalities between parameter positions. A write through another parameter needs no binding condition, because the formal relation places P in every call's contract-read footprint, which EFF-5 separates from that argument's writes. Every other formal `ensures` still follows only from the actual's own `ensures`, and a frame discharge supplies no premise to another relation's query. FN-1 says the selected actual satisfies its own boundary rather than supplying the proof of the formal's templates. Selection ground: Halo's host interface promises an unchanged stack length for a member that may write the stack, and a host function that only reads the stack could satisfy it neither by its row (rows are exact under EFF-2) nor by its own `ensures` (`entry()` is admitted only on a written parameter); the owner chose this direction, a narrower row discharging the frame promise, on the board card raised for the same gap in Firn's script host.

## 2026-10-22 v0.164: `clear` empties a window and keeps its storage

Rules: changed OP-10, OP-13, PRE-1

Summary: A program that reuses one window, such as a byte buffer emptied after every batch, could not set its length to zero without one `take_back` per element or a transfer of every element into another window, and the read-only length leaves a library no other way, as the [retained-buffer comparison](../research/investigations/slots-clear/DESIGN.md#existing-operations-do-not-supply-the-required-reset) shows. PRE-1 adds the record `clear<W, T: drop>`, and OP-10 makes it the eleventh window operation over `Slots`, `Ring` and `Paged`: it runs each element's derived release in ascending logical order, sets the length to zero, keeps the storage, capacity, ring origin and pages, allocates nothing, visits no element when the element release is empty, refuses a linear element type at every call, and ends every element, range and page reference into the window while a reference to the window itself stays valid. OP-13 names `clear` as a bump allocator's reset. The element bound was chosen on the status board: every droppable element type, instead of a reset restricted to elements that need no release.

## 2026-10-22 v0.163: a `set` evaluates its right-hand side before its target

Rules: changed SET-1, OP-12, OWN-1, LIV-1, PAR-2, EFF-5

Summary: SET-1 evaluated the target before the right-hand side and carried its address across it, but after the right-hand side rechecked only the root's liveness, writability, moved prefixes and the references the target path is reached through, so an accepted `set` could write storage its own right-hand side had moved or released: `set v[1_u64] = remove_at(window: &v, index: 0_u64);` on a two-element window of boxes released the stale copy of the box `remove_at` had moved to slot 0, a double free, and `set b.inner[0_u64] = refill(cell: &b);`, whose callee grows the window, stored into the block `grow` had released (both measured on the compiler at c40acc366, research/investigations/spec-proof/DESIGN.md, incidental finding 6). SET-1 now evaluates the right-hand side first and then evaluates the target in the state it left, making every target judgment there (writable root, liveness, each subscript's OP-4 discharge, the validity of references the target is reached through), so a `set p = e;` other than an OP-12 update means exactly `let t = e; set p = move t;` and nothing evaluated for the target crosses the right-hand side. The first program is now refused by OP-4, since one element remains and index 1 is out of bounds, and the second writes the new block. A right-hand side that changes a binding a subscript reads now selects the slot that binding holds afterwards. A payload target whose right-hand side writes the enum, or anything in it, is now refused under REF-1 at target evaluation, since that write ends the arm's variant fact, where before the selected payload storage was held across the right-hand side and a content write was accepted. OP-12's atomic update reads its target out at the call's first argument; EFF-5 clause 2 now states that a by-value argument also contributes a read of every place its offset atoms read, which the compiler already compared, so a callee row that writes one of them is refused at the call and the place read out is the place target evaluation names after the call, as OP-12 now says. OWN-1 and LIV-1 now say SET-1 judges its target after the right-hand side instead of rechecking premises there. PAR-2's access table reads a target's liveness where SET-1 evaluates it, instead of at statement entry, so `set x = g(move x);` contributes what its decomposition `let t = g(move x); set x = move t;` contributes, and an OP-12 read-out still contributes the write of its target. Selection ground: the owner chose this option on the design card of item wf-sound-set-rhs-target, which recommended it because it removes stale targets by construction with no new rule and keeps assignment decomposable into a binding and a store, instead of holding the target's storage under REF-2 across the right-hand side, which adds a concept and a refusal and still makes the direct and the decomposed spellings differ, applying OP-12's prefix condition to every `set`, which refuses right-hand sides that disturb no storage the commit uses, or reading the subscripts first and locating the place afterwards, which joins two evaluation moments.

## 2026-10-21 v0.158: a shared object may hold a linear state, whose handles are linear and each end in `shared_close`

Rules: changed OWN-1, PROV-6, SHARE-1, SHARE-3, WAIT-2, PRE-1; added to SHARE-1 `shared_close`, the one total order in which an object's handles end, and the refusal of a linear state type that has its own handle type as a part; removed the `drop` bound of `Shared<T>`, `shared_new` and `shared_share`

Summary: A shared object's state was released with its last handle, so `Shared<T>`, `shared_new` and `shared_share` required `T: drop`, and a value that must be consumed explicitly, such as a file being written, a connection's receive half or a `nodrop` struct, could not pass between contexts that are already running, the only route between them being a shared object. The bound is gone. PROV-6 makes a `Shared<T>` handle linear exactly when `T` is linear, through an ownership of the state's type that adds no release edge, and OWN-1 lists the state of a `Shared<T>` handle among the parts a type's capabilities follow, so each handle of a linear state ends in the new waiting prelude call `shared_close`, which consumes the handle and returns `Some` holding the state when it is the object's last handle to end, and `None` otherwise. SHARE-3 makes each close a shared effect, so the last closer observes every statement the other contexts completed before their closes. WAIT-2 makes the order in which an object's handles end an input of the execution, because whether a close returns the state can turn on a release in another context, which is no shared effect. A close is a waiting call, which no atomic block contains, and a linear handle is never released implicitly, so no statement holds the object when its last close takes the state. SHARE-1 refuses, at a generic function's symbolic instance and again at each concrete instance, a linear state type that reaches its own handle type through fields, payload fields, elements, `Box` content or the state behind a `Shared` handle, since a handle its own object held would keep the count from reaching the last close. `SharedRead<T>`, `Frozen<T>` and `ConcurrentHashMap<V>` keep their `drop` bounds: a read-only handle takes no state, a frozen value never changes, and clearing or releasing a map drops every entry at once. Selection ground: the owner's ruling of 2026-10-09 on the board (item firn-wf-linear-share) chose linear handles with an explicit close; the detail rules are option A of the design card on item linear-in-shared, which the owner chose on 2026-10-21. Refused: an owner handle whose waiting reclaim returns the state while the other handles stay droppable, which waits forever while its owner holds another handle; a handoff channel alone, which cannot let contexts share one linear state; and refusing every linear-state handle inside a linear state, which also refuses handing one object's handle to a running context through another object.

## 2026-10-20 v0.152: a condition the checker decides is redundant source

Rules: changed OP-5, GRAM-6, ENT-6, MSR-4

Summary: OP-5 adds a source redundancy judgment for the condition of every `if` and `value_if`, `else if` links included, queried after the condition's own evaluation and before its branch-entry facts. In a noncontradictory entering state the condition is decided True when every fact the then-block's entry would establish is already derivable (each goal origin through the Signed Goal query, the comparison origin in the closed L0 state), and False when the same holds for the else side; a decided condition is a hard error with residual `RedundantCondition` and a repair that deletes the test and its dead branch, so the deletion removes no fact a later goal could use. A generic body is judged once at the symbolic instance of its own parameters, a contradictory entering state admits the condition, leaving reachability to FN-1, and a condition with neither a goal origin nor a comparison origin, such as a user function's result, has no derivable truth and is admitted. GRAM-6 points a condition's redundancy to OP-5, ENT-6 names OP-5 as a Signed Goal consumer, and MSR-4 lists OP-5 among the numeric disposition's consumers and lets OP-5 state its own result judgment. The worked example returns the converted value as the exit status instead of testing it, because the old test is itself a decided condition; the rule text first drafted against v0.136 is renumbered to v0.152 because main reached v0.151 first. Selection ground: executable source should contain only the tests its run needs, since a decided test costs run time and tells a reader, often an agent, that an excluded case is still possible.
