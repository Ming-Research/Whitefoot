Decision: Contexts run on driver threads, one per CPU unless `WF_DRIVERS` names a count and one where the host has no kernel ring, each driver with its own ring, parked contexts and run queue; a context changes hands only where one of its frames suspends, a started context is made ready on its starter's driver, a driver with nothing to run takes about half of another's ready contexts, which have no operation in flight, and a parked context is woken by the driver whose ring holds its operation, because a compute task never waits [PAR-1, PAR-2] so no suspension falls between a compute offer and its join, placing starts round robin on fixed drivers woke a parked driver for every start and join (four drivers ran a million start-then-join steps in 35.8 seconds against 0.12 on one) and scaled a 64-connection echo server only 1.04 times, while this placement ran those steps in 0.22 seconds and the server at 1.71 to 2.13 times its one-driver rate and 0.73 to 0.86 of the best native echo server at 64 and 1024 connections ([Experiment 5](../../research/investigations/io-model/WAITS.md#experiment-5-several-driver-threads)), instead of one driver for every context, round-robin placement, or running contexts on compute workers.

Decision: A waiting function lowers to an LLVM switched-resume coroutine that starts suspended, whose frame the context's arena allocates last in, first out, and a call transfers into its callee and a finishing callee back into its caller by a resume placed immediately before the suspension, because LLVM 18's coroutine split turns that resume into a tail call, so returns do not grow the native stack, and LLVM 18 has no symmetric-transfer intrinsic ([design](../../research/investigations/io-model/WAITS.md#a-waiting-function-is-a-resumable-frame)), and the compiled server lowered this way held 0.84 and 0.93 of the hand-written one-driver server at 64 connections where the stackful build held 0.84 and 0.97 ([Experiment 3](../../research/investigations/io-model/WAITS.md#experiment-3-the-resumable-frame-server)), instead of returning every finished callee through the driver's ready queue.

Decision: Contexts and their frame arenas take their memory from host regions the context driver reserves itself, 64 MiB at a time and carved into power-of-two blocks kept on free lists, because the runtime every build links never calls the program's allocator [STOR-8], so a program that uses no heap needs none, and one region's mapping serves thousands of contexts: the compiled server's mapping count stayed at 37 from 1,000 to 19,000 idle connections while the stackful build's grew by two per connection ([Experiment 3](../../research/investigations/io-model/WAITS.md#experiment-3-the-resumable-frame-server)), instead of the program's allocator or a reservation per context, which would add a kernel mapping per connection as the stacks did.

Decision: A waiting host operation lowers to a start, which submits into the running context's one completion record or answers at once, a suspension only while that record is pending, and a finish that reads the record into the operation's result, with the start answering whether the operation is pending through a bridge entry a test host can replace like its submits and joins, because a context has at most one host operation pending at a time, so one record per context serves every call it makes, instead of a record in the frame of every waiting function that calls the host.

Decision: A suspended frame registers its context on its pending record without entering the ring, the driver flushes and reaps the ring only when no context is ready, and a record published on the driver thread wakes its context by the record's address, while one another thread publishes is found by a pass over the parked contexts, because entering the ring for every wait and scanning every parked context on every wake held the compiled server to 0.64 and 0.59 of the hand-written shape at 64 and 1024 connections, and removing both, with the program's echo window raised to the hand-written server's 64 KiB, raised it to 0.94 and 1.12 in two-line runs and 0.88 and 0.80 to 1.05 in the full protocol ([Experiment 2](../../research/investigations/io-model/WAITS.md#experiment-2-the-compiled-context-server)), instead of a ring entry per wait or a scan per wake.

Decision: With other contexts live and a ring to wait in, a socket receive goes to the ring at once rather than first trying the host without waiting, because the attempt is a system call of its own that finds no data when the peer has not answered yet, and removing it raised the compiled server from 0.80 to 0.90 of the hand-written shape at 64 connections in one run ([Experiment 2](../../research/investigations/io-model/WAITS.md#experiment-2-the-compiled-context-server)), instead of the first attempt a sequential program keeps, where no other context could use the wait.

Decision: A spawn lowers to a synthesized wrapper that makes the call and releases its result, whose frame and argument block the new context's arena holds, with a join before every exit of the starting activation that suspends the starting frame until the activation's contexts have finished and no path that runs the call inline, because [WAIT-3] makes the spawned call run concurrently with its starter until the activation leaves, and running the call inline would wait for it ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#102-the-meaning-and-its-join-points)), instead of reusing the compute lanes, which refuse an offer by running it on the caller.

Decision: A bound spawn lowers to a start whose wrapper returns the call's result into a slot of the starting frame and a join of that one context before the first later statement of the `let`'s block that may leave the block or that names the binding in an expression, set target or statement it holds, or whose resolved footprint reaches the binding, and otherwise at the block's end, because every read, write, release and reference formation of the binding names it, so the join stands exactly where [WAIT-3] places it, and a loop, a match, a destructuring `let` or an atomic statement that names nothing the call holds proceeds alongside it ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#102-the-meaning-and-its-join-points)), instead of joining at the next statement, which serializes a gather, joining inside the using statement on the path that reaches the use, which leaves later code a joined and an unjoined path to merge, or joining before every statement whose overlap footprint is refused or not resolved.

Decision: With no kernel completion ring and other contexts live, a socket receive, send or accept waits for its descriptor's readiness and is then made on the driver thread, because a blocking call on that thread stops every context, and a server whose socket waits went to the helper pool held exactly as many silent peers as the pool's eight threads, answering eight reverse-order peers and not nine, where readiness waits answered sixteen ([readiness route](../../research/investigations/io-model/WAITS.md#the-readiness-route-on-a-host-without-a-ring)), instead of queuing peer-bound socket waits on the helper pool.

Decision: A shared object is one block of the context runtime's pool holding a header (handle count, lock word, holder count, parked and watching contexts) and then the state, an atomic statement counts a handle of its own before it acquires and releases it after it unlocks on every edge that leaves its block, and a handle's release drops the state and returns the block when it was the last, because the runtime every build links never calls the program's allocator [STOR-8] and a block may move or release the handle it was reached through, instead of allocating objects with the program's heap or refusing a block that touches its target place.

Decision: A statement that finds its object held spins for a bounded time and then parks its context, an unlock wakes the first parked statement to try again, which keeps its place at the queue's head if it misses again, and the unlock after two such vain wakes hands it the object, because a holder's block cannot wait, so a holder is always running and finishes within its block's compute, while handing every parked statement the object left it held by a context no driver was running and made 97 percent of the Redis subset's pipelined acquires park on two drivers, against 0.6 percent with retries ([Experiment 7](../../research/investigations/io-model/SHARED.md#the-acquire-without-a-convoy-results)), and the bound gives a parked statement the object after at most two vain wakes, which [WAIT-2]'s promise that a statement whose guard stays true takes effect needs while every context keeps reaching its completion or a wait ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#103-progress-and-a-program-that-stops)), instead of a first-come handoff that keeps strict arrival order or retries without a bound; the count of two is provisional, one retry keeping the common case on a running context while no workload has compared one, three or more, to be reopened when a statement's wait shows in a workload's tail latency or handoffs show in a profile.

Decision: A statement whose guard reads false parks among the object's watching contexts, which every statement that writes the object wakes when it ends (in this version every statement, since lowering acquires every one for writing), and a woken statement acquires the object again and evaluates its guard again, because a guard writes nothing, so only a write can change its answer, and it re-reads the state it takes effect in, instead of a condition the writer signals by name.

Rejected:
- A first-come queue that hands the object to the parked context at its head: rejected because the object then stays held until a driver resumes that context, and every statement that arrives meanwhile parks behind it ([Experiment 7](../../research/investigations/io-model/SHARED.md#attribution)).
- One driver thread for every context: rejected because a server then uses one core; at four drivers the echo server ran 1.71 to 2.13 times its one-driver rate at 64 and 1024 connections ([Experiment 5](../../research/investigations/io-model/WAITS.md#experiment-5-several-driver-threads)).
- Placing each start round robin on a driver it never leaves: rejected because every start and every join then wakes another thread, which cost a start-then-join step 35.8 microseconds at four drivers against 0.12 at one, and the server scaled only 1.04 times at 64 connections ([Experiment 5](../../research/investigations/io-model/WAITS.md#the-first-placement-round-robin)).
- A stack of its own per context, owned by the floor and switched by the driver (Experiments 1 and 2): rejected because each context costs two kernel mappings, which bounds a process near the mapping limit, and a compute join on a context's stack stops every other context ([design](../../research/investigations/io-model/WAITS.md#a-waiting-function-is-a-resumable-frame)).
- Replaced decision beginning "A statement that finds its object held spins for a bounded time and then parks its context, and an unlock wakes": rejected because a statement it woke could miss the object at every retry, and [WAIT-2] now promises that a statement whose guard stays true takes effect; the retry stays and gains a bound.
- Replaced decision beginning "A marked waiting `let` lowers to a start": rejected because it joined before every statement whose overlap footprint was refused or not resolved, a loop, a match, an atomic statement or a read through a Box among them, so a starter waited for a context whose guard only that statement would make true, before the point [WAIT-3] fixes.
- A bound on how long a statement has waited instead of how often it was woken: rejected because the promise needs only that a waiting statement eventually holds the object, which a count of vain wakes gives on every schedule, while a time bound adds a threshold that depends on the host's speed.
- Starting, besides every spawn, each unspawned call whose callee may reach an atomic statement with a guard, found by a fixed point over the checked bodies: rejected because [WAIT-2] now runs a call that is not spawned in order, so starting it would change the program's meaning rather than its cost.
