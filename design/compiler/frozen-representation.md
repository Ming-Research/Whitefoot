Decision: A `Frozen<T>` handle is lowered as a pointer to its value inside one runtime pool block whose header holds an atomic handle count, the raw pool allocation and its granted extent and no lock, `frozen_share` being a relaxed increment and a release an acquire-release decrement whose last caller releases the value in place and returns the block, and the checker and lowering model it as the cell kind with a distinct frozen release class, because a read through `inner` is then exactly a cell's content read, the count protocol is the shared object's without the lock an immutable value never needs, and every place the cell kind grants an owner's power checks the release class, instead of reusing the shared-object block with its lock, or a separate nominal kind whose every arm would duplicate the cell's read path now.

Decision: Align a frozen payload within its one pool grant and keep a fixed 32-byte header immediately before the payload, aligned to 16 bytes on every supported target and retaining the raw pool pointer in that header, because sharing and release can recover their metadata from the value alone at every supported heap alignment, instead of assuming the pool base alignment satisfies every payload, using a host-dependent header extent, or adding alignment-dependent handle projections. The target qualifies the payload plus this header and the maximum requested-alignment padding before emission. The complete grant, including explicit padding and metadata, remains the metered holding.

Rejected:
- Reusing the shared-object block and its lock for frozen values: rejected because no write ever reaches a frozen value, so the lock would only serialize readers.
