Decision: Contiguous runtime-capacity Box owners are one pointer to one header-first allocation, with only the shape's runtime measure words stored, because this keeps owner, call and capture transport to one word and makes construction and cleanup own one allocation. A fat descriptor can also own one element allocation and make measures direct, but widens transport and separates owner metadata from the in-block representation; the current choice is retained provisionally on those grounds, not on a general speed claim. The [capture comparison](../../research/investigations/access-effects/parallel-array-captures.md) qualifies a narrower task-ABI change, while the general layout and growth study remains in the maintained backlog.

Decision: Constant- and runtime-capacity shapes use the same header ordering and element-address rule, omitting compile-time measures and giving Slots and Ring their distinct physical headers, because this avoids placement-specific measure sources and offsets while satisfying OP-9's layout ceilings, instead of an elements-first inline layout with a separate adapter or a shared physical header containing unused words. Shared helpers could support different layouts; their extra cases and evidence are the tradeoff, not necessarily duplicate emitters.

Decision: Construct values with constant-capacity window storage by initializing their headers and value-bearing fields, leaving unoccupied Slots and Ring elements uninitialized, including through copied struct and enum fields, while retaining inactive enum payload zeroing and complete Array element initialization, because WIN-1 makes the unoccupied tail unobservable and Snowghost's match_complex memset accounted for 21 percent of instructions in a callgrind profile of one ecma262 style computation (Snowghost 58fa8ee, proto_layout_seq, collection limited to compute_styles; [profile](https://github.com/Ming-Research/Snowghost-wf/blob/8b4f33256/research/investigations/concurrency/DESIGN.md#styles-work-per-element)) before its rule index reduced the call count (the reported profile motivates this change, not a measured speedup from it), instead of zero-filling the whole value.

Decision: Represent Slots and Ring with a shape, element type and optional capacity, retaining separate Array forms and one measured identity per specification row, because shape and optional capacity encode the distinctions layout and measure classification consume without separately synchronized placement flags. Retire the region-bearing view, store, arena and extent types rather than leave them unconstructible, because no current source or runtime consumer owns their semantics, instead of one checked type per placement or dead exhaustive-match arms.

Decision: A contiguous range reference lowers to a nonowning element pointer and count, with selected element accesses retaining their complete typed suffix and length read from the reference kind, because neither capacity nor allocator provenance is needed by the admitted operations and the selected element type cannot supply the range's length. The dedicated range place feeds ordinary address, value, reference, store and measure lowering, instead of coercing its pointer/count pair into an owned descriptor or materializing the source container's metadata beside it.

Decision: Lower `grow` of a `Box<Slots<T>>` cell to one `wf__heap_retake` of the cell at the new size, storing the new capacity and the returned block; it calls `realloc` for a block of at least 1024 bytes, because the allocator may extend the block in place or remap large blocks without copying, which on the i9-14900K made Halo's integer-table kernel 14.0% faster and sort 2.5% faster with no other kernel slower beyond noise ([Halo-wf `research/experiments/halo-bench/RESULTS.md`, "Growing the array in place with a reallocating grow"](https://github.com/Ming-Research/Halo-wf/blob/6fc3b83ebdd0/research/experiments/halo-bench/RESULTS.md#growing-the-array-in-place-with-a-reallocating-grow), run 37773076340 at Halo-wf `6fc3b83`), while STOR-7 still permits the address change and the block keeps the alignment `malloc` gave it, instead of allocating a new block, copying the filled slots and freeing the old one. A failed `realloc` leaves the old block and terminates as STOR-8 states. The reallocation is counted through `wf__heap_retake`, replacing the old cell size with the new size in the current driver's heap counter only on success.

Decision: `wf__heap_retake` grows a block smaller than 1024 bytes by allocating a fresh block, copying the old block and freeing it, because glibc's `realloc` always takes the lock of the arena owning the block while small `malloc` and `free` use a per-thread cache, which with four workers made Snowghost's text preparation queue on one arena lock (4-thread to 1-thread ratio about 0.79 against about 0.52 with the copy, `futex` calls about 159,000 against about 1,000, on a 4-vCPU AMD EPYC 7763) while Halo's single-threaded integer-table and sort kernels stayed within their twin's spread on the i9-14900K ([grow-allocator contention](../../research/investigations/grow-allocator-contention/DESIGN.md#results)), instead of calling `realloc` for every size or copying every block. A 131072-byte limit passed the same criteria; the smaller limit keeps `realloc` for more of the blocks that can grow in place, as the investigation fixed before measuring. Contention on blocks of 1024 bytes or more was not measured.

Decision: Ordinary target lowering substitutes zero only for the element-address operand of a step whose selected-target stride is zero, retaining logical indices, lengths and window coordinates in their other uses, because STOR-6 requires exact target-domain representations for the indices actually used in address formation while a zero-stride step has zero displacement for every admitted logical index, instead of rejecting representable zero-byte storage because its logical cardinality exceeds the signed address domain or weakening STOR-6 to permit unrepresentable address operands. The rule uses the checked target layout for the element of each step, including nested places, generated fill and cleanup walks, ranges and transfer-size calculations; an empty final field does not erase a nonzero-stride outer step.

Decision: A constant-capacity zero Array, Slots or Ring omits its nonexistent element's target alignment by representing the empty payload as a zero-length byte array, while Slots and Ring retain their ordinary descriptor words, because OP-9 repeats the element layout zero times and nested owners must be qualified against the representation actually emitted, instead of preserving a typed empty tail that can enlarge the header and stride beyond the calculated layout or rejecting an otherwise representable empty owner. Runtime-capacity tails remain typed because they can hold elements; a nonzero capacity of a zero-size element is a different case and keeps its ordinary coordinate rules.

Decision: A `Segments<T>` Box owner is one pointer to one header-first allocation holding the segment count, the count plus one element offsets beginning at zero, and then the elements at the first offset past the bounds that the element's alignment admits, recomputed from the count at each access, because this keeps the owner a thin pointer released by one free like the other runtime shapes and a segment's range is two bound loads and one address step, instead of a separately allocated bounds array, which adds an allocation and release, or a stored element-offset word, which would replace a shift, an add and a mask per access with one load; this last choice is provisional, unmeasured, and reopens if a profile shows the offset computation on a hot path. The construction sums the lengths once and sizes the block with the checked arithmetic of the other runtime-capacity shapes at the actual target stride, instead of judging a target-independent size predicate with the language layout ceiling.

Decision: A Paged Box owner is one pointer to one header-first cell holding len, cap, directory capacity and the page-pointer tail, with the target layout ceiling counting the three header words and one directory entry, because an in-cell directory removes the separate directory pointer's dependent load from every element access, which the hand-written page table does not pay; this remains the owner-selected representation, with no general performance claim: on the M5 Air the header-first cell measured within the noise twin's spread of the hand-written table ([C3 measurement](../../research/investigations/paged-storage/DESIGN.md#c3-header-first-measurement-on-the-m5-air)), but on the i9-14900K both lowerings are 2 to 11 percent slower in layout and the header-first cell takes the most page faults ([C3 on the i9-14900K](../../research/investigations/paged-storage/DESIGN.md#c3-on-the-i9-14900k-both-lowerings-fail)), so the retained layout remains open to a future measured replacement; the owner re-approved the header-first cell for the built-in form instead of adopting the X1/X2 experiments. Pages hold B elements, where B is the largest power of two satisfying B * stride_ceiling(T) <= 4096, with B = 1 when the stride ceiling exceeds 4096, because fixed powers of two give constant-time shift-and-mask indexing while page allocation never moves an earlier payload ([selected lowering](../../research/investigations/paged-storage/DESIGN.md#lowering)), and the language's stride ceiling rather than the target's stride makes the page length, which `paged_page_len` and `p.pages.len` expose, the same on every qualified target, instead of a target-stride page size that would make an accepted program's output depend on the target, or a radix descent. The actual stride, at or below the ceiling, still addresses elements, so a page's bytes never exceed 4096 when the stride ceiling is at most 4096, a larger ceiling gives single-element pages, and a zero actual stride keeps zero displacement whatever B is.

Decision: Paged construction sizes the cell for a directory doubled from at least one entry to fit the requested pages, and growth beyond that directory capacity allocates a new cell, copies its header and existing page pointers, frees the old cell and replaces the pointer through the Box reference before allocating the added pages; release visits initialized elements in index order, frees the pages and then frees the cell with its directory, because amortized cell growth preserves the required stable payload storage and one-word owner, instead of copying payloads or allocating a cell for every element. The cell size includes the three-word header in the checked allocation arithmetic, and boundary placement and removal retain the cell.

Decision: A Run reference lowers as a directory pointer at cell + 24, logical lower endpoint and length, and a page reference as an ordinary contiguous pointer and length, because element addressing needs both the page and offset and growth invalidates every reference before replacing the cell that holds the directory, instead of carrying a Box owner in a nonowning run or keeping references across cell reallocation.

Rejected:
- A Paged descriptor pointing to a separately allocated directory: rejected because it pays a dependent load per element access that the hand-written page table does not, and the built-in form on it failed C3 on the i9-14900K ([C3 comparison](../../research/investigations/paged-storage/DESIGN.md#c3-result-and-header-first-response)); how much of that loss the load caused is not isolated.
- Allocating a new block, moving the filled slots and freeing the old one for every `grow`: rejected because it copies on every growth even where the allocator could extend in place, which kept Halo's in-place table growth at 1.000 of the copying source while `realloc` gave 0.860 on the same source.
- Calling `realloc` for every `grow`: rejected because small blocks then take the owning glibc arena's lock on every growth and four workers queued on it, losing most of Snowghost's text-preparation speedup.
- Claiming the thin owner is universally faster than a fat descriptor: rejected because owner width, measure loads, allocation count, copying and linked layout have different costs, and the retained measurements do not isolate the general choice.
- Keeping a pointer to a separately allocated descriptor and a second element block: rejected because it keeps one-word transport by adding another allocation and release, whereas the selected header-first block meets both objectives together.
- Depending on optional optimizer facts or LLVM dead-code elimination to erase a zero-stride address: rejected because qualification must hold for ordinary pre-optimization materialization and facts must not select target success.
- Replacing every logical index of a zero-byte element with zero: rejected because bounds, range lengths, window coordinates and source observations retain their original logical values.
- Retaining the high-alignment typed tail and rejecting nested zero-capacity owners under the existing language ceilings: rejected because no element is present to require that alignment, and the existing zero-capacity Array representation supplies a semantics-preserving omission without reducing container capability.
- Treating a zero-length typed LLVM array as alignment-free: rejected because its element still determines the LLVM ABI alignment, so header, stride and parent-object qualification can disagree with actual emission.
