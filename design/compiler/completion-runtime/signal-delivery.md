Decision: Stop requests enter a growing FIFO in the runtime pool and complete the ordinary pending record under the queue lock, while the same lock removes a timed-out waiter without consuming a later request, because requests already observed between calls must retain their order and a finite overwrite queue would lose that history, instead of a bounded queue with silent drops; pool exhaustion uses the existing reported runtime-resource termination.

Decision: The POSIX launcher's original thread receives stop requests while the entry runs on its declared stack; on Linux it blocks SIGINT and SIGTERM before creating the entry, whose descendants inherit the mask, then unblocks its own mask with default dispositions while no listener exists and blocks it while reading an open signalfd through ordinary completion submit/join, which offers the read to the ring first and uses the file adapter otherwise, because [the AMD host comparison](../../../research/investigations/stop-signals/README.md#startup-cost-on-amd-hosts) found that creating a receiver before the entry slowed width-one stencil by 11 to 28 percent and removing it restored the merge base's speed, instead of a receiver thread created at start or at first listen; a first-listen receiver cannot change the masks of earlier threads, which would either remain unblocked and defeat signalfd or remain blocked without a receiver applying the default. The launcher owns open, close and entry-return commands and releases an open listener's host state before joining the entry.

Decision: POSIX entry-thread creation failure ends startup with a diagnostic, floor-only probes retain no-op stop hooks, and native callers without a launcher loop receive ENOTSUP when opening a listener, because running the entry on the original thread would strand reception and a native caller cannot retroactively block its existing threads, instead of continuing with stop signals blocked and no receiver or silently creating a substitute receiver thread.

Decision: The POSIX receiver serializes observation through signalfd reads or kqueue signal events and Windows publishes from its console callback under a lock, with a close-generation condition holding close, logoff and shutdown callbacks until their listener closes, because the host may merge signals before observation and Windows ends the process when those callbacks return, instead of reconstructing sender order from missing host history or returning from a termination callback before the program can stop ([host constraints](../../../research/investigations/stop-signals/README.md#hosts)).

Rejected:
- A receiver thread created at start: rejected because the AMD host comparison measured a width-one stencil slowdown of 11 to 28 percent that disappeared when that thread was removed.
- A receiver thread created at first listen: rejected because earlier threads would either keep stop signals unblocked and defeat signalfd or keep them blocked with nobody applying the default before the first listen.
