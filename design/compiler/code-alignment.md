Decision: Every function the compiler produces starts on a 64-byte boundary: the emitter writes `align 64` on each definition of the module, the hand-written `ordinary_values.ll` carries it on each of its definitions, and the C runtime compiles with `-falign-functions=64` among the driver's host arguments, because a kernel whose code did not change failed the paired regression comparison when one new runtime import moved every function by 16 bytes, its time follows where several of its functions fall within 64-byte lines, and a start fixed on such a boundary for every function keeps those positions whatever precedes it, which the [placement experiment](../../research/investigations/code-placement/DESIGN.md#conclusion) confirmed on the four processor models it reached, instead of leaving each function where the linker happens to put it.

Decision: Each function is aligned, not only the start of each module's code, because a compiler change that alters one function's size moves every later function of the same module, which per-function alignment absorbs and an aligned section alone does not, and that alignment is written in the module itself, because clang ignores `-falign-functions` for LLVM input ([code placement](../../research/investigations/code-placement/DESIGN.md#clang-does-not-align-llvm-input-with--falign-functions)) and the module reaches the host through the driver's link, through `--emit-llvm` consumers such as the regression instrument and through link-time optimization, which an attribute of the definition reaches from one place, instead of the internal LLVM option `-align-all-functions` repeated at every host invocation.

Decision: The boundary is 64 bytes on every target, as a provisional choice because 64 bytes is the line of the x86-64 hosts where the effect was measured while arm64's 128-byte lines cannot be measured on the hosted macOS runner, which resolves only about 20 percent, reopened when a placement effect is measured on arm64, instead of a boundary per target chosen without a measurement.

Decision: Loop headers keep LLVM's own alignment, because once a function starts on a 64-byte boundary the offset of each of its loops within its line is fixed, so loop alignment is a separate performance choice whose padding runs on each loop entry, and `-falign-loops=32` met the experiment's selection rule on no host, its one large gain, 4 to 9 percent on `records` on an EPYC 9V45, coming with a placement dependence in a cell that run did not locate, instead of compiling the module with `-falign-loops=32`; the choice reopens with the TODO on the aligned layout's cost to `records`.

Decision: The fixed layout's cost on some processors is accepted, as a provisional choice, because a layout no unrelated change can move is what lets the regression gate and a writer attribute a time to the code that produced it, while on an AMD EPYC 9V74 the aligned `records` kernel took 5 to 14 percent longer than its median unaligned placement in a three-round run, this change's own comparisons against `main` failed on `records` in three of five runs, 8 to 18 percent longer, and elsewhere the aligned layout of `records` lay between 5 percent slower and 10 percent faster ([results](../../research/investigations/code-placement/DESIGN.md#results)), reopened when the [TODO on the aligned layout of `records`](../../docs/todo.md#parallel-lowering-and-runtime) finds a deterministic layout without that cost, instead of keeping the linker's layout for the speed it happens to give one processor.

Rejected:
- Aligning only the functions that run hot: rejected because a kernel's time depends on where several of its functions fall, and which ones are hot is not known when the module is emitted.
- Aligning each module's code section without padding each function: rejected because it keeps positions only against changes ahead of the module, while a change in one function's size, the common compiler change, still moves every later function of that module within its line.
- `-mbranches-within-32B-boundaries`: rejected because it pads branches away from 32-byte boundaries for one processor family's jump erratum and leaves each function's start where it falls, and the hosts that showed the effect are not of that family.
- Measuring placement-robustly while leaving the compiler unchanged: rejected because the gate would stop charging changes with placement while a program would still change speed by tens of percent when an unrelated import moved it.
- Leaving function alignment out of the driver because the compute bundle's alignment controls neither removed placement sensitivity nor showed a gain: rejected because those controls passed `-falign-functions=64` to the emitted module's LLVM, which clang ignores, so no kernel function was aligned, and their shifted arm moved the scheduler rather than the kernel.
