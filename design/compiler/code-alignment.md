Decision: Every function the compiler produces starts on a 64-byte boundary: the emitter writes `align 64` on each definition of the module, the hand-written `ordinary_values.ll` carries it on each of its definitions, and the C runtime compiles with `-falign-functions=64` among the driver's host arguments, because a kernel whose code did not change failed the paired regression comparison when one new runtime import moved every function by 16 bytes, its time follows where several of its functions fall within 64-byte lines, and only a start fixed on such a boundary leaves those positions unchanged whatever precedes the function, which the [placement experiment](../../research/investigations/code-placement/DESIGN.md#results) confirmed on the i9-14900K and on AMD EPYC 7763 and 9V45 and Intel Xeon 8370C runners, where no shift of the aligned module and runtime changed any of the five compute kernels' times by the regression gate's own rule and the aligned images lay within about 3 percent of the unaligned layouts, instead of leaving each function where the linker happens to put it. The fixed layout is not the fastest one everywhere: on an AMD EPYC 9V74 a three-round run read the aligned layout of the `records` kernel about 5 to 10 percent slower than its unaligned layouts, a cost accepted for a layout that no unrelated change can move, while finding a deterministic layout without it stays open ([TODO](../../docs/todo.md#parallel-lowering-and-runtime)).

Decision: The module's alignment is written in the module itself rather than passed to the host compiler, because clang ignores `-falign-functions` for LLVM input ([code placement](../../research/investigations/code-placement/DESIGN.md#clang-does-not-align-llvm-input-with--falign-functions)) and the module reaches the host through the driver's link, through `--emit-llvm` consumers such as the regression instrument and through link-time optimization, which an attribute of the definition reaches from one place, instead of the internal LLVM option `-align-all-functions` repeated at every host invocation.

Decision: The boundary is 64 bytes on every target, as a provisional choice because 64 bytes is the line of the x86-64 hosts where the effect was measured while arm64's 128-byte lines cannot be measured on the hosted macOS runner, which resolves only about 20 percent, reopened when a placement effect is measured on arm64, instead of a boundary per target chosen without a measurement.

Decision: Loop headers keep LLVM's own alignment, because once a function starts on a 64-byte boundary the offset of each of its loops within its line is fixed, so loop alignment is a separate performance choice whose padding runs on each loop entry, and in the placement experiment `-falign-loops=32` made no kernel faster at two widths on the i9-14900K or the EPYC 7763 while on the 9V45 it made `records` 4 to 9 percent faster but its time moved with placement, instead of compiling the module with `-falign-loops=32`; the choice reopens with the TODO on the aligned layout's cost to `records`.

Rejected:
- Aligning only the functions that run hot: rejected because a kernel's time depends on where several of its functions fall, and which ones are hot is not known when the module is emitted.
- `-mbranches-within-32B-boundaries`: rejected because it pads branches away from 32-byte boundaries for one processor family's jump erratum and leaves each function's start where it falls, and the hosts that showed the effect are not of that family.
- Measuring placement-robustly while leaving the compiler unchanged: rejected because the gate would stop charging changes with placement while a program would still change speed by tens of percent when an unrelated import moved it.
- Leaving the driver's compilation unchanged after the compute bundle's alignment arm read within one percent: rejected because that arm passed `-falign-functions=64` to the emitted module's LLVM, which clang ignores, so no kernel function was aligned, and its shifted arm moved the scheduler rather than the kernel.
