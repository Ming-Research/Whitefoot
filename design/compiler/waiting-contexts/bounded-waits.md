Decision: Each driver keeps the contexts waiting on it with a deadline in a binary heap on the deadline's instant, bounds every park and poll by the earliest one, and looks at the heap when it reaps: it completes a sleep, completes a readiness wait it polls itself with nothing transferred, and asks the route that holds any other operation to cancel it, because a parked context's operation belongs to its driver and only the thread holding that driver's service token touches its parked contexts, so the heap needs no lock ([design](../../../research/investigations/io-model/TIME-AND-FILES.md#one-timer-queue-per-driver)), instead of one timer thread for the program or a linked timeout on each ring entry.

Decision: A driver holds its own service token while it services its state and marks it outside while its thread runs a context; an idle driver may borrow an outside driver for one bounded pass that completes its due sleeps and detaches records already published as terminal, runs no context while borrowing, and then runs the detached contexts itself, while ring completions that need the submitting thread stay with the owner, and with several drivers an idle driver parks at most 1 ms between borrow attempts, because a context computing without waiting otherwise left its driver's deadlines unserviced until it waited again: a 100 ms timer beside a two-second computation fired at 1.99 s with two drivers and at 0.103 s with borrowing, on one CPU and on two ([result](../../../research/investigations/driver-handoff/DESIGN.md#result-idle-drivers-borrowing-a-computing-drivers-due-timers-d)), instead of only moving ready contexts to an idle driver, which left the timer at 1.99 s because the starter's driver resumed the computation before the woken driver could take it.

Decision: A cancellation goes through the route that holds the operation: an asynchronous cancel on the Linux ring, `CancelIoEx` on the Windows port, and an interruption of the helper executing it, a signal installed without restart on POSIX and `CancelSynchronousIo` on Windows, repeated each millisecond until the operation completes, while Windows helper accepts and transfers use bounded readiness polls and bounded sends use nonblocking mode, returning the first transferred prefix and attempting to restore blocking mode without replacing that outcome, because `CancelSynchronousIo` does not end Winsock waits and writability promises only some buffer space; an operation whose own outcome came first completes with it, because each route reports a cancelled operation only when it transferred nothing, instead of polling before every blocking call, which neither bounds a large socket send nor protects a standard stream another process can drain between the poll and the call ([Windows transfer analysis](../../../research/investigations/context-cancellation/README.md#windows-helper-sends)).

Decision: A body hands its deadline to the submit, and an operation with a deadline is never made on the driver thread: a socket transfer or accept carrying a never-firing watch waits for readiness even before any other context runs, and any other operation goes to the helpers and switches the program to the policy the first context other than the root switches it to, every later operation the ring does not carry running on the helpers, because the driver thread is the one that must end it and a program that bounds a wait waits on another party, as a program with contexts does, instead of arming the deadline after the operation was routed, which left such an operation blocking the only thread that could cancel it, or sending that one operation to a helper that retires after it, which would keep the program's other operations on its thread but needs a pool that shrinks, reopened when a program that never spawns and bounds a stream wait shows the helper handoff costing its other operations.

Decision: A pool that `WF_IO_HELPERS` pins grows by one helper when none is free to take an operation with a deadline or a real cancellation watch, and the waiting thread of a pool pinned at zero leaves such an operation to that helper, because [PRE-2] produces the operation's outcome once its deadline is reached, which the thread inside the operation cannot bring about, instead of keeping the pinned count exactly, under which a pool pinned at zero ran the operation on the waiting thread and waited past the deadline.

Decision: A watched wait uses the per-driver list of the [context-cancellation decision](../../language/system-interface/context-cancellation.md), selects its completion reason on the owning driver, and stores that reason in the native record's file-open diagnostic word, because file opens take no cancellation watch so the request kinds are disjoint and the existing 160-byte record and helper/ring cancellation marker suffice, instead of enlarging every record or reserving a second monotonic-clock value for cancellation.

Decision: A real watch routes a pending socket accept, receive or send through the native ring or a helper that observes its bound rather than the driver's descriptor-only readiness poll, because the driver's wake epoch lets it request cancellation on those routes and Windows helper socket waits recheck that request between polls capped at 50 ms, while the driver's descriptor-only readiness poll cannot observe a firing, instead of leaving a fired source waiting for unrelated socket readiness; a never watch takes the ordinary route after one pointer comparison ([prototype mechanism](../../../research/investigations/context-cancellation/README.md#the-mechanism-under-every-shape)).

Rejected:
- One timer thread for the whole program: rejected because every expiry would cross to the driver that owns the waiting context, whose own loop already wakes at the earliest instant it is given while it runs no context, and an idle driver's borrow services the deadlines of one that is running a context; a single driver whose thread computes is the open case the driver-handoff work addresses ([study](../../../research/investigations/driver-handoff/DESIGN.md)).
- A linked timeout on each ring entry: rejected because the readiness and helper routes need the driver's bound anyway, so the ring would carry a second mechanism for the same deadline.
- Polling for readiness before each blocking helper call: rejected because a standard stream shared with other processes can be ready at the poll and empty at the call, which then blocks past the deadline.
- Keeping a pinned helper count exact for an operation with a deadline: rejected because a pool pinned at zero then runs the operation on the thread that must end it, which waits past the deadline [PRE-2] rules out.
