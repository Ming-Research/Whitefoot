Decision: A stored aggregate result crosses the call boundary as its LLVM first-class value when each scalar leaf of its representation gets its own return register on every admitted target, which allows at most three integer-class words and two floating leaves, and a larger one keeps the caller's destination pointer, because a call the host optimizer does not inline otherwise stores its small result into caller memory that the caller reloads, while beyond that budget LLVM silently returns the value through a hidden pointer after all, or on x86-64 returns a third floating leaf through the x87 stack, which passes through memory and turns a signaling NaN into a quiet one, so the [result-register investigation](../../research/investigations/result-registers/DESIGN.md#demotion-probe) bounds register leaves rather than bytes, instead of a destination for every aggregate, every aggregate by value, a byte bound, `fastcc`, or packing leaves into integer words. The budget is that of x86-64, the smallest among admitted targets, so every target shares one ABI, and a linked definition whose result fits returns the same value through an LLVM definition over its C body. The measured gain is the boundary's alone: each surviving call loses its result's store and reload, and on the timed hash-map and owning-map paths no call changes whether it is inlined ([timing](../../research/investigations/result-registers/DESIGN.md#timing)).

Decision: A definition whose result returns in registers keeps its unchanged destination-form body under an internal `<symbol>.body` symbol, never marked always-inline, and its public symbol becomes an entry that gives the body one frame slot, calls it and returns the loaded value, because the host then optimizes the body alone, as it optimizes a destination-form definition, before it inlines the body into its one caller, so the body keeps every loop structure the destination form gives it, while a body that returns the value lets the host fold its final exit test into a `select`, which lost the threaded ASCII loop of `records` in the [lowering comparison](../../research/investigations/result-registers/DESIGN.md#lowering), instead of joining every return in one block that loads a local result slot, or loading the slot at each return. The form relies on that pass order: a host that inlined the body before optimizing it would merge it unoptimized. A caller stores the returned value into the storage its plan selected, and parameters, their facts and storage plans are unchanged.

Rejected:
- A destination for every stored aggregate: rejected because every call that stays out of line pays a store and a reload of its small result, measured on the surviving hash-map `find`, `insert` and `remove` calls, while a register return pays neither.
- Every stored aggregate by value: rejected because LLVM returns a value with more integer leaves than return registers through a hidden pointer anyway, so larger results gain nothing and their first-class copies are lowered one element at a time, and on x86-64 a third floating leaf would lose a signaling NaN's bits in the x87 stack.
- A 16-byte bound: rejected because four 32-bit fields and a 16-byte array fit it and are still returned through a hidden pointer on x86-64, three 32-bit floats fit it and lose bit-exactness through the x87 stack, and three 64-bit words exceed it yet return in registers.
- A 16-byte bound added to the leaf budget: rejected because it sends 24-byte three-leaf results such as `(u64, Option<u64>)` through memory although they return in registers, and the maintained programs return such results.
- `fastcc` for internal functions: rejected because the destination is an IR parameter that no calling convention removes, and linked C bodies share the callable ABI.
- Packing a result of at most two words into integer registers, as C and Rust do: rejected because it needs per-target coercion rules and packing code at every boundary, while every surviving result of at most two words in the maintained programs already fits one register per leaf; reconsider when such a result needs more integer leaves than registers.
- A per-target budget, eight integer and eight floating leaves on AArch64: rejected because emitted signatures, linked definitions and their tests would then differ by target, while the surviving results between the two budgets in the maintained programs, the launcher's `ExitStatus` and eight four-word results, lie on no measured path ([corpus](../../research/investigations/result-registers/DESIGN.md#corpus)); reconsider when such a call lies on one.
- Joining every return in one block that loads the callee's own result slot: rejected because the host folds the final exit test into a `select` at that block before JumpThreading can thread it, which removed the inner ASCII loop of `records`, and the maintained records comparison failed at two widths in every hosted run of that form; its faster hash-map trace came from the host inlining `find` and `remove`, whose probe loop it had not yet unrolled, not from the register return.
- Loading and returning the slot at each exit, whole or leaf by leaf: rejected because the host gathers those returns into one block itself and folds the same test, and the joined aggregates, which SROA does not split after inlining, grew the hash-map `find` from 144 to 250 instructions.
- Marking the internal body always-inline: rejected because the always-inliner runs before per-function optimization, so the body would be merged into its entry unoptimized and meet the same folding.
