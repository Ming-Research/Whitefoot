Decision: Resolve the running compiler's directory once and select its sibling `clang[.exe]` when present, reporting an unusable sibling as a toolchain error with its expected path rather than selecting host clang; when no sibling exists, retain the source-build defaults, `/usr/bin/clang` on Unix and PATH `clang` on Windows, with no public toolchain override, because release packages must use their companion compiler while source builds and their existing CI still use the configured host toolchain, instead of requiring every source build to stage a release layout or allowing an override to replace a package's compiler.

Decision: Carry that resolved toolchain through native compilation, runtime C construction, capability probes, stack reports, full LTO and cached ThinLTO links, keeping the once-per-process syntax/ABI probes against the selected executable as [backend-facts](backend-facts.md) requires and the Darwin method probe as [resource-exhaustion-floor](resource-exhaustion-floor.md) requires; source-build probe I/O or launch failures retain the conservative legacy syntax/ABI forms and select Darwin inline probing with an explicit 4096-byte interval, while packaged mode first verifies `clang --version` and reports probe scratch-file, launch or signal failures as toolchain errors, with ordinary probe rejection selecting the legacy syntax/ABI form or Darwin inline method respectively, because independent selection can probe one LLVM consumer and emit to another and an unusable selected tool is different from an unsupported form, instead of resolving clang separately at each invocation, fixing the build host's capability answers into the executable or treating package probe failures as syntax rejection. Neither mode emits unprobed Darwin functions; an unsupported selected inline method fails native compilation rather than weakening the floor.

Decision: In packaged mode on Linux, require bundled lld and its `ld.lld` driver alias, passing the absolute alias path by `--ld-path` for every ordinary, full-LTO and cached ThinLTO link; a missing alias or unusable packaged linker reports the expected path and a toolchain error without host fallback, because [lld's dispatcher](https://github.com/llvm/llvm-project/blob/llvmorg-22.1.8/lld/Common/DriverDispatcher.cpp) selects the ELF driver by executable name and a partial bundle must not silently use another LLVM installation, instead of canonicalizing the alias to generic `lld`, relying on PATH or applying bundled linker selection only to LTO.

Decision: In packaged mode on macOS, require a valid explicit macOS `SDKROOT`, or discover the SDK with `/usr/bin/xcrun --sdk macosx --show-sdk-path` when `SDKROOT` is absent, and discover Apple's system linker with xcrun; pass the selected SDK by `-isysroot` and the absolute linker by `--ld-path`, reporting invalid SDKROOT or failed discovery as a toolchain error, because upstream clang does not supply the host SDK and the selected link contract retains Apple's linker with bundled libLTO, instead of substituting ld64.lld, quietly replacing an invalid explicit SDK, or falling back to host clang.

Decision: Native-cache toolchain identity includes the resolved clang path and first version-output line, the explicitly selected linker path, and the selected macOS SDK path when applicable, because these choices affect native construction even when clang's version line is unchanged, instead of keying reused runtime and native products only by clang's version or path. Source-build mode retains its default linker and SDK behavior; this identity does not claim to detect changed toolchain bytes at unchanged paths and version strings.
