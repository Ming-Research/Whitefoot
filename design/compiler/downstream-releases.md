Decision: Programs written in Whitefoot that are projects of their own, such as firn, Halo and Snowghost, live in their own repositories with their own gates, while this repository keeps the language, the compiler and the standard library, because one shared gate ran the compiler's whole suite on every application push and the applications' cases on every compiler push, while the gates the applications need, Redis behavior differentials, the Lua oracle corpus and timing on the owner's 14900K host, belong in no compiler gate, instead of application lanes inside this repository's gate.

Decision: A downstream takes the compiler as a published release and pins it by name, a release being made on request for a main commit whose gate passed, named `wf-` and the commit's first 12 hex digits for the default lightweight mode, and holding that commit's gate-profile `whitefootc` for linux-x86_64 and macos-arm64, and an unmerged commit whose gate passed getting an experiment release, `wf-exp-`, that a downstream pins only on an experiment branch; the opt-in bundled mode adds `-bundled` to either tag, because a downstream needs a compiler that changes only when it chooses to adapt to it, while the specification's version advances with every approved rule change and the compiler changes within one version, instead of a release per specification version or a downstream that builds the compiler from a submodule of this repository.

Decision: A release also holds `whitefoot-language.tar.gz`, its commit's `spec/kernel-spec.md`, `lib/std/modules.wfg` and every `lib/std/**/module.wfm` at their repository paths, listed in the manifest and covered by `SHA256SUMS`, which Whitefoot-kit downloads beside the compiler, because each downstream pins a different release while the specification changes almost daily, so a writer reading another commit's specification writes programs its pinned compiler refuses or forms it has retired, and an external user has only the release, instead of a copy of the newest specification kept in Whitefoot-kit, which differs from what each downstream pins, or writers fetching the files from this repository at the pinned commit, which needs this repository's layout and network access to it.

Decision: A release is made only by hand, and a release more than 30 days old is removed by a weekly run unless it is the newest lightweight release of a main commit or a bundled release of a main commit, a removed release being made again on request, because each release is made for a downstream that needs its commit and the owner periodically moves every downstream to the newest release, as a provisional choice for Whitefoot's period of rapid change, reopened when that period ends and downstreams need releases that last, instead of a release of every main commit, keeping every release, or keeping the releases downstreams pin, which would make this repository read its consumers.

Decision: This repository's gate builds no downstream program, and a compiler change that breaks one shows when the periodic upgrade moves that downstream to a newer release, because the upgrade runs the downstream's own gate against the newer compiler and adapts the program in the same change, instead of a scheduled downstream run against main or a downstream case pinned in this gate.

Decision: The release workflow's `bundle_toolchain` input defaults to false, preserving existing lightweight compiler tags, asset names, archive contents and host-toolchain prerequisites; its Linux compiler uses the LLVM major the commit pins for the gate, recorded as `linux_llvm_major` for Whitefoot-kit to install, because existing downstreams take frequent small releases and already provision that qualified host toolchain, instead of changing every existing release and extraction consumer when a bundled package is requested. Decision: Setting `bundle_toolchain=true` produces Linux x86-64, macOS arm64 and Windows x86-64 bundles under `wf-<12 hex digits>-bundled` or `wf-exp-<12 hex digits>-bundled`, with assets `whitefootc-linux-x86_64-bundled.tar.gz`, `whitefootc-macos-arm64-bundled.tar.gz` and `whitefootc-windows-x86_64-bundled.zip`; each keeps the compiler, clang and lld in `bin/`, clang builtin headers and the retained compiler-rt builtins/crt objects in their upstream resource layout, the shared-library dependency closure, macOS libLTO, retained-component licenses and a toolchain manifest, and the release's specification and standard-library interface files, because the first external release needs a companion native compiler while existing lightweight tags may already be published and have extraction consumers, instead of replacing existing tag assets or requiring bundled releases to use the host's clang. The Linux bundle still requires system development headers/libraries and the macOS bundle Apple's SDK and system linker; the Windows bundle requires nothing installed beyond Windows itself (its acceptance ran on Windows Server 2022 and no other Windows release was checked), and no other platform lane is selected.

Decision: The Windows bundle carries `bin/whitefootc.exe` linked with a static C runtime beside the clang, lld, MinGW-w64 headers, import libraries and compiler-rt builtins trimmed from the pinned llvm-mingw release (UCRT variant, whose digest `.github/toolchain/llvm-assets.json` records), and is a zip archive that exists only in bundled mode, because the Windows SDK and Visual C++ headers and libraries may not be redistributed in a package, a clean Windows machine has no Visual C++ redistributable for a dynamically linked compiler to import, a zip is what Windows extracts without extra tools, and a lightweight release has no toolchain for a Windows compiler to use, instead of requiring the user to install Visual Studio Build Tools, shipping the Visual C++ redistributable DLLs, a tar.gz like the other two platforms, or a lightweight Windows compiler that finds the host's clang.

Decision: A bundled release is published only after the reusable acceptance workflow qualifies every required check on the exact candidate archive bytes from the release jobs, and the same workflow can be dispatched manually against an existing release; the workflow revision supplies the maintained acceptance runner and witness, while the verified release manifest identifies the source commit of the unchanged candidate compiler and language bytes; failed or unverified checks, including unsupported witness behavior and macOS host-clang denial and the Windows archive's run in a Server Core container, block publication without changing expectations, because a candidate commit may predate the acceptance files and qualifying a staging tree or rebuilding a package for testing does not establish that the delivered archive resolves its companion toolchain and preserves native behavior, instead of requiring acceptance files from the candidate commit, publishing before acceptance or treating a standalone trimming smoke test as release qualification. The acceptance artifact records the selected archive hashes, compiler/toolchain identities, commands and check results; an existing lightweight release remains outside the bundled acceptance claim, and a bundled release made before the Windows archive existed is qualified on the other two.

Decision: The Windows archive is qualified by installing it inside a Windows Server Core container started from the stock image, with the runner's build matched to the image's, using the commands of the Windows section of the getting started guide (its download replaced by a copy of the candidate archive and of the release's checksum file, every other PowerShell block and the guide's programs run as written, read by the check's own small reader of column-zero three-backtick fences, which fails on any other fence form instead of skipping the block), and running its compiler there, where the same witnesses, coroutine IR, link modes and cache reports run as for Linux, the stack exhaustion image built there runs on the runner because a crash that ends a process holding the floor's gibibyte of committed stack took about twenty minutes in the container and about a second on the runner, in [measurements](../../research/experiments/windows-container-crash-exit/README.md#result) of an equivalent program on the hosted images, while the property checked is the probing method the packaged clang chose, every produced image is read for Visual C++ or MinGW runtime imports, and removing the headers, clang or lld from the installed package must fail with the missing component named, because a hosted Windows runner holds Rust, LLVM, Visual Studio and the Visual C++ redistributable, so a package that used any of them or lacked a DLL a clean machine lacks would pass there, while the container has none, instead of hiding the runner's clang and running on the runner, reusing the macOS execution-denial sandbox, extracting the archive by a command the guide does not state, or running the corpus target's [documentation example test](verification/documentation-examples.md) against the package's compiler, which needs Rust that the container does not hold.

Decision: The Linux x86-64 and macOS arm64 archives are qualified by installing them with the commands of their section of the getting started guide, from a directory whose name holds a space and away from the repository, and building and running the guide's programs with the installed compiler, requiring each program's exit status and the rejected program's text to be the ones the guide states, the installed directory being the package every other check inspects, where the guide's download is replaced by a copy of the candidate archive and of the release's checksum file and every other command runs as written, so that on Linux the commands run as root in the stock Ubuntu container and the guide's `apt-get` line is the only source of the libraries the bundled toolchain links against, and on macOS they run inside the sandbox that denies the host's clang, with `xcode-select --install` the one command not run, because the hosted image already holds the Command Line Tools and the command would open an installer window, and the check showing instead the SDK and the system linker they provide, the guide being read by a small reader of column-zero three-backtick fences that fails on any other fence form instead of skipping the block, because a guide whose commands no run executes stays right only until the next edit of either, and the use the bundled package was made for is a reader following that guide on a machine that holds no compiler of its own, instead of extracting the archive by the check's own command and comparing the guide's text with it, which shows equal text and not commands that work and builds none of the guide's programs with the package, or running the corpus target's [documentation example test](verification/documentation-examples.md) against the package's compiler, which needs Rust and a host linker that the clean Linux container lacks and the macOS denial sandbox must not rely on.

Decision: The weekly removal never removes a bundled release of a main commit, `wf-<12 hex digits>-bundled`, by age, and that release does not take the place of the newest release of a main commit, which stays with the newest lightweight release; a bundled experiment release, `wf-exp-<12 hex digits>-bundled`, is removed after 30 days like any experiment release, because an external user pins a bundled release by name and no periodic upgrade moves them to a newer one, which the 30-day rule relies on, while a bundled release holding the newest place would let the lightweight release that downstreams pin age out, instead of the 30-day rule for every `wf-` tag or a separate longer window for bundled releases.

Rejected:
- A Windows package without a C library and linker, completed by the user's Visual Studio Build Tools: rejected because the user must install a multi-gigabyte toolchain whose license for non-individual use is the user's to hold, so a clean machine cannot just run the package.
- Redistributing the Windows SDK and Visual C++ headers and libraries in the package: rejected because their license allows redistributing only the linked result and the Visual C++ runtime DLLs.
- A release that carries no documents, writers reading this repository at the release's commit: rejected because writers then depend on this repository's layout and on network access to it, which an external user or an offline writer lacks.
- Path-filtered application lanes in this repository's gate: rejected because the applications would stay under this repository's specification, design-tree and complete-`make check` merge rules, and the Redis and Lua reference tooling would enter its CI.
- One repository for every application: rejected because Halo is a general Lua engine meant to stand alone, and every firn push would run Halo's gate.
- A release per specification version, keeping only the newest build of each: rejected because a downstream pinned to a version would receive every compiler change made within it.
- A daily release of main's last commit: rejected because a release is made when a downstream needs a commit, so each already has a user.
- A submodule of this repository in each downstream, building the compiler when no release exists: rejected because the downstream would compile this repository in its own CI and carry its whole tree for one executable.
- Applying the 30-day rule unchanged to bundled releases: rejected because an external user's pinned release would disappear a month after it is published, and a bundled release in the newest place would end the exemption of the lightweight release that downstreams pin.
- A separate, longer retention window for bundled releases: rejected because it adds a number to choose and still ends in an expiry the external user meets, where a release made once by hand for the outside needs none.
- A scheduled downstream run against main's newest compiler: rejected because the periodic upgrade runs the same downstream gates and adapts the code in the change that moves the pin.
