Decision: Programs written in Whitefoot that are projects of their own, such as firn, Halo and Snowghost, live in their own repositories with their own gates, while this repository keeps the language, the compiler and the standard library, because one shared gate ran the compiler's whole suite on every application push and the applications' cases on every compiler push, while the gates the applications need, Redis behavior differentials, the Lua oracle corpus and timing on the owner's 14900K host, belong in no compiler gate, instead of application lanes inside this repository's gate.

Decision: A downstream takes the compiler as a published release and pins it by name, a release being made on request for a main commit whose gate passed, named `wf-` and the commit's first 12 hex digits for the default lightweight mode, and holding that commit's gate-profile `whitefootc` for linux-x86_64 and macos-arm64, and an unmerged commit whose gate passed getting an experiment release, `wf-exp-`, that a downstream pins only on an experiment branch; the opt-in bundled mode adds `-bundled` to either tag, because a downstream needs a compiler that changes only when it chooses to adapt to it, while the specification's version advances with every approved rule change and the compiler changes within one version, instead of a release per specification version or a downstream that builds the compiler from a submodule of this repository.

Decision: A release also holds `whitefoot-language.tar.gz`, its commit's `spec/kernel-spec.md`, `lib/std/modules.wfg` and every `lib/std/**/module.wfm` at their repository paths, listed in the manifest and covered by `SHA256SUMS`, which Whitefoot-kit downloads beside the compiler, because each downstream pins a different release while the specification changes almost daily, so a writer reading another commit's specification writes programs its pinned compiler refuses or forms it has retired, and an external user has only the release, instead of a copy of the newest specification kept in Whitefoot-kit, which differs from what each downstream pins, or writers fetching the files from this repository at the pinned commit, which needs this repository's layout and network access to it.

Decision: A release is made only by hand, and a release more than 30 days old is removed by a weekly run unless it is the newest release of a main commit, a removed release being made again on request, because each release is made for a downstream that needs its commit and the owner periodically moves every downstream to the newest release, as a provisional choice for Whitefoot's period of rapid change, reopened when that period ends and downstreams need releases that last, instead of a release of every main commit, keeping every release, or keeping the releases downstreams pin, which would make this repository read its consumers.

Decision: This repository's gate builds no downstream program, and a compiler change that breaks one shows when the periodic upgrade moves that downstream to a newer release, because the upgrade runs the downstream's own gate against the newer compiler and adapts the program in the same change, instead of a scheduled downstream run against main or a downstream case pinned in this gate.

Decision: The release workflow's `bundle_toolchain` input defaults to false, preserving existing lightweight compiler tags, asset names, archive contents and host-toolchain prerequisites; its Linux compiler uses the LLVM major the commit pins for the gate, recorded as `linux_llvm_major` for Whitefoot-kit to install, because existing downstreams take frequent small releases and already provision that qualified host toolchain, instead of changing every existing release and extraction consumer when a bundled package is requested. Source builds retain those same defaults.

Decision: Setting `bundle_toolchain=true` produces Linux x86-64 and macOS arm64 bundles under `wf-<12 hex digits>-bundled` or `wf-exp-<12 hex digits>-bundled`, with assets `whitefootc-linux-x86_64-bundled.tar.gz` and `whitefootc-macos-arm64-bundled.tar.gz`; each keeps `whitefootc`, clang and lld in `bin/`, clang builtin headers and the retained compiler-rt builtins/crt objects in their upstream resource layout, the shared-library dependency closure, macOS libLTO, retained-component licenses and a toolchain manifest, and the release's specification and standard-library interface files, because the first external release needs a companion native compiler while existing lightweight tags may already be published and have extraction consumers, instead of replacing existing tag assets or requiring bundled releases to use the host's clang. The bundle still requires system development headers/libraries and, on macOS, Apple's SDK and system linker; no Windows bundle or additional platform lane is selected.

Decision: A bundled release is published only after the reusable acceptance workflow qualifies every required check on the exact candidate archive bytes from the release jobs, and the same workflow can be dispatched manually against an existing release; the workflow revision supplies the maintained acceptance runner and witness, while the verified release manifest identifies the source commit of the unchanged candidate compiler and language bytes; failed or unverified checks, including unsupported witness behavior and macOS host-clang denial, block publication without changing expectations, because a candidate commit may predate the acceptance files and qualifying a staging tree or rebuilding a package for testing does not establish that the delivered archive resolves its companion toolchain and preserves native behavior, instead of requiring acceptance files from the candidate commit, publishing before acceptance or treating a standalone trimming smoke test as release qualification. The acceptance artifact records the selected archive hashes, compiler/toolchain identities, commands and check results; an existing lightweight release remains outside the bundled acceptance claim.

Rejected:
- A release that carries no documents, writers reading this repository at the release's commit: rejected because writers then depend on this repository's layout and on network access to it, which an external user or an offline writer lacks.
- Path-filtered application lanes in this repository's gate: rejected because the applications would stay under this repository's specification, design-tree and complete-`make check` merge rules, and the Redis and Lua reference tooling would enter its CI.
- One repository for every application: rejected because Halo is a general Lua engine meant to stand alone, and every firn push would run Halo's gate.
- A release per specification version, keeping only the newest build of each: rejected because a downstream pinned to a version would receive every compiler change made within it.
- A daily release of main's last commit: rejected because a release is made when a downstream needs a commit, so each already has a user.
- A submodule of this repository in each downstream, building the compiler when no release exists: rejected because the downstream would compile this repository in its own CI and carry its whole tree for one executable.
- A scheduled downstream run against main's newest compiler: rejected because the periodic upgrade runs the same downstream gates and adapts the code in the change that moves the pin.
