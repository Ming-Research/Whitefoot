Decision: Programs written in Whitefoot that are projects of their own, such as firn, Halo and Snowghost, live in their own repositories with their own gates, while this repository keeps the language, the compiler and the standard library, because one shared gate ran the compiler's whole suite on every application push and the applications' cases on every compiler push, while the gates the applications need, Redis behavior differentials, the Lua oracle corpus and timing on the owner's 14900K host, belong in no compiler gate, instead of application lanes inside this repository's gate.

Decision: A downstream takes the compiler as a published release and pins it by name, a release being made on request for a main commit whose gate passed, named `wf-` and the commit's first 12 hex digits, and holding that commit's gate-profile `whitefootc` for linux-x86_64 and macos-arm64, and an unmerged commit whose gate passed getting an experiment release, `wf-exp-`, that a downstream pins only on an experiment branch, because a downstream needs a compiler that changes only when it chooses to adapt to it, while the specification's version advances with every approved rule change and the compiler changes within one version, instead of a release per specification version or a downstream that builds the compiler from a submodule of this repository.

Decision: A release carries no documents for the downstream's writers, who read the specification, the maintained programs and the standard library's interfaces in this repository at the release's commit, as a provisional choice because what a release should carry for writers and in what form is a larger choice than the release mechanism, reopened when the downstreams' first upgrades show what their writers read or a writer must work without this repository ([TODO](../../docs/todo.md#modules-and-libraries)), instead of a documentation bundle chosen now.

Decision: A release is made only by hand, and a release more than 30 days old is removed by a weekly run unless it is the newest release of a main commit, a removed release being made again on request, because each release is made for a downstream that needs its commit and the owner periodically moves every downstream to the newest release, as a provisional choice for Whitefoot's period of rapid change, reopened when that period ends and downstreams need releases that last, instead of a release of every main commit, keeping every release, or keeping the releases downstreams pin, which would make this repository read its consumers.

Decision: This repository's gate builds no downstream program, and a compiler change that breaks one shows when the periodic upgrade moves that downstream to a newer release, because the upgrade runs the downstream's own gate against the newer compiler and adapts the program in the same change, instead of a scheduled downstream run against main or a downstream case pinned in this gate.

Rejected:
- Path-filtered application lanes in this repository's gate: rejected because the applications would stay under this repository's specification, design-tree and complete-`make check` merge rules, and the Redis and Lua reference tooling would enter its CI.
- One repository for every application: rejected because Halo is a general Lua engine meant to stand alone, and every firn push would run Halo's gate.
- A release per specification version, keeping only the newest build of each: rejected because a downstream pinned to a version would receive every compiler change made within it.
- A daily release of main's last commit: rejected because a release is made when a downstream needs a commit, so each already has a user.
- A submodule of this repository in each downstream, building the compiler when no release exists: rejected because the downstream would compile this repository in its own CI and carry its whole tree for one executable.
- A scheduled downstream run against main's newest compiler: rejected because the periodic upgrade runs the same downstream gates and adapts the code in the change that moves the pin.
