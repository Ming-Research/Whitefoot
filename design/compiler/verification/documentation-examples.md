Decision: Documentation opts complete, canonical Whitefoot programs into gate verification through a fenced block whose marker is `whitefoot`, with optional `run exit=N` or `reject RULE` and an optional `file=NAME` basename defaulting to `example.wf`, because Whitefoot and Whitefoot-kit's writing guide share one convention that checks the program together with its reader-visible claim instead of relying on an author's remembered compiler result. The scope is every Markdown file under `docs/` and both repository README translations; bare `whitefoot` requires the acceptance that `whitefootc --check` reports without lowering, linking or running, a run compiles and links and exits without arguments with the stated portable status from 0 through 255, and rejection requires the first source diagnostic to cite the stated rule. Unknown attributes, two outcomes and attributes on other markers fail with the document and fence line; legacy `wf` fences are ignored. Fragments use `text` or inline code instead of program markers.

Decision: The documentation check is a Rust integration test in the existing corpus target, reusing the CLI's source-checking library entry for acceptance and rejection and the ordinary compilation, native linking and bounded execution support for runs, because compiler-backed checks belong to `cargo test` and the corpus gate already runs the whole target instead of introducing a second extractor or verification stage. It collects failures across all blocks so one incorrect example does not hide the others.

Decision: A `whitefoot reject` block may attach an exact `whitefoot-output` fence separated only by blank lines, whose bytes are compared with the compiler's complete default text rejection including its final newline and the logical filename chosen by `file=NAME`, because the diagnostic the reader sees is part of the example's claim instead of comparing only selected fields or silently updating expected text. Both backtick and tilde fences have at least three markers and close with the same character and no fewer markers. The [getting-started guide's checking note](../../../docs/guide/getting-started.md#how-examples-are-checked) owns the author-facing convention.

Rejected:
- A Python extractor: rejected because compiler-backed checks go through `cargo test`, and a separate extractor would duplicate the Rust test's source and outcome boundary.
- Checking untagged fences: rejected because existing articles contain fragments and output that are not complete programs, so treating every fence as source would invent claims those articles do not make.
- Regenerating expected output automatically: rejected because the expected text is what the reader sees and must change only when an author changes it; rewriting it from the actual rejection would conceal a changed claim.
