Decision: Conversion mode and numeric endpoint types survive explicitly from semantic formation through goals and checked expressions, with symbolic endpoints retained until concrete lowering, because exact, checked and domain-query forms share type pairs but have different obligations and result shapes, instead of recovering mode from whole-type totality or Result layout. Domain checking and conditional integer-result publication stay in the existing entailment walk and ledger, with a focused domain helper, instead of a second analysis pass; the [implementation sequence](../../research/investigations/numeric-conversions/DESIGN.md#implementation-sequence-after-owner-review) identifies the affected owners.

Decision: Bare conversion lowers under its retained domain proof to the selected value operation, while checked and domain-query conversions share total validity computation and only checked builds Result, because removing an impossible source failure path should not depend on optimizer recognition and a validity query cannot execute an invalid partial cast, instead of lowering every form through a checked Result or adding a general backend-assumption family for this operation. Specified NaN normalization remains part of value production.

Decision: Sufficient conversion bounds carry positive-only normalization and checked integer values reuse the existing private Result payload as their fact destination, because failure of a sufficient interval cannot refute representability and a conversion result is not a storage assignment, instead of giving a sufficient interval an equivalent negation or inventing a SET commit identity for the saved value.

Decision: Retain integer wrapping as an explicit conversion mode and lower it through the shared integer cast using the source signedness for extension, while proof consumers retain modular expression identity without exact input equality, because the existing cast already implements truncation, sign extension, zero extension and same-width bit preservation and wrapping has no domain obligation or Result payload, instead of a second conversion pipeline, a checked-result fallback or reusing exact-conversion evidence. The [companion comparison](../../research/investigations/numeric-conversions/DESIGN.md#companion-operations-and-explicit-deferrals) identifies the signed-to-unsigned widening control.

Decision: The rounding conversion keeps its own mode through checked expressions and IR, and the emitter validates its float destination and then emits the exact conversion's float-destination sequence, because LLVM's unconstrained `sitofp`, `uitofp`, `fpext` and `fptrunc` round an inexact value to nearest with ties to even in the default floating-point environment, which compiled programs never leave (the emitter uses no constrained intrinsics, `strictfp` or fast-math flags, and no runtime or source operation changes the rounding mode), and that sequence already carries the canonical NaN selection, instead of a software rounding sequence or constrained intrinsics.

Rejected:
- Mapping the rounding mode to the exact mode before the IR: rejected because a backend fact or assumption later derived from an exact conversion's discharged domain would then attach to a rounding conversion that has no domain proof.
