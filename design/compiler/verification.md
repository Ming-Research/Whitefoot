Decision: Local heavy verification uses one host-wide owner across worktrees, bounded independent build and test parallelism, visible phase/exit accounting and a cancellable process group with an explicit command deadline, because overlapping optimized builds and suites made an ordinary build take minutes without test progress in the [build/test investigation](../../research/investigations/test-economy/build-and-test.md), instead of independently spending the host's whole capacity in each agent or hiding build-lock waits inside a test command. A command deadline reports incomplete verification and never selects source acceptance.

Decision: Tests reuse immutable native objects and dependency-tracked example executables while rerunning their assertions and preserving distinct compiler modes and macro-interposed builds, because repeated compilation of identical support code checks no new behavior and stale compiler-dependent artifacts check the wrong revision, instead of rebuilding every support unit for each case or caching test verdicts.

Decision: Compiler-backed verification uses the existing optimized Rust `gate` profile with assertions and overflow checks retained, while dev compiler binaries are built when debugging the Rust implementation, because unoptimized proof analysis makes real-source tests much slower and a separate dev build adds no assertion coverage to this profile, instead of routinely constructing and executing an additional unoptimized compiler for verification. This choice changes the Rust implementation's construction, not WF optimization options or source acceptance.

Decision: Local builds of the `gate` profile compile incrementally, while hosted CI builds it with incremental compilation off, because without it an edit rebuilds the whole crate once for the binary and once for the test harness, 83 s and 141 s on four cores, where the [measured edits](../../research/investigations/compiler-architecture/DESIGN.md#f9-changing-the-compiler-costs-minutes-per-edit) took 10 to 25 s with it, while a fresh CI checkout has no incremental state to reuse and its first build ran 3 to 4% and its measured tests about 9% slower with it, instead of one construction for both or splitting the crate for build latency.

Decision: Local canonical correctness verification and hosted correctness jobs consume one Makefile-owned group inventory and its execution recipes, with CI deriving its matrix from that inventory and retaining only host setup and scheduling, because separately written workflow commands can omit a local check or introduce an unreported extra even when both reuse Make targets in the [entry-point comparison](../../research/investigations/test-economy/redesign.md#one-correctness-inventory-for-local-and-ci), instead of maintaining two lists and adding another checker to compare them. Platform-specific qualification and paired performance remain explicitly separate, and correspondence review inspects filters and actual callers rather than treating matching group names as complete coverage evidence.

Decision: Automatic CI checks maintained correctness and performance regressions in the formal test system, with the canonical correctness gate and separate paired performance checks free of direct or indirect dependencies on research programs, scripts, fixtures and datasets; useful observations and necessary inputs/oracles are extracted into formal test ownership, while research remains explicitly invoked, because the [research-boundary audit](../../research/investigations/test-economy/redesign.md#research-boundary-and-extraction) finds experimental models, repeated measurements and shared research inputs wired into ordinary verification without distinct permanent-test grounds, instead of treating an experiment's executability or use of the current compiler as admission to daily CI. Use lightweight compiler-independent dependency checks plus completion review of unresolved dynamic and indirect paths, retaining normal complete checkouts, because supported reference checks catch accidental regressions without special checkout or cache conditions, instead of relying only on manual review or withholding research inputs from CI. Routine correctness CI and local `make check` never build or time a candidate/baseline pair; the separate performance workflow owns that comparison. Documentation and source comments may cite research evidence; the check reports its supported forms and does not claim a complete dependency proof.

Decision: A verification assertion is owned by the contract it checks: specification-derived acceptance, rejection and runtime requirements belong in conformance, complete program functions and interactions in programs, and additional compiler implementation obligations in compiler tests; canonical rendering visits the owned sources as a batch, and historical snapshots are individually migrated or retired against the active specification, because the [test-system redesign](../../research/investigations/test-economy/redesign.md#basic-test-contract) identifies useful properties independently of fixture language and executable packaging, instead of assigning arbitrary WF wrappers to Rust unit tests or keeping historical verdicts as a second correctness authority. These responsibilities do not require separate test executables.

Decision: A new test that compiles WF or constructs and executes its native output identifies the missing coverage and the additional compilation, execution or configuration it requires, preferring an existing case or a more direct implementation assertion when it supplies the required evidence, because repeated end-to-end construction accumulates across the suite and future compiler optimization does not justify redundant cases now, instead of treating every WF fragment as grounds for another compile/run case. Ordinary conformance compiler calls and necessary runtime observations remain; slowness alone does not justify removing coverage, and this admission rule adds neither a timing campaign nor a per-case approval requirement.

Decision: Paired performance regression compiles each revision's corresponding formal implementation of the same identified workload with that revision's compiler and ordinary runtime, while one current timing instrument checks complete results, validates the expected sample matrix and decides with unrounded paired ratios; workload names, fixtures and oracle interfaces must match before construction, because a language revision can preserve an algorithm and input while necessarily changing its accepted source spelling and owned-value ABI, so compiling only current source with the merge-base compiler can measure no baseline at all, instead of requiring byte-identical source across syntax-breaking language revisions or treating build failure as a passing performance result. Every measured invocation first compares identical candidate images and reports inconclusive evidence if that host control fails, while instrument changes additionally receive explicit slowdown controls under criteria stated before measurement, because the [identical-image failure](../../research/investigations/test-economy/redesign.md#identical-image-host-control-failure) demonstrates that qualification on one runner does not establish another invocation's conditions. Qualification controls do not establish a statistical false-alarm rate, and a one-width suspect or CPU-only regression remains visible without claiming the carried-forward rule detects every slowdown.

Decision: Conformance has only the `runnable` manifest status and pass/fail adapter outcomes; an unexpected unsupported stop fails, because a capability gap is a compiler defect rather than grounds to suspend a normative case, instead of pending/xfail statuses or a third non-failing gap outcome.

Decision: Accept/reject conformance reaches complete source-semantic publication through the same ordinary front-end continuation that full compilation consumes; run/unsupported cases continue through lowering and target compilation, because STOR-6 begins after source acceptance and an incidental host address domain cannot replace the source verdict, instead of an adapter-specific checker or requiring every source-only verdict to generate a native image.

Rejected:
- Shortening repeated schedules or removing normative cases merely because they are slow: rejected because those changes would remove the behavior evidence the gate is meant to preserve.
- A shared cache of compiler verdicts between unit tests and the native conformance adapter: rejected because the adapter must still reach each verdict through its own ordinary compilation path.
- Compiling current sources with both revisions' compilers: rejected because a syntax or ABI revision can make the merge-base compiler unable to construct an otherwise equivalent workload, producing no comparison evidence.
- Silently skipping a mismatched or unbuildable workload: rejected because absence of comparable evidence is not a passing regression result.
