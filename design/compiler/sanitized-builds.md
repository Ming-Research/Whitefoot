Decision: `whitefootc --sanitize address|thread` builds a program under AddressSanitizer with UndefinedBehaviorSanitizer, or under ThreadSanitizer, by adding the sanitizer's function attribute to the attribute group every emitted definition carries and the sanitizer's clang arguments to every runtime compile, emitted-module compile and link of the ordinary, full-LTO and cached builds, with the arguments in the native-cache keys, because clang adds no sanitizer attribute to definitions it reads as LLVM and its instrumentation passes skip a definition without one, and an option on the compiler lets anyone check their own accepted program, instead of instrumenting only the test harness's link or selecting the runtime by an environment variable, which the compiler's rule that no environment decides the runtime a program gets refuses.

Decision: A sanitized build changes no acceptance, lowering choice or verdict, only instrumentation: the restricted fork-child closure keeps `-fno-sanitize=all` after the sanitizer's arguments, UndefinedBehaviorSanitizer covers only the C runtime because it is a clang front-end check that LLVM input never passes through, the hand-written LLVM adapters of the ordinary library stay uninstrumented because every load and store they make is to their own stack slots, around a call to an instrumented C body, and AddressSanitizer's use-after-return detection stays off because its heap-allocated fake stack would keep deep recursion from reaching the guard band the [resource-exhaustion floor](resource-exhaustion-floor.md) reports exhaustion from. AddressSanitizer sees no bound inside memory the runtime maps and divides itself (the context frame pool, which holds the frames of waiting contexts, the concurrent map's tables, the io_uring rings and the snapshot mappings), so a clean run says nothing about accesses inside those mappings until the runtime marks their unused parts for it.

Decision: CI runs the corpus target's programs and every running conformance case, each case also built with the `--par` lowering and required to reach the same verdict, under both configurations in a Linux workflow of its own on the revisions the gate checks, writing each report to a file outside the case directories that fails the job whatever the case's own exit status, with leak reports off and AddressSanitizer's notice that it leaves the runtime's 1 GiB thread stacks, above its 64 MiB cleanup limit, poisoned at a call that does not return counted as no report, since an error that notice lets through still arrives as a report in the same file, and a pull request merges only with that workflow green on its head, because an accepted program has no memory error, undefined behavior or data race, so any report is a soundness defect of the checker, compiler or runtime found independently of the checker, instead of a gate group, since platform-specific qualification stays apart from the gate ([verification](verification.md)).

Rejected:
- Instrumenting only the harness's own link: rejected because outsiders could not build their own programs sanitized, and the harness link is not the path the compiler ships.
- Judging a case by its exit status alone: rejected because a case expecting a failing status could pass on the status a report exits with.
- Leak detection: rejected because the runtime keeps its process-lifetime objects until exit, which is not a memory error.
