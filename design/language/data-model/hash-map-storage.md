Decision: The owning HashMap uses enum buckets and occupancy-only migration into a fresh backing through the shared exchange helper, because the [matched comparison](https://github.com/mbbill/Whitefoot/blob/20f3b4d618fd64eff245a5b5e7a5162483f94c0b/research/experiments/container-representation/map-library/RESULTS.md#constant-interface-comparison-and-selected-helper-body) preserves must-consume pairs and lowers growth cost without enlarging every bucket, instead of destination planning or per-bucket windows. This accepts two live backings during rehash and dense storage's wide-growth advantage, not a universal layout winner.

Decision: A rebuild moves each owner straight from the old backing into the first available bucket of one capacity-bounded scan, and an owner the scan does not place, or that an exchange returns, goes back to the old backing, whose remaining owners are then parked in a stale window the map owns while the rebuild reports failure and a map holding parked owners refuses further rebuilds, because the counting argument that every owner finds a bucket is carried by no checked fact, so a retry loop has no progress [TERM-1], and a generic owner on that unreachable path can neither be dropped nor left in a window that must be released empty ([migration](../../../research/investigations/termination/runs/migration.md#hash-map-rebuild)), instead of retrying until a bucket frees, returning the stranded owners to the caller, or dropping them; this costs one empty-window allocation per map and leaves parked owners reachable by iteration and release but not by key.

Decision: HashMap insertion returns either a payload-free success or one shared pair payload with a replacement/refusal reason, because the [source comparison](https://github.com/mbbill/Whitefoot/blob/20f3b4d618fd64eff245a5b5e7a5162483f94c0b/research/experiments/container-representation/map-library/RESULTS.md#compact-result-boundary-control) establishes a smaller wide result and lower replacement/churn cost, instead of reserving separate storage for mutually exclusive returned pairs. This accepts a second match and a larger zero-sized result; it selects neither compiler union layout nor fewer transfers on every path.

Rejected:
- Planning destinations and permuting the old backing as the default rebuild: rejected because the direct ordinary protocol preserves must-consume owners with fewer requests and lower measured growth cost; its smaller same-capacity peak remains a reason to reconsider it for a memory-constrained consumer.
- One inline one-slot window in every bucket: rejected because it increases bucket stride without a consistent advantage over the compact enum protocol in the matched rebuild comparison.
- Selecting dense payloads as the universal representation from wide-growth timings: rejected because the separate index and dependent access have different measured costs, and there is no measured application distribution that makes wide growth the governing operation. A concrete consumer can select that tradeoff later.
- Duplicating the exchange inside migration solely to remove its intermediate result: rejected because the constant-interface source control removes that result but does not establish a stable independent timing benefit after accounting for the unchanged C controls; the registered performance criterion was not fully met.
- Keeping separate payload-bearing Replaced and Full variants as the library interface: rejected because their repeated pair storage and inactive-result initialization have a measured wide-value cost that an ordinary shared-payload form avoids without losing an ownership outcome.
- Inferring a compiler-known sparse representation or a universal compact-enum ABI from the result experiment: rejected because changing the public result alone separates this cost from bucket layout, and zero-sized pairs and retained replacement paths still expose tradeoffs.
