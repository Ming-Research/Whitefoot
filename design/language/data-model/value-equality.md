Decision: `==` and `!=` are one value equality over the equality types, decided from a type's structure at compile time: the integers, `unit`, enums and structs other than the storage shapes and `Box` that remove no capability and whose every payload field or field has an equality type, opaque ones included, and `Array<T, N>` of an equality type, so that two values are equal exactly when they are the same value, because writers compared structs, payload enums and fixed arrays field by field in hand-written helpers (eleven whole-struct comparators in one Snowghost file alone) and a rule read from the structure needs no annotation, runs no user code and leaves no run-time failure, instead of an equality each type declares, content equality of boxes and runtime-sized sequences now, or equality only through function-kind callbacks ([value equality](../../../research/investigations/value-equality/DESIGN.md#proposed-direction)).

Decision: Floats, and every type with a float part, are not equality types, and floats keep `feq` and its family, because IEEE equality is not reflexive and the checker uses a value equality as an equivalence it may substitute, instead of comparing float parts by their bits, which disagrees with `feq` on signed zero and NaN, or by IEEE equality, which breaks reflexivity.

Decision: Tag-only enums, `Bool` included, compare with `==` and `!=`, and `eeq` and `ene` retire, because a tag-only enum is an equality type whose values have no payload and a second spelling of the same equality would remain, instead of keeping the prefixed family beside `==`.

Decision: The checker reads a value equality by the definition the executable operation computes: an established equality of two structs decomposes into the equalities of their fields, a goal equality of two structs holds when every field equality does, and the range judgment reads an equality of two enum, struct or `Array` values as the equalities of their integer parts with an enum's tags equal and each payload part related under its variant, because proofs and code then share one equality, instead of an opaque predicate that yields no field fact, or an equality written only in range clauses that the executable language lacks.

Decision: A type parameter reaches `==` only through the built-in bound `Eq`, spelled like `Int` and `Float`, which admits exactly the equality types and implies copy, while a range clause of a function whose parameter is bounded only `copy` may still relate its values with `==`, stating the value equality at each concrete instance whose type is an equality type and nothing at any other, because floats are copy but not equality types, so a bound is where a generic body's `==` is checked at its definition, and the fill constructors keep one `copy`-bounded signature, instead of `==` on every copy type with a second, total-order float equality beside `feq`, or `==` on `copy` parameters checked only at instantiation.

Rejected:
- `==` on every copy type, floats compared by total order: rejected because a float would then have two equalities that disagree on NaN and signed zero.
- `==` on a `copy` type parameter checked only at each instantiation: rejected because the generic body would go unchecked and the error would land at a caller.
- An `opaque` exclusion from the equality types: rejected because `Array` is itself opaque and comparable, and equality reveals only whether two values are the same.
- An expansion of `==` into integer projections only inside generic range clauses: rejected because proofs would then hold an equality the executable language does not have.
- A conversion from a tag-only discriminant to an integer with integer comparison: rejected because it exposes the tag representation, invites integer operations and ordering, and adds a broader conversion proof surface.
- A per-type pure source mapper to integer codes with a separately reviewed injectivity guard: rejected because it duplicates a per-type ordinal convention and needs an external guard that exhaustiveness alone cannot discharge.
- Exhaustive nested matches over every ordered pair of variants: rejected because the repeated identity test would have needed a projected 6,952 source-level variant-pair arms.
