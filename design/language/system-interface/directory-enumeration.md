Decision: Directory enumeration transfers a bounded batch of records into a range reference the caller forms over byte storage the caller already owns, and advances the supplied directory cursor, because the destination is then storage whose extent the caller states with the ordinary bounds contracts, while a window owned by the directory handle would need a second draining interface and lifetime rules for the entries it hands out, instead of returning a reference to one entry, which no function may return at all, or a handle-owned window drained one item at a time.

Decision: An enumerated name reaches source only as name bytes and no order is fixed, because turning a name into a host string or path value would reintroduce a path model and a fixed order would promise what hosts do not provide, instead of ordered, path-valued entries.

Decision: A listing leaves out the self and parent entries, and a successful batch over a nonempty window holds an entry, the host operation reading again before it completes when a host batch held only those two, so the wait suspends once and its deadline governs every read, because a name given with a root never denotes them, so every program that uses a listed name must skip them, and the second host call costs nothing, being the call a caller makes anyway to reach the end of the listing, instead of reporting them unfiltered, returning a successful batch with no entry, or submitting the second read from the operation's finish.

Decision: A directory batch returns its outcome, its numeric endpoint and its entry count as separate results, the endpoint bounds holding unconditionally, because a numeric result carries its bound as an ordinary comparison the caller keeps after the call, while the same bound arriving inside a success variant's payload reaches the caller only through a later match on that payload, instead of a directory-specific proof producer or a bounds-failure branch the operation can never take.

Rejected:
- Reporting the self and parent entries unfiltered: rejected because each program must then skip them in the host's own encoding, which the directory walk in `tests/programs/wfgrep.wf` did for one-byte names only and so opened them on Windows, and the extra host call given for it is the call a caller makes anyway to reach the end.
- A successful batch with no entry when the host's batch held only the self and parent entries: rejected because it reports progress without any, so a caller that ends its walk at an empty batch misses the entries after it.
- Submitting the second read from the operation's finish: rejected because the finish then waits on a host read its frame does not suspend for, on the driver thread when no helper takes it and with no deadline, which the waiting contexts and their bounded waits forbid.
