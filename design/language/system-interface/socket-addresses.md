Decision: The family and components of a SocketAddress are read by the nonwaiting std::net function socket_address_ip, declaring only reads of the address it is given and returning the ordinary enum IpAddress, whose Ipv4 variant carries the four u8 octets and whose Ipv6 variant carries the eight u16 groups that socket_address_v4 and socket_address_v6 take, in written order, because an address is a value the program already holds with exactly one of two families and a fixed number of components in each, so one total pattern match yields its family and its components with no index or window length to prove and no handle factory or host state involved, and every address reads back as the constructor call that would build it, instead of a family enum with a byte-window copy whose required length depends on the family, a per-byte reader whose index needs a proof, a fixed 16-byte array whose last twelve bytes mean nothing for IPv4, or a function that formats address text, which is the program's own spelling choice.

Decision: The port of a SocketAddress is read by the nonwaiting std::net function socket_address_port, declaring only reads of the address it is given and returning the u16 port, because the port is one u16 in both families, so it needs no pattern match and no second reader per family.

Decision: An IPv6 address carries only its address and port, so a scope identifier or flow label the host reports for a peer is not kept, as a provisional choice, because the need that brought these readers, Firn's CLIENT LIST, prints only the address and the port as Redis does, and the runtime's address value already keeps nothing else, instead of adding both to the address value and to socket_address_v6 now; the uncertainty is whether any program needs to reach a link-local IPv6 peer or report its zone, and the choice is reopened when a program must reconnect to or print a link-local IPv6 peer.

Decision: The local address of a connection is the nonwaiting std::net function local_address on the connection's receiving half, declaring reads of that half and returning Result<SocketAddress, IoError> whose refusal carries the host's code and the new origin 10, because one query then serves an accepted connection and one tcp_connect opened alike, costs a host call only when a program asks, as Redis looks a client's local address up only when it first formats that client, changes no connection state that another operation's order must respect, and leaves the host's refusal of the query visible, while a closed half is consumed by its close and cannot reach the query at all, so that after close_receive, for example on the peer's end of stream, the sending half stays open but its connection's own address can no longer be queried and a program that needs it queries before closing the receiving half, instead of a local field of AcceptedConnection filled at every accept, a query on TcpConnection or a query on each half.

Rejected:
- A local field of AcceptedConnection filled at every accept: rejected because every accept would pay a host call for an address most programs never read, a connection that tcp_connect opened would still have no way to learn its own end, and every destructuring of AcceptedConnection would change for it.
- A query on TcpConnection: rejected because TcpConnection is an ordinary struct whose two halves may come from different connections, so it names no single connection.
- A query on each half: rejected because both halves of one connection report the same endpoint, so a second function would be a second spelling of one fact, and a query on the sending half would keep the connection's own address readable after close_receive, the one case the receiving-half query gives up, which is accepted because a program that needs the address reads it while it still holds the receiving half.
- An infallible local_address: rejected because the host may refuse the query, for example for lack of resources, and an invented address would hide that refusal.
- A family enum with a byte-window copy of the address: rejected because the copy's required length depends on the family, so a caller must handle a window-too-small outcome for a value whose size is fixed by a pattern match it already makes.
