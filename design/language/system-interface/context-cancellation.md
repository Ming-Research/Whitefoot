Decision: Every host wait that takes an optional deadline, and sleep_until, takes an explicit CancelWatch immediately after its deadline (shape S1), with cancel_never for a must-finish wait, because each wait then shows whether a stop can end it, instead of combining the watch with the deadline, setting it on the context or binding it to the resource (owner's board card firn-cancel-shape; [shapes and results](../../../research/investigations/context-cancellation/README.md#results)).

Decision: Cancellation sources and watches are droppable opaque structs whose private fields hold Shared<CancelState> and SharedRead<CancelState> respectively, with explicit close functions equivalent to dropping, because cancellation state is ordinary runtime memory and a source stored in Shared state must admit drop; the shared fields supply ordinary field-wise release without a host-specific release rule (owner's board card firn-wf-cancel-drop-card). Sources, watches and read-only shared views retain the same state independently, and waits borrow their watch until return, because ordinary ownership then keeps every pending wait's state live without reference-count traffic at park, instead of copy watches whose state can disappear while copies remain.

Decision: A firing finds waits on each driver's own intrusive watch list and ends them through the existing deadline cancellation route, because the prototype's eight firn throughput cells were within noise of polling and its observed process stops took about 50 ms instead of about one second, instead of registering each parked wait under a cancellation object's shared lock ([results and their limits](../../../research/investigations/context-cancellation/README.md#results)).

Decision: Cancellation is the payload-free IoError variant Cancelled, carried by ReadFailed for reads, and sleep_until changes its unit result to Result<unit, unit>, whose Ok retains the successful unit result and whose Err reports cancellation, because these outcomes distinguish a fired watch from a reached deadline without introducing a second failure type into time or changing read-stop nesting, instead of reporting a firing as DeadlinePassed as the performance prototype did.

Decision: cancel_state takes a CancelWatch and returns SharedRead<CancelState> over the same retained state, whose public fired Bool stays true after firing and stays false for cancel_never, because one cancellation must be observable by both host waits and atomic guards while closing handles changes neither observation, instead of a copied or program-maintained flag (owner's board card firn-cancel-guard-shape, option A; [study](../../../research/investigations/context-cancellation/guards.md#3-the-stacked-pr-needs-a-small-semantic-core-followed-by-explicit-compiler-and-runtime-support)).

Decision: cancel_fire declares waits and performs one held shared-state transition under ordinary atomic ordering and progress, waking guard watches on the state and the guards that read its flag false while retaining find-at-fire driver notification for host waits, because nonwaiting firing inside an atomic block would either reacquire its held state or change a state that the block must observe stably, instead of hidden nested acquisition; observing fired does not establish completion of host waits, joins or cleanup and introduces no independent ordering of unrelated host effects.

Decision: A watch's `fired` field reads its cancellation flag without holding the cancellation state, admitted only as a place atom of an atomic statement's guard or block, a borrow, a move or a read anywhere else being refused [PRE-2] and a write being a readonly error [TYPE-2], because a statement holds one object, so a guard that waits for work or for cancellation can no longer hold the cancellation state beside its object, while the flag only goes from false to true, so a read of true still orders the reader after the firing and every shared-state update completed before it ([cancellation flags](../../../research/investigations/shared-state/DESIGN.md#cancellation-flags)), instead of retiring the cancellation guards, holding the one-object statement until a guard may read atomic values, or a cancellation clause of the statement (the recommended option of the design card one-object-cancel-guard on the board item one-object-statement). It is a case of the owner-approved direction that a guard may read atomic values, and merges into it when that lands; it re-proposes the live read of the flag that the firing decision refused, because the read now holds nothing and names no fact, so no block relies on the flag staying as read.

Decision: Each flag read takes effect at its own point after its statement begins and before the statement's point, several reads in one statement following one another rather than taking effect at one instant [SHARE-3], names no fact [ENT-2] and takes away overlap permission [PAR-1, PAR-2], because two reads of one flag in one block may see it unfired and then fired, so a fact from one read need not hold at another, and overlapped statements could see the flag unfired after a statement before them in source order saw it fired, instead of a read at the statement's one point, which would need the cancellation state held.

Rejected:
- Nodrop sources and watches closed explicitly: rejected because proof's review of v0.111 found that this exposes only two forgotten-fire mistakes at compile time, while it blocks storing sources in droppable shared state; explicit consumption does not prove that a source was fired.
- Host-specific non-empty release for cancellation handles (option A): rejected because their state is ordinary shared runtime memory, whose retain can be released by a private shared field without a release rule selected by host origin.
- Making only sources droppable: rejected because a watch retains the same ordinary shared state and has no separate must-close resource obligation to justify nodrop.
- S2, one bound value replacing the deadline: rejected because a copy watch naming runtime state needs another lifetime rule when the state is released while copies remain, and it hides the explicit per-wait watch chosen by the owner.
- S3, a watch set on the context: rejected because ambient cancellation hides the capability from the wait's parameters, needs an escape for a must-finish wait and needs another inheritance rule for spawned contexts.
- S4, a watch bound into a resource handle: rejected because sleeps have no such handle and mixed cancellable and must-finish use of one resource needs two bindings.
- Register at park under the source's lock: rejected because each request would pay shared lock and list-update traffic for a firing that happens once at shutdown, whereas the measured find-at-fire path matched polling within noise.
- A bare cancel_fired query: rejected because a guard holds at most one call, whose arguments are atoms [GRAM-5], so a call returning the flag could not stand beside a held read in one guard, while a place atom reading the watch's field can, and lowering registers a waiting guard on the flags it reads.
- A program-owned shared stop flag beside cancellation: rejected because its update and cancel_fire would be two independently observable transitions.
- A cancellation-specific target (option B): rejected because a statement holds one object, so a cancellation state held beside it would bring back several objects per statement, while the flag read holds nothing.
- Cancellation interrupting a pending statement without its body (option C): rejected because it changes the selected guard-state meaning and requires a new outcome and outgoing-edge model.
- Retiring the cancellation guards until a guard may read atomic values: rejected because a program would lose, for an unknown time, a guard that waits for work or for cancellation.
- Holding the one-object statement until a guard may read atomic values: rejected because the work waiting on it would wait for a design not yet scheduled, while the flag read is a case of that design and merges into it.
- A cancellation clause of the statement, such as `until`: rejected because it serves a guard but not a block that reads the flag, and needs syntax of its own.
- A `fired` read without holding through the `SharedRead<CancelState>` view: rejected because it would be a rule keyed on a shared type's argument.
