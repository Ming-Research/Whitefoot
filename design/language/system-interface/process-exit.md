Decision: An invocation receives a `ProcessExit` capability as the `exit` field of `Inputs`, which `exit_share` duplicates for a spawned context, and the waiting `exit_now(exit, status)` ends the execution with that status at once, running no join, release or scope exit [WAIT-2], because a server in its orderly stop must be able to end at once while another context still waits, as Redis 7.2.16 ends with status 1 on a second interrupt, a capability the invocation hands over keeps that authority an ordinary parameter as the clocks and the memory meter are, and a waiting call is never overlapped with adjacent statements [PAR-1], so the exit takes effect in its context's order with no rule of its own (the owner's answer to the exit-form question, option 1), instead of a non-waiting exit or an exit taking `StopSignals`.

Rejected:
- A non-waiting `exit_now` that compute code could call: rejected because PAR-1 could overlap it with an adjacent statement, so the specification would either let an earlier statement stay undone when the program ends or give PAR-1 a case of its own for the exit.
- An exit taking `StopSignals`, with no new `Inputs` field: rejected because a function on a capability that observes something else is refused (language/system-interface/handle-factory), and every holder of the stop capability would then hold the authority to end the program.
