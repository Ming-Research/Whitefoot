Decision: A program opens files and directories by host path, absolute or relative to a directory it holds, only through a separate host-path authority, a fieldless value the host supplies as an optional input that no program can construct, and a function given only a directory half cannot open by host path, because Firn must open a configuration file named on its command line, an included file and an existing data directory whose paths are read from configuration bytes, while a function given only a directory half must gain no new authority to open by host path ([option A](../../../../research/investigations/host-paths/DESIGN.md#options)), instead of widening the relative path type or giving every directory a path open (both under Rejected).

Decision: the host-path authority offers six opens, a read file, a directory's read half and both halves of an existing directory, each from a host string or from a byte window of a buffer with a stated encoding, and never creates an entry, because an argument path arrives as a host string, a path read from configuration arrives as bytes, and a data directory that must already exist is refused when missing rather than created ([recommended interface](../../../../research/investigations/host-paths/DESIGN.md#recommended-ordinary-interface)), instead of the existing create-if-missing directory open, which hides a misconfigured path by creating an empty directory.

Decision: host-path lookup is the host's own lookup from the given directory, following every link and resolving parent components as the host does, after the links before them on a POSIX host and textually in the Win32 dialect on Windows, while the single-name opens used for traversal below a directory and the component-by-component lookup of `open_read` never follow a link, because a path a user names should mean what the host's own tools take it to mean, and a link reached by a lookup below a directory must not lead outside it ([parent components](../../../../research/investigations/host-paths/DESIGN.md#parent-components-lexical-or-filesystem-resolution)), instead of lexical normalization on POSIX, which opens a different file than the host when a component is a link.

Decision: POSIX and Windows hosts supply the authority, and a host without a host filesystem supplies none, so no program reaches a host-path open there, because a target without a host filesystem must still run programs that do not use one ([weak targets](../../../../research/investigations/host-paths/DESIGN.md#weak-and-embedded-targets)), instead of rejecting such targets.

Decision: a Windows host path is UTF-16 code units, native bytes being each unit low byte first with unpaired surrogates kept and UTF-8 converted explicitly, and is looked up in the Win32 dialect: an extended `\\?\` path as written, a device path refused as an invalid path, and every other form normalized by the host's own GetFullPathNameW after its starting point, a relative or root-relative path after the spelling the host reports for base's handle at the open, a drive-relative path on another drive after the host's current directory for that drive, which no program can change; a relative path whose normalized form begins with the spelling the host reports for base, code unit for code unit, and then ends or continues after a separator opens from base's handle by its remainder, every other path from the root namespace, and the lookup follows every symbolic link and junction while single-name opens keep refusing every reparse point, because UTF-16 code units are what the Windows host itself takes, the Win32 dialect is what the host's own tools mean by a path and by `..`, no program can change the host's per-drive current directories after the invocation starts, the refusal of every reparse point at a single name is the existing conservative behavior, and the existing handle representation can resolve a remainder below a directory handle but not a parent above it ([Windows as built](../../../../research/investigations/host-paths/DESIGN.md#windows-as-built)), instead of resolving every relative path from base's reported spelling, which a concurrent rename of base could redirect, or resolving parents physically, which the Win32 dialect does not do.

Decision: the two halves of an existing directory come from one host lookup, the second half duplicating the first's descriptor, take two credits and return both when the open fails, and a byte-window path is copied into a bounded runtime block of at most the host's path limit, because two lookups could select two different directories if an entry is replaced between them, and the copy must outlive the caller's buffer while the open waits ([completion transport](../../../../research/investigations/host-paths/DESIGN.md#completion-transport-lifetime-and-acquisition)), instead of two lookups or borrowing the caller's buffer across the wait.

Rejected:
- Widening the relative path type to accept absolute paths and parents (option B): rejected because the same directory parameter would then authorize more paths that ignore it, so an existing write half could reach its parents, and it still cannot express paths read from file bytes or an existing-only directory open.
- A byte-constructed path value with path opens on any directory (option C): rejected because a path is data, not permission, so either every directory half gains authority over absolute and escaping paths, or escaping paths are refused and the broad host-path need is not met.
