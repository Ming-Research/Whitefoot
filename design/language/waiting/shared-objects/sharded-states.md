Decision: State that many contexts update and a reader combines or replaces, such as a server's per-command statistics or a per-driver pending write buffer, is a shards state `Shards<T>`: `len` shards, each a place of type T, held only as the state of a shared object. A shard target `s = &h[mine]`, whose index atom is a place holding the shard selector, names one shard, and a whole target `all = &h` names every shard; both are ordinary atomic statements with one point in the one order [SHARE-3]. This is because the count witness needs an update path that writes no cache line another driver writes, which one shared object cannot give and an object per context can ([results](../../../../research/investigations/shared-counters/DESIGN.md#9-results-the-arms-that-need-no-language-change)), and because a whole statement then has every shard at one point, so its total is the value one shared integer would hold there, with no new memory model, no target capability and no change on a single-driver target, where a shards state has one shard. The runtime itself keeps its heap total in counters local to each driver and compute worker for the same reason (language/system-interface/memory-statistics). This is instead of single-step integer cells, the hand-built array of shared objects, a hidden-combine counter type, a peak kept by the runtime in the memory meter, the compiler sharding objects that are only added to, or per-context counts flushed now and then (below).

Decision: Which shard a shard target names, and how many shards a state has, are inputs of the execution [WAIT-2]; the program never supplies a shard's index, the number is at least one and fixed for the object's life, and an implementation may choose it by the driver count. This is because where a context executes is not observable [WAIT-2], so only the implementation can give a statement the shard of the thread running it, while an index the program computed would carry a bounds obligation and would let contexts on two drivers pick one shard, which is what holds the hand-built array to 0.31 to 0.66 of the private rate ([results](../../../../research/investigations/shared-counters/DESIGN.md#92-the-hand-built-array)). A program knows only the standing fact `len >= 1` and loops over `len`. This is instead of a writer-chosen index, or a driver number made observable to programs.

Decision: A guard reads no path into a shards state, because a guard on one shard whose identity is an input of the execution states no condition a writer can rely on, and a guard on the whole run would make every shard write look for watches on the object, a step on the update path this state exists to keep free; admitting a whole-run guard later, when a program needs to wait for a total, changes no accepted program, while withdrawing one would. This is instead of a whole-run guard woken by every shard write, as a write to a map entry wakes the watches of its whole map (compiler/waiting-contexts/state-locks). This is provisional; reopen when a program must wait for a total or a threshold of one.

Decision: A shard's type T is any type with drop, and `shared_shards_new::<T, fn make>()` calls its maker `make`, a function-kind argument [FN-3] that is pure and does not wait, once for each shard and stores what each call returns in that shard. This is because a shard is then a place like a map's entry, able to own a buffer, a queue or a handle that a whole statement exchanges with `swap` for a fresh one, as Firn's per-driver pending write buffers need, while each shard keeps T's fixed inline size and releasing the state releases every shard's value, as releasing a map releases its entries; a function-kind argument is the language's form for a value made once per place without closures, and a pure maker that does not wait keeps the constructor pure and makes its number of calls, an input of the execution, visible only in heap readings. This is instead of a copy type T with every shard a copy of one argument, which keeps buffers and queues out of shards, or two constructors, one copying a value and one calling a maker, which state one meaning twice.

Decision: A shards state's one home is a shared object's state, never a `swap`'s exchange, because each object's number of shards is its own input of the execution, so exchanging the shard runs of two objects could change a number the state keeps for its life, instead of a map's homes, which include the exchange.

Decision: The shard selector is the one value of the fieldless prelude struct `AnyShard`, which `any_shard()` returns and which a shard target takes as its index atom in the existing target grammar, because a target's form is then chosen by its index atom's type, as a map's entry and key-set targets are, with no grammar change. `AnyShard` is copy and, as every fieldless struct, an equality type [OP-16], so `any_shard() == any_shard()` is admitted and always true, which tells a program nothing and selects no shard. This is instead of a dedicated target syntax (below).

Decision: A shard is no site of a type invariant [TYPE-11]: a shard target's block neither assumes nor owes the invariant of its shard's struct, as no site covers an element of a storage shape or a map's entry. This is because a whole target and a callee receiving `&Shards<T>` write shards through element positions, which owe no invariant, so a shard target that assumed one would rest on writes nothing checked. This is instead of a shard target that assumes and owes the invariant, which would need every write through a whole target to owe it for each shard, a quantified obligation the proof language does not state, or refusing a shard type that declares an invariant, which would forbid it even where the program proves the invariant before each call that needs it. This is provisional; reopen together with type invariants over the elements of storage shapes and the entries of maps.

Rejected:
- Single-step integer cells for counts, a `SharedCell<T: Int>` type that no statement targets, with load, store, add, raise and compare-and-exchange operations each one point in the order: rejected because a contended hardware add on one line reached 0.059 of the rate of each thread on its own line at 8 P-cores, where the registered condition for preferring the cells was 0.5, and 118 million a second, below the hand-built array's 175 million ([results](../../../../research/investigations/shared-counters/DESIGN.md#93-the-hardware-atomic-add)); a provisional ground, since the registered noise rule marks that run inconclusive, twin noise 9% against its 3% limit, and the ruling rests on the ratio lying 9.7 times that noise below its threshold ([what the results decide](../../../../research/investigations/shared-counters/DESIGN.md#96-what-the-results-decide)), and a run under a noise rule that decides contended arms with the ratio within its noise of 0.5 reopens this. It covers counts only: a sequence whose every take must return a value ordered by the statements' one order, such as a log's global sequence or the next identifier, cannot be split into shards and is a separate question.
- A writer-built array of shared objects, each context updating element `index mod 16`, written as a pattern instead of a language change: rejected because it reached 0.31 to 0.66 of the private-object rate and fell from 175 to 135 million a second between 8 P-cores and 16 hyperthreads, since contexts, not drivers, choose its elements and every statement still counts its element's handle ([results](../../../../research/investigations/shared-counters/DESIGN.md#92-the-hand-built-array)); a provisional ground, since the registered comparison against the shards state itself waits for its implementation, and an implemented state at most 1.25 times the array's rate at every CPU count reopens this.
- A hidden-combine counter type, `Tally<T>` with add, raise and read: rejected because each counter costs its own run of cache lines, about 1.9 MiB for Redis's per-command table at 32 shards, against one state holding every statistic, and several statistics then cannot change in one step.
- A peak maintained by the runtime in `MemoryMeter`: rejected because an exact peak of a sum of counters local to each driver and compute worker needs a global write at every allocation, the cost the heap accounting refused, and Redis records the maximum of readings taken after commands.
- The compiler sharding a `Shared<u64>` whose every statement in the program only adds or reads: rejected because it needs every function body, and a change elsewhere would silently change an object's representation and cost.
- Each context counting in its own state and adding to one shared object every k commands: rejected because a reader then sees a total no counter held at one point, missing up to k - 1 updates per context, a policy a program may state for itself but not the language's general meaning of a count.
- A maker that receives a seed by reference, `fn make(seed: &S) -> made: T`: rejected because a whole statement right after creation already gives each shard a value computed from run-time data, before any other context holds a handle, so a seed would add a type parameter and an argument to every creation for a case the whole target covers.
- Shards of `Option<T>` that start as `None`, as a map's entries do, with no maker: rejected because every shard statement would then match on a value present after its first update, a branch on the path this state exists to keep short, and a whole reader would handle shards never made.
- A dedicated target syntax for the shard target, such as a keyword in the index position: rejected because it adds a grammar form for what an index atom's type already selects in the existing target grammar, as it does for a map's entry and key-set targets.
