Decision: State that many contexts update and a reader combines, such as a server's per-command statistics, is a shards state `Shards<T>`: `len` shards of a copy type T, each a copy of the value `shared_shards_new::<T>(value: v)` takes, held only as the state of a shared object. A shard target `s = &h[mine]`, whose index atom is a place holding the shard selector `any_shard()` returns, names one shard, and a whole target `all = &h` names every shard; both are ordinary atomic statements with one point in the one order [SHARE-3]. This is because the count witness needs an update path that writes no cache line another driver writes, where 64 contexts on one shared object fell to 2.81 million updates a second at 8 P-cores while each on its own object reached 346 million ([results](../../../../research/investigations/shared-counters/DESIGN.md#92-the-hand-built-array)), and because a whole statement then reads every shard at one point, so its total is the value one shared integer would hold there, with no new memory model, no target capability and no change on a single-driver target, where a shards state has one shard. The runtime itself keeps its heap total in per-thread counters for the same reason (language/system-interface/memory-statistics). This is instead of single-step integer cells, the hand-built array of shared objects, a hidden-combine counter type or per-context counts flushed now and then (below). This is proposed.

Decision: Which shard a shard target names, and how many shards a state has, are inputs of the execution [WAIT-2]; the program never supplies a shard's index, the number is at least one and fixed for the object's life, and an implementation may choose it by the driver count. This is because where a context executes is not observable [WAIT-2], so only the implementation can give a statement the shard of the thread running it, while an index the program computed would carry a bounds obligation and would let contexts on two drivers pick one shard, which is what holds the hand-built array to 0.31 to 0.66 of the private rate ([results](../../../../research/investigations/shared-counters/DESIGN.md#92-the-hand-built-array)). A whole statement learns only `len >= 1` and loops over `len`. This is instead of a writer-chosen index, or a driver number made observable to programs. This is proposed.

Decision: A guard reads no path into a shards state, because a guard on one shard whose identity is an input of the execution states no condition a writer can rely on, and a guard on the whole run would make every shard write look for watches on the object, a step on the update path this state exists to keep free; admitting a whole-run guard later, when a program needs to wait for a total, changes no accepted program, while withdrawing one would. This is instead of a whole-run guard woken by every shard write, as a write to a map entry wakes the watches of its whole map (compiler/waiting-contexts/state-locks). This is provisional; reopen when a program must wait for a total or a threshold of one. This is proposed.

Decision: A shard's type T is copy, and a shards state's one home is a shared object's state, never a `swap`'s exchange, because a copy type holds no handle, `Box` or runtime-capacity storage, so each shard is inline storage of fixed size and a copy of the initial value is well defined, and because each object's number of shards is its own input of the execution, so exchanging the shard runs of two objects could change a number the state keeps for its life. This is instead of any droppable T, which would put handles and heap storage into shards and need a function to make each shard's first value, or a map's homes, which include the exchange. This is proposed.

Rejected:
- Single-step integer cells, a `SharedCell<T: Int>` type that no statement targets, with load, store, add, raise and compare-and-exchange operations each one point in the order: rejected for counts because a contended hardware add on one line reached 0.059 of the rate of each thread on its own line at 8 P-cores, where the registered condition for preferring the cells was 0.5, and 118 million a second, below the hand-built array's 175 million ([results](../../../../research/investigations/shared-counters/DESIGN.md#93-the-hardware-atomic-add)); it stays a candidate for identifier allocation, which needs the global value back at once.
- A writer-built array of shared objects, each context updating element `index mod 16`, written as a pattern instead of a language change: rejected because it reached 0.31 to 0.66 of the private-object rate and fell from 175 to 135 million a second between 8 P-cores and 16 hyperthreads, since contexts, not drivers, choose its elements and every statement still counts its element's handle ([results](../../../../research/investigations/shared-counters/DESIGN.md#92-the-hand-built-array)); a provisional ground, since the registered comparison against the shards state itself waits for its implementation, and an implemented state at most 1.25 times the array's rate at every CPU count reopens this.
- A hidden-combine counter type, `Tally<T>` with add, raise and read: rejected because each counter costs its own run of cache lines, about 1.9 MiB for Redis's per-command table at 32 shards, against one state holding every statistic, and several statistics then cannot change in one step.
- A peak maintained by the runtime in `MemoryMeter`: rejected because an exact peak of a sum of per-thread counters needs a global write at every allocation, the cost the heap accounting refused, and Redis records the maximum of readings taken after commands.
- The compiler sharding a `Shared<u64>` whose every statement in the program only adds or reads: rejected because it needs every function body, and a change elsewhere would silently change an object's representation and cost.
- Each context counting in its own state and adding to one shared object every k commands: rejected as the general answer because a reader then sees a total no counter held at one point, missing up to k − 1 updates per context, a policy a program may state for itself but not the language's meaning of a count.
