Decision: State that many contexts reach by key is a keyed table, a field of type `KeyedTable<V>` in a shared state or the state itself, holding an `Option<V>` entry for every byte string, because one sharing primitive then covers objects and keyspaces and one statement holds a table's entries together with its state's other fields, the log beside a key's entry, with no second handle and no nested statement ([parts](../../../../research/investigations/shared-state/DESIGN.md#parts)), instead of a second handle type whose blocks reached objects through nested statements.

Decision: A key is a `&[u8]` the runtime hashes and compares, because the runtime would otherwise call the writer's hash and equality under a cell's lock in the middle of a probe, and the index's correctness would then rest on a protocol no admission checks, while byte strings are what a server's keys are and a key is named as a range of its input without building one, instead of a key of any type with a `HashMapKey` binding or integer keys only.

Decision: A statement's header grants what its guard and block may reach of the state: the fields that are no table through the binding `s`, and each table through one table binding, `e = &s^.t[k]` or `es = &s^.t[ks]` for its entries or `t = &s^.t` for the table whole, with each table granted whole once or by entries alone, no path to a table except through its binding, and a callee's row that reaches a table through `s` requiring the table's whole binding, because a statement's parts are then read from its header as a function's accesses are read from its row, so the hold that excludes every statement on a table's keys is written where the parts are named instead of implied by a path in the block or by a generic callee's `writes(env)`, while entries are still locked together in one order from keys known before the block ([entries in the header](../../../../research/investigations/shared-state/DESIGN.md#entries-are-named-in-the-header)), instead of the implicit whole hold, under which the header's silence about a table meant the whole table when the block reached it and nothing otherwise, and a header with entry bindings beside a whole path had no stated meaning.

Decision: A whole binding's table is indexable in the guard and block, `t^[k]` the entry under a key and `&t^[ks]` the entries under a set, with no obligation since a table holds an entry under every key, and so is any `&KeyedTable<V>` a callee receives, because a key a block computes, a script's, needs the table held whole, which costs nothing more for being written, and the two forms are the header's two forms moved inside, so executors written against `&Option<V>` and `&KeyedEntries<V>` serve both, instead of a subscript on any table place, which held the table whole unwritten, or a lookup row returning an index, since a table has no index a program could hold.

Decision: A key set, `KeySet`, holds distinct keys in the order each was first inserted, `key_set_insert` answers a key's index, that of its first insertion, and an entry binding over the set reaches the entry of the set's key at each index, because the order a program needs is its request's, so a command naming several keys replies and records in the order of its arguments, which the index each argument's insertion returned maps to the set's entries without a second search, while the order the entries are locked in is the runtime's protocol against deadlock, which the program cannot observe, since the statement's guard and block take effect at one point [SHARE-3] and lowering takes every entry of a set before the guard (compiler/waiting-contexts/state-locks); a program keeps a key's last value or its count in its own data at that index, so the language fixes no merge policy ([MSET after the redesign](../../../../research/investigations/shared-state/DESIGN.md#mset-after-the-redesign)), instead of keys in increasing order of their bytes, each with a payload a later put replaced or an add summed, which made every insertion search and move the set's items, about 30 to 50 ns more per ten-key `MSET` than one sort at the hold, made firn rank `MGET`'s and `MSETNX`'s arguments again and write its append-only records in byte order, and fixed two merge policies in the prelude.

Decision: A statement whose guard and block write nothing through an entry binding holds that entry beside the other such statements on its key, and nothing in the source marks it, because those statements' reads take effect at one point each in one order whichever of them runs first [SHARE-3], so sharing changes no outcome, while every client of the benchmark's four `LRANGE` tests reads one list, which firn answered at 0.44 to 0.61 of Garnet on 4 to 16 server CPUs with exclusive holds and at 1.14 to 1.22 of it with shared ones ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores), [shared reads](../../../../research/investigations/concurrent-map/DESIGN.md#shared-reads-of-one-key)), instead of a read form the writer marks, which asks the writer to choose for a difference no program observes, or reads that check a version afterwards, which a block that runs once cannot redo after a torn read.

Decision: A table has one representation wherever it is, the runtime's concurrent index, built empty with a capacity by `keyed_table_new`, and its entries are reached by a subscript of a reference to it, which for a table in a shared state only an atomic statement's table binding forms, because an unshared table is then the same index used by its sole holder, so a callee indexes a `&KeyedTable<V>` without knowing whether the table is shared and the language needs no rule about where a table may appear, instead of confining a table to the argument of `shared_new` and forbidding it to be moved whole, which guards against a second representation that no operation can reach.

Decision: The table is `KeyedTable<V>`, the set `KeySet` and the entries an entry binding names over a set `KeyedEntries<V>`, because a prelude name always displaces a source declaration of the same spelling [PRE-1] and `Table` already names a struct in conformance cases, instead of `Table`, `Keys` and `Entries`.

Rejected:
- The implicit whole hold, a statement holding a table whole when its block forms any path to it other than an entry binding: rejected because the header then said less than the block held, the slowest hold a statement can take was the one it did not show, a callee's row could imply it where no reader of the statement saw it, and the mixed header was accepted with a meaning no rule stated; it was the first design's convenience for `keyed_table_count`.
- A hold per field that is no table, `m = &s^.meta`: rejected because the lock layout has one unit for those fields, so the binding `s` grants that unit and a per-field binding would state a part the layout does not have, while a callee taking the state would need every field listed.
- Admitting a path to a whole-bound table through `s` beside its binding: rejected because a binding then had two spellings and the "use every binding" check could not tell a forgotten binding from one reached the other way.
- Replaced decision beginning "State that many contexts reach by key is a shared map held through `SharedMap<V>` handles": rejected because a second handle type made a table's entries and its state's other fields two statements, nested by kind.
- Replaced decision beginning "A whole-map statement `atomic s = &m { ... }` holds every entry": rejected because a statement names the entries it reaches in its header and counting is an operation on the table.
- Replaced decision beginning "For a whole-map statement, which holds every entry, an implementation holds only the entries its block reaches": rejected because the header then said the whole map while only the reached entries were locked, and finding those keys meant running part of the block before the hold.
- Replaced decision beginning "The block of a keyed or whole-map statement contains no call to a waiting function": rejected because no statement contains another.
- Replaced decision beginning "A keyed statement whose guard and block write nothing through its binding, and whose block runs at most one object statement": rejected because no block contains an object statement now, so the condition on object statements is gone.
- Replaced decision beginning "The handle is `SharedMap<V>` and its state `SharedMapState<V>`": rejected because the table is a field type and the handle is the state's.
- A compiler that runs the part of a block computing its keys before taking any lock: rejected because the generated code then differs from the written code, the key computations run twice and must answer the same both times, conditions must guard the early run, and a key it could not compute fell back silently to the whole table ([refused along the way](../../../../research/investigations/shared-state/DESIGN.md#refused-along-the-way)).
- Implicitly locking the whole table when a block's keys are known too late: rejected because it lets slow code through unseen.
- Taking each entry at its first use in code order: rejected because two statements meeting two keys in opposite orders wait for each other.
- A single-threaded hash map as a field of a state: rejected because entries under different keys are inserted, removed and moved to a larger table by different contexts at once, so such a map could be locked only whole.
- Every keyed statement holding its entry exclusively whether its block reads or writes: rejected because readers of one list then take turns, firn's `LRANGE_100` staying at 1.24 to 1.55 million a second on 2 to 16 server CPUs while Garnet grew to 2.83 million ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores)).
- A read form the writer marks: rejected because the outcome is the same either way [SHARE-3] and the checker already knows which paths the block writes.
- Keys in increasing order of their bytes, each with a payload a later put replaced or an add summed (the replaced decision beginning "A key set, `KeySet`, holds distinct keys in increasing lexicographic order"): rejected because the order a reader saw was the runtime's lock order, which a command's replies and records do not follow, keeping that order at every insertion cost a search and a move per key, and the payload fixed two merge policies a program keeps itself.
- An opaque key set whose length and order exist only inside the statement: rejected because the block would still visit the keys in the lock order, so replies and records in argument order would still need a second ranking, and a command tells a repeated key from a new one by what insertion answers before the statement.
- A key of any type with a `HashMapKey` binding: rejected because the runtime would call writer code under a cell's lock in the middle of a probe.
- A map sharded into `Shared` objects, each a lock and a table: rejected because the index the runtime keeps reads without locking and locks one entry per write, which led or tied every measured cell against the fastest comparators ([measured](../../../../research/investigations/concurrent-map/DESIGN.md#measured)), while shards serialize unrelated keys that share a shard.
