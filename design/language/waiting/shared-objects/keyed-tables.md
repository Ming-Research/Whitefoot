Decision: State that many contexts reach by key is a concurrent hash map, `ConcurrentHashMap<V>`, holding an `Option<V>` entry for every byte string, and a map is an ordinary affine value that `map_new` makes empty, that takes every place a value can take [TYPE-9] and moves and is released as other values are, and that becomes part of a shared state when moved into `shared_new`'s value, reached there only inside atomic statements as every part of a state is [SHARE-1]. This is because the ground for a map that is only a state, that a target reached it while the state changing beside its entries lived in other objects the same statement named, went with several targets per statement, a map that is only a state cannot be built into a state beside other fields and leaves the entries a flush removes no place outside a statement, and a map keeps one meaning in every position through one subscript rule with no rule of its own ([a map as a value](../../../../research/investigations/shared-state/DESIGN.md#a-map-as-a-value)), instead of a map that exists only as a shared object's state, made with its object by `shared_map_new` (the recommended option of the design card one-object-map-values on the board item one-object-statement). This re-proposes the field and local tables the tree had refused, whose access rules differed by position, whose pending hold was settled at publication and which a header reached by a provenance: access is now one rule in every position, an ordinary path and OP-4, no header names a map, and the hold is the lowering's, which the program cannot observe and which only `shared_new` and the map's release settle (compiler/waiting-contexts/state-locks).

Decision: A key is a `&[u8]` the runtime hashes and compares, because the runtime would otherwise call the writer's hash and equality under a cell's lock in the middle of a probe, and the index's correctness would then rest on a protocol no admission checks, while byte strings are what a server's keys are and a key is named as a range of its input without building one, instead of a key of any type with a `HashMapKey` binding or integer keys only.

Decision: A map's entries are the places its subscripts select on any map place, `m[k]` the entry under a key and `&m[ks]` the entries under a key set, with no obligation since a map holds an entry under every key, one rule wherever the map is, `t^[k]` through a `&ConcurrentHashMap<V>` a callee receives and `s^.dbs[i][k]` inside a state included [OP-4, SHARE-1], because a statement reaches its object's maps by ordinary paths, so its header names no entry and which part of the state it locks is the lowering's under the equivalence [SHARE-3] (compiler/waiting-contexts/state-locks), and executors written against `&Option<V>` and `&Entries<V>` serve every placement, instead of entry and key-set targets in the header, which took a map's entries from keys known when the statement began, or a lookup row returning an index, since a map has no index a program could hold.

Decision: A key set, `KeySet`, holds distinct keys in the order each was first inserted, `key_set_insert` answers a key's index, that of its first insertion, and a key-set subscript `&m[ks]` reaches the entry of the set's key at each index, because the order a program needs is its request's, so a command naming several keys replies and records in the order of its arguments, which the index each argument's insertion returned maps to the set's entries without a second search, while the order in which an implementation locks the entries is not observable, since the statement's guard and block take effect at one point [SHARE-3]; a program keeps a key's last value or its count in its own data at that index, so the language fixes no merge policy ([MSET after the redesign](../../../../research/investigations/shared-state/DESIGN.md#mset-after-the-redesign)), instead of keys in increasing order of their bytes, each with a payload a later put replaced or an add summed, which made every insertion search and move the set's items, about 30 to 50 ns more per ten-key `MSET` than one sort at the hold, made firn rank `MGET`'s and `MSETNX`'s arguments again and write its append-only records in byte order, and fixed two merge policies in the prelude.

Decision: A statement whose guard and block write nothing in a map they reach by one key reads that entry beside the other such statements on its key, and nothing in the source marks it, because those statements' reads take effect at one point each in one order whichever of them runs first [SHARE-3], so sharing changes no outcome, while every client of the benchmark's four `LRANGE` tests reads one list, which firn answered at 0.44 to 0.61 of Garnet on 4 to 16 server CPUs with exclusive holds and at 1.14 to 1.22 of it with shared ones ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores), [shared reads](../../../../research/investigations/concurrent-map/DESIGN.md#shared-reads-of-one-key)), instead of a read form the writer marks, which asks the writer to choose for a difference no program observes, or reads that check a version afterwards, which a block that runs once cannot redo after a torn read.

Decision: The map is `ConcurrentHashMap<V>`, the set `KeySet` and the entries a key-set subscript selects `Entries<V>`, because every map, wherever it is placed, is the one concurrent hash map that contexts reach once it is part of a shared state, so the name says what the type is, while the entries are only ever a reference's referent, so a short name serves, and a prelude name displaces a source declaration of the same spelling [PRE-1], instead of `KeyedTable` and `KeyedEntries`, named when a table could also be a local value with another meaning. The name is provisional, since its earlier ground, that a map is never unshared, no longer holds now that a map may stay a local value one context reaches; reopen it if an unshared map type is proposed.

Decision: A program enumerates a map by `map_scan`, a step from a `u64` cursor that inserts into a key set, in increasing order of position and then of bytes, every key whose entry is `Some` and whose position lies from the cursor up to the step's extent, and returns the extent, `0` at the end, where each byte sequence's position is the same in every map and, like each step's extent, is an input of the execution. This is because every `u64` is then a cursor with a meaning, so a stale or forged cursor is safe and any context may continue a scan, a key `Some` for the whole scan is inserted exactly once however the map grows, shrinks or is written between steps, which is stronger than the at-least-once a Redis `SCAN` needs, the key set gives the entries through `&m[ks]` in the same statement, and the runtime homes a key by the top bits of its position in every table size, so a step reads only its homes' runs of cells ([the cursor](../../../../research/investigations/map-enumeration/DESIGN.md#the-cursor)), instead of an opaque cursor whose promise holds only over a chain of calls, or a specified hash.

Decision: `map_clear` makes every entry of a map `None` through any `&ConcurrentHashMap<V>`, replacing its earlier rejection, which held that a swap with a fresh map releases the old entries outside every lock, because a nonwaiting callee holding the map through a reference, such as a script's command executor, could swap in only a map it makes and releases inside the statement, which releases the old entries under the hold, while releasing values is not observable, so the entries leave the map under the hold and are released after it ([clearing](../../../../research/investigations/map-enumeration/DESIGN.md#clearing)), instead of clearing by a scan that writes `None` under every key, which copies every key and releases every value under the hold.

Decision: `key_set_read_key` copies as many first bytes of a set's key at an index as a range holds and returns the key's length, because a function cannot return a reference [REF-3] and a server copies a key into its reply anyway ([reading a key](../../../../research/investigations/map-enumeration/DESIGN.md#reading-a-key-sets-key)), instead of appending to a `Box<Slots<u8>>`, which would fix a growth policy in the prelude.

Decision: A KeySet returns its runtime-held storage on release, and a ConcurrentHashMap releases its held values and then returns its runtime-held storage; both have nonempty release independently of their declared fields, because those opaque declarations expose no ownership of the runtime allocations and field-only release would contradict the key set's retained-byte measure and leave the map's storage unreclaimed, instead of treating their scalar or absent fields as their complete release behavior.

Rejected:
- A hold per field that is no map, `m = &s^.meta`: rejected because the fields that are no map share the object's own lock, while state that changes apart can live in an object of its own, which a statement of its own holds.
- Admitting a path to a whole-bound table through `s` beside its binding: rejected because a binding then had two spellings and the "use every binding" check could not tell a forgotten binding from one reached the other way.
- Replaced decision beginning "State that many contexts reach by key is a shared map held through `SharedMap<V>` handles": rejected because a second handle type made a table's entries and its state's other fields two statements, nested by kind.
- Replaced decision beginning "A whole-map statement `atomic s = &m { ... }` holds every entry": rejected because it made a map's statement a form of its own, while a statement on any object now holds its whole state, a map's entries among its parts, and counting is an operation on the map.
- Replaced decision beginning "For a whole-map statement, which holds every entry, an implementation holds only the entries its block reaches": rejected because finding the keys a block reaches meant running part of the block before the hold, while a map is now locked by one entry only where its key is a binding fixed before the statement.
- Replaced decision beginning "The block of a keyed or whole-map statement contains no call to a waiting function": rejected because no statement contains another.
- Replaced decision beginning "A keyed statement whose guard and block write nothing through its binding, and whose block runs at most one object statement": rejected because no block contains an object statement now, so the condition on object statements is gone.
- Replaced decision beginning "The handle is `SharedMap<V>` and its state `SharedMapState<V>`": rejected because the table is a field type and the handle is the state's.
- A compiler that runs the part of a block computing its keys before taking any lock: rejected because the generated code then differs from the written code, the key computations run twice and must answer the same both times, conditions must guard the early run, and a key it could not compute fell back silently to the whole table ([refused along the way](../../../../research/investigations/shared-state/DESIGN.md#refused-along-the-way)).
- Taking each entry at its first use in code order: rejected because two statements meeting two keys in opposite orders wait for each other.
- A single-threaded hash map as a field of a state: rejected because entries under different keys are inserted, removed and moved to a larger table by different contexts at once, so such a map could be locked only whole.
- Every keyed statement holding its entry exclusively whether its block reads or writes: rejected because readers of one list then take turns, firn's `LRANGE_100` staying at 1.24 to 1.55 million a second on 2 to 16 server CPUs while Garnet grew to 2.83 million ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores)).
- A read form the writer marks: rejected because the outcome is the same either way [SHARE-3] and the checker already knows which paths the block writes.
- Keys in increasing order of their bytes, each with a payload a later put replaced or an add summed (the replaced decision beginning "A key set, `KeySet`, holds distinct keys in increasing lexicographic order"): rejected because the order a reader saw was the runtime's lock order, which a command's replies and records do not follow, keeping that order at every insertion cost a search and a move per key, and the payload fixed two merge policies a program keeps itself.
- An opaque key set whose length and order exist only inside the statement: rejected because the block would still visit the keys in the lock order, so replies and records in argument order would still need a second ranking, and a command tells a repeated key from a new one by what insertion answers before the statement.
- A key of any type with a `HashMapKey` binding: rejected because the runtime would call writer code under a cell's lock in the middle of a probe.
- A map sharded into `Shared` objects, each a lock and a table: rejected because the index the runtime keeps reads without locking and locks one entry per write, which led or tied every measured cell against the fastest comparators ([measured](../../../../research/investigations/concurrent-map/DESIGN.md#measured)), while shards serialize unrelated keys that share a shard.
- Replaced header grants and their provenance: rejected because a statement's one binding names the whole state and every map in it is reached by an ordinary path, so no grant or provenance follows aliases.
- `KeyedTable` and `KeyedEntries`: rejected because every map is the one concurrent implementation that a shared state's contexts reach, and entries exist only as reference referents.
- An opaque scan cursor with Redis's at-least-once promise: rejected because the promise is a property of a chain of calls rather than of one call, which makes the rule longer and weaker, and the cursor would encode the table's index structure.
- A specified hash of a key's bytes as its position: rejected because it fixes the runtime's hash in the specification and lets an input choose colliding keys.
- Each scan step's keys in an order that is an input of the execution: rejected because sorting gives a complete scan of the same keys one sequence in every map, a provisional ground, since the sort's cost beside reading the step's cells is assumed small and unmeasured; reopen if a measured scan step spends most of its time sorting.
- `map_reserve`: rejected because construction fixes initial capacity and cooperative index moves grow the map.
- A `shared struct` declaration: rejected because a map is an ordinary value that a state's struct holds as a field, so `shared_new` of an ordinary struct value builds such a state, and a second declaration form, whose constructor's type would differ from its name, adds nothing.
- Replaced decision beginning "State that many contexts reach by key is a concurrent hash map, `ConcurrentHashMap<V>`, holding an `Option<V>` entry for every byte string. It exists only as the state of a shared object": rejected because its ground, that a target reached a map while the state changing beside its entries lived in other objects the same statement named, went with several targets per statement, and a map that is only a state cannot be built into a state beside other fields.
- Entry and key-set targets, `e = &h[k]` and `es = &h[ks]`, beside a whole target `t = &h` alone on its handle place (the replaced decisions beginning "A statement names a map's parts by its targets" and "A whole target's map is indexable in the guard and block"): rejected because a statement reaches its object's maps by ordinary paths, so a header form for entries would be a second way to reach them, while the lowering locks one entry where every reach of a map is one key the statement does not write.
- Maps outside a shared state that nothing may subscript, pass to a call or borrow, with `map_detach` for a flush: rejected because the type then has rules of its own outside a state, and an array of maps could not be built, since filling `Slots` needs a reference.
- Maps that never leave a shared state, made empty by a construction form of their own: rejected because it needs exception rules for the types that hold maps and placement limits carried down containment, and leaves no place to write a map's initial capacity.

Decision: A byte-bounded scan is a separate `map_scan_within` returning a `ScanStep` with variant `Next` or `Needs`, retaining `map_scan` unchanged, because a caller budgeting heap needs whole-position progress and the exact budget required for an indivisible first position, instead of changing the existing count hint into a bound or silently returning an unchanged cursor, and because a caller that reserves memory before it scans must learn the size it needs before anything is copied.

Decision: A read-only `key_set_bytes` operation reports the heap holding of a key set's storage, including unused capacity and exactly what releasing the set returns, as an execution input, with an equality to the readonly `bytes` measure, and `map_scan_within` declares unconditional monotonicity and entry-plus-limit bounds over that measure, because firn must prove its reservation accounting after temporary allocations end and `Needs` leaves the set unchanged, instead of estimating storage from key lengths or changing `ScanStep` to carry another result ([retained-byte ruling](../../../../research/investigations/map-enumeration/DESIGN.md#retained-bytes-and-the-contract-language-gap)).
