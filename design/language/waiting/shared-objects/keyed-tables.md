Decision: State that many contexts reach by key is a keyed table, a field of type `KeyedTable<V>` in a shared state or the state itself, holding an `Option<V>` entry for every byte string, because one sharing primitive then covers objects and keyspaces and one statement holds a table's entries together with its state's other fields, the log beside a key's entry, with no second handle and no nested statement ([parts](../../../../research/investigations/shared-state/DESIGN.md#parts)), instead of a second handle type whose blocks reached objects through nested statements.

Decision: A key is a `&[u8]` the runtime hashes and compares, because the runtime would otherwise call the writer's hash and equality under a cell's lock in the middle of a probe, and the index's correctness would then rest on a protocol no admission checks, while byte strings are what a server's keys are and a key is named as a range of its input without building one, instead of a key of any type with a `HashMapKey` binding or integer keys only.

Decision: A table's entries are reached only through entry bindings in the atomic statement's header, `e = &s^.t[k]` for one key and `es = &s^.t[ks]` over a key set, and a table has no subscript in a block, because every key a statement uses on one table must be known before any of its entries is locked, since they are locked together in one order, and the header is what the language evaluates before the block, so a key computed inside a block has nowhere to be written and an attempt is the subscript's ordinary type error [OP-4] ([entries in the header](../../../../research/investigations/shared-state/DESIGN.md#entries-are-named-in-the-header)), instead of a rule that every key used on a table exists before the statement, which writes one container's need into the language, or a compiler that derives the keys from the block.

Decision: A key set, `KeySet`, holds distinct keys in increasing lexicographic order of their bytes, each with a `u64` payload that a later addition of the same key replaces or adds to, and an entry binding over it visits its keys in that order, because the order a reader sees is then the order the entries are locked in, so nothing is sorted out of sight, a key named twice is one entry, and the payload keeps each multi-key command's answer, the last value of `MSET` and the count of a key `EXISTS` names twice ([key sets](../../../../research/investigations/shared-state/DESIGN.md#keys-an-ordered-set)), instead of a list in the order its keys were added, which the runtime would sort where the reader cannot see it.

Decision: For a batch already owned by its caller, one explicit `key_prepare` operation packages the caller's deduplicated source with a private acquisition order, exposes that source transitively readonly and keeps entry indices in source order, because lock ordering requires a stable key-to-order correspondence but does not require copying key bytes, relocating business values or choosing the application's duplicate policy ([prepared keys](../../../../research/investigations/shared-state/DESIGN.md#prepared-keys-source-order-and-lock-order)), instead of extending the ordered set's payload protocol or exposing separate construction, sorting and finishing stages. This provisionally supplements KeySet until the source-storage capability of a replacement is settled.

Decision: Preparation returns the owned source on a bounds or duplicate error, with bounds errors before duplicate errors and the smallest source index or duplicate index pair, because a rejected request must still return its caller's input buffer and diagnostic identity must not depend on the private sorting algorithm, instead of dropping the input on error or reporting whichever invalid pair that algorithm visits first.

Decision: A statement whose guard and block write nothing through an entry binding holds that entry beside the other such statements on its key, and nothing in the source marks it, because those statements' reads take effect at one point each in one order whichever of them runs first [SHARE-3], so sharing changes no outcome, while every client of the benchmark's four `LRANGE` tests reads one list, which firn answered at 0.44 to 0.61 of Garnet on 4 to 16 server CPUs with exclusive holds and at 1.14 to 1.22 of it with shared ones ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores), [shared reads](../../../../research/investigations/concurrent-map/DESIGN.md#shared-reads-of-one-key)), instead of a read form the writer marks, which asks the writer to choose for a difference no program observes, or reads that check a version afterwards, which a block that runs once cannot redo after a torn read.

Decision: A table has one representation wherever it is, the runtime's concurrent index, built empty with a capacity by `keyed_table_new`, and outside an entry binding it is only counted, moved or released, because no unshared use then exists whose representation would differ, so the language needs no rule about where a table may appear, instead of confining a table to the argument of `shared_new` and forbidding it to be moved whole, which guards against a second representation that no operation can reach.

Decision: The table is `KeyedTable<V>`, the set `KeySet` and the entries an entry binding names over a set `KeyedEntries<V>`, because a prelude name always displaces a source declaration of the same spelling [PRE-1] and `Table` already names a struct in conformance cases, instead of `Table`, `Keys` and `Entries`.

Rejected:
- Replaced decision beginning "State that many contexts reach by key is a shared map held through `SharedMap<V>` handles": rejected because a second handle type made a table's entries and its state's other fields two statements, nested by kind.
- Replaced decision beginning "A whole-map statement `atomic s = &m { ... }` holds every entry": rejected because a statement names the entries it reaches in its header and counting is an operation on the table.
- Replaced decision beginning "For a whole-map statement, which holds every entry, an implementation holds only the entries its block reaches": rejected because the header then said the whole map while only the reached entries were locked, and finding those keys meant running part of the block before the hold.
- Replaced decision beginning "The block of a keyed or whole-map statement contains no call to a waiting function": rejected because no statement contains another.
- Replaced decision beginning "A keyed statement whose guard and block write nothing through its binding, and whose block runs at most one object statement": rejected because no block contains an object statement now, so the condition on object statements is gone.
- Replaced decision beginning "The handle is `SharedMap<V>` and its state `SharedMapState<V>`": rejected because the table is a field type and the handle is the state's.
- A compiler that runs the part of a block computing its keys before taking any lock: rejected because the generated code then differs from the written code, the key computations run twice and must answer the same both times, conditions must guard the early run, and a key it could not compute fell back silently to the whole table ([refused along the way](../../../../research/investigations/shared-state/DESIGN.md#refused-along-the-way)).
- Locking the whole table when a block's keys are known too late: rejected because it lets slow code through unseen.
- Taking each entry at its first use in code order: rejected because two statements meeting two keys in opposite orders wait for each other.
- A single-threaded hash map as a field of a state: rejected because entries under different keys are inserted, removed and moved to a larger table by different contexts at once, so such a map could be locked only whole.
- Every keyed statement holding its entry exclusively whether its block reads or writes: rejected because readers of one list then take turns, firn's `LRANGE_100` staying at 1.24 to 1.55 million a second on 2 to 16 server CPUs while Garnet grew to 2.83 million ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores)).
- A read form the writer marks: rejected because the outcome is the same either way [SHARE-3] and the checker already knows which paths the block writes.
- A key of any type with a `HashMapKey` binding: rejected because the runtime would call writer code under a cell's lock in the middle of a probe.
- A map sharded into `Shared` objects, each a lock and a table: rejected because the index the runtime keeps reads without locking and locks one entry per write, which led or tied every measured cell against the fastest comparators ([measured](../../../../research/investigations/concurrent-map/DESIGN.md#measured)), while shards serialize unrelated keys that share a shard.
