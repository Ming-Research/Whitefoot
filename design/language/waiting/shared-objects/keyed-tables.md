Decision: State that many contexts reach by key is a concurrent hash map, `ConcurrentHashMap<V>`, holding an `Option<V>` entry for every byte string. It exists only as the state of a shared object, made together with its object by `shared_map_new::<V>(capacity: n)` as `box_slots_new` makes a `Box<Slots<T>>`, and placed by [TYPE-9]'s table of homes, so a map's entries may hold handles to maps but never maps. This is because a concurrent table is shared by nature and a type's behavior should not depend on where it sits: the language has one meaning for a map, a shared one, reached through a target, while the state that changes beside a key's entry lives in objects of its own that the same statement names. This is instead of a table that was a field of a shared state or an unshared local value, under which a local table carried pending holds settled when it was published, a state's other fields formed a lock unit beside its tables, and a header reached a table through the state's binding by a provenance the checker carried through every alias, or a handle type of its own, `SharedMap<V>`, whose entries and an object's fields needed two statements nested by kind.

Decision: A key is a `&[u8]` the runtime hashes and compares, because the runtime would otherwise call the writer's hash and equality under a cell's lock in the middle of a probe, and the index's correctness would then rest on a protocol no admission checks, while byte strings are what a server's keys are and a key is named as a range of its input without building one, instead of a key of any type with a `HashMapKey` binding or integer keys only.

Decision: A statement names a map's parts by its targets: `e = &h[k]` for one entry, `es = &h[ks]` for the entries under a key set built before the statement, and `t = &h` for the map whole, with several entry and key-set targets on one handle place, and a whole target alone on that place. This is because the hold is then read from the header, the entries are still locked together in one order from keys known when the statement begins ([entries in the header](../../../../research/investigations/shared-state/DESIGN.md#entries-are-named-in-the-header)), and a callee reaches a map only through a whole target, since a map is only a state, so no row rule is needed to find a hold a callee implies. This is instead of table bindings through the state's binding, which needed a grant judgment, a row rule and a provenance carried through every alias.

Decision: A whole target's map is indexable in the guard and block, `t^[k]` the entry under a key and `&t^[ks]` the entries under a set, with no obligation since a map holds an entry under every key, and so is any `&ConcurrentHashMap<V>` a callee receives, because a key a block computes, a script's, needs the map held whole, which costs nothing more for being written, and the two forms are the header's two forms moved inside, so executors written against `&Option<V>` and `&Entries<V>` serve both, instead of a lookup row returning an index, since a map has no index a program could hold.

Decision: A key set, `KeySet`, holds distinct keys in the order each was first inserted, `key_set_insert` answers a key's index, that of its first insertion, and an entry target over the set reaches the entry of the set's key at each index, because the order a program needs is its request's, so a command naming several keys replies and records in the order of its arguments, which the index each argument's insertion returned maps to the set's entries without a second search, while the order the entries are locked in is the runtime's protocol against deadlock, which the program cannot observe, since the statement's guard and block take effect at one point [SHARE-3] and lowering takes every entry of a set before the guard (compiler/waiting-contexts/state-locks); a program keeps a key's last value or its count in its own data at that index, so the language fixes no merge policy ([MSET after the redesign](../../../../research/investigations/shared-state/DESIGN.md#mset-after-the-redesign)), instead of keys in increasing order of their bytes, each with a payload a later put replaced or an add summed, which made every insertion search and move the set's items, about 30 to 50 ns more per ten-key `MSET` than one sort at the hold, made firn rank `MGET`'s and `MSETNX`'s arguments again and write its append-only records in byte order, and fixed two merge policies in the prelude.

Decision: A statement whose guard and block write nothing through an entry target holds that entry beside the other such statements on its key, and nothing in the source marks it, because those statements' reads take effect at one point each in one order whichever of them runs first [SHARE-3], so sharing changes no outcome, while every client of the benchmark's four `LRANGE` tests reads one list, which firn answered at 0.44 to 0.61 of Garnet on 4 to 16 server CPUs with exclusive holds and at 1.14 to 1.22 of it with shared ones ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores), [shared reads](../../../../research/investigations/concurrent-map/DESIGN.md#shared-reads-of-one-key)), instead of a read form the writer marks, which asks the writer to choose for a difference no program observes, or reads that check a version afterwards, which a block that runs once cannot redo after a torn read.

Decision: The map is `ConcurrentHashMap<V>`, the set `KeySet` and the entries a target names over a set `Entries<V>`, because the map's name says what the type is, a hash map that contexts reach concurrently, which is its only meaning now that it is never unshared, and the entries are only ever a reference's referent, so a short name serves, while a prelude name displaces a source declaration of the same spelling [PRE-1], instead of `KeyedTable` and `KeyedEntries`, named when a table could also be a local value.

Rejected:
- The implicit whole hold, a statement holding a table whole when its block forms any path to it other than an entry target: rejected because the header then said less than the block held, the slowest hold a statement can take was the one it did not show, a callee's row could imply it where no reader of the statement saw it, and the mixed header was accepted with a meaning no rule stated; it was the first design's convenience for `keyed_table_count`.
- A hold per field that is no map, `m = &s^.meta`: rejected because fields share one object lock, while fields that change apart can live in separate objects named by separate targets.
- Admitting a path to a whole-bound table through `s` beside its binding: rejected because a binding then had two spellings and the "use every binding" check could not tell a forgotten binding from one reached the other way.
- Replaced decision beginning "State that many contexts reach by key is a shared map held through `SharedMap<V>` handles": rejected because a second handle type made a table's entries and its state's other fields two statements, nested by kind.
- Replaced decision beginning "A whole-map statement `atomic s = &m { ... }` holds every entry": rejected because a statement names the entries it reaches in its header and counting is an operation on the table.
- Replaced decision beginning "For a whole-map statement, which holds every entry, an implementation holds only the entries its block reaches": rejected because the header then said the whole map while only the reached entries were locked, and finding those keys meant running part of the block before the hold.
- Replaced decision beginning "The block of a keyed or whole-map statement contains no call to a waiting function": rejected because no statement contains another.
- Replaced decision beginning "A keyed statement whose guard and block write nothing through its binding, and whose block runs at most one object statement": rejected because no block contains an object statement now, so the condition on object statements is gone.
- Replaced decision beginning "The handle is `SharedMap<V>` and its state `SharedMapState<V>`": rejected because the table is a field type and the handle is the state's.
- A compiler that runs the part of a block computing its keys before taking any lock: rejected because the generated code then differs from the written code, the key computations run twice and must answer the same both times, conditions must guard the early run, and a key it could not compute fell back silently to the whole table ([refused along the way](../../../../research/investigations/shared-state/DESIGN.md#refused-along-the-way)).
- Implicitly locking the whole table when a block's keys are known too late: rejected because it lets slow code through unseen.
- Taking each entry at its first use in code order: rejected because two statements meeting two keys in opposite orders wait for each other.
- A single-threaded hash map as a field of a state: rejected because entries under different keys are inserted, removed and moved to a larger table by different contexts at once, so such a map could be locked only whole.
- Every keyed statement holding its entry exclusively whether its block reads or writes: rejected because readers of one list then take turns, firn's `LRANGE_100` staying at 1.24 to 1.55 million a second on 2 to 16 server CPUs while Garnet grew to 2.83 million ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores)).
- A read form the writer marks: rejected because the outcome is the same either way [SHARE-3] and the checker already knows which paths the block writes.
- Keys in increasing order of their bytes, each with a payload a later put replaced or an add summed (the replaced decision beginning "A key set, `KeySet`, holds distinct keys in increasing lexicographic order"): rejected because the order a reader saw was the runtime's lock order, which a command's replies and records do not follow, keeping that order at every insertion cost a search and a move per key, and the payload fixed two merge policies a program keeps itself.
- An opaque key set whose length and order exist only inside the statement: rejected because the block would still visit the keys in the lock order, so replies and records in argument order would still need a second ranking, and a command tells a repeated key from a new one by what insertion answers before the statement.
- A key of any type with a `HashMapKey` binding: rejected because the runtime would call writer code under a cell's lock in the middle of a probe.
- A map sharded into `Shared` objects, each a lock and a table: rejected because the index the runtime keeps reads without locking and locks one entry per write, which led or tied every measured cell against the fastest comparators ([measured](../../../../research/investigations/concurrent-map/DESIGN.md#measured)), while shards serialize unrelated keys that share a shard.
- Replaced table-as-a-field placement: rejected because map objects remove state-derived lock units and grants through state bindings.
- Replaced local-table representation: rejected because local tables carried pending holds settled on publication and gave the type different access rules at different placements.
- Replaced header grants and their provenance: rejected because each target names a map handle directly and callees receive map references only through whole targets.
- `KeyedTable` and `KeyedEntries`: rejected because a map now has only its concurrent shared meaning and entries exist only as reference referents.
- `map_clear`: rejected because swapping with a fresh map releases old entries outside every lock, while clearing releases them under the whole hold.
- `map_reserve`: rejected because construction fixes initial capacity and cooperative index moves grow the map.
- A `shared struct` declaration: rejected because once one statement holds several objects, maps and other state live in separate objects held together, so one guard construct and one placement table cover every case, instead of a second declaration form whose constructor's type differs from its name.
