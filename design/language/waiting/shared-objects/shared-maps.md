Decision: State that many contexts reach by key is a shared map held through `SharedMap<V>` handles, keyed by byte strings, whose entry under a key is an `Option<V>` reached only inside a keyed statement `atomic e = &m[key] { ... }` that holds that one entry and takes effect at one point, statements on one key taking effect in one order and statements on different keys waiting for none of each other, because a keyspace behind one `Shared` object serializes every client of a server on one lock while one statement form serves every single-key command with no library function and no callback ([design](../../../../research/investigations/concurrent-map/DESIGN.md#stage-b-the-language-surface-stated-before-building)), instead of a library map behind a `Shared` object or a family of map operations taking a callback.

Decision: A key is a `&[u8]` the runtime hashes and compares, because the runtime would otherwise call the writer's hash and equality under a cell's lock in the middle of a probe, and the index's correctness would then rest on a protocol no admission checks, while byte strings are what a server's keys are and a key is named as a range of its input without building one, instead of a key of any type with a `HashMapKey` binding or integer keys only.

Decision: A whole-map statement `atomic s = &m { ... }` holds every entry, binds `&SharedMapState<V>`, the map's state, which `shared_map_count` counts exactly, and reaches entries inside its block through `atomic e = &s^[key] { ... }`, which waits for nothing and counts as no call, because commands over several keys (`MSET`, `DEL` and `EXISTS` of several) and an exact count need one point for all of them, and every keyed statement pays one store on its own thread's cache line to be excluded, instead of a statement over a list of keys taken in an order the runtime fixes, which needs a type for a list of keys and a binding over several entries.

Decision: A whole-map statement whose block reaches the map only through statements on its own entries, under keys the compiler can compute before the block runs, holds those entries and no others, with no change to its source, because the statement already says that its block takes effect at one point and which entries it reaches, firn's `MSET` answered 0.35, 0.20 and 0.10 of Garnet on 4, 8 and 16 server CPUs while every such statement held the whole map and 1.66, 1.83 and 1.64 of it holding its keys ([holding only the entries](../../../../research/investigations/concurrent-map/DESIGN.md#holding-only-the-entries-a-statement-reaches)), and a statement whose keys cannot be computed first, or that counts the map, holds the whole map as before, instead of a key-list type built before the statement, an indexed target `&m[i in a..b => key]`, or a `for` clause on the statement, each of which asks the writer to restate what the block already contains.

Decision: The block of a keyed or whole-map statement contains no call to a waiting function, and of atomic statements only those on a `Shared` object, with no guard, and in a whole-map block those on its own entries, because entries and maps are then always taken before objects and an object's holder takes nothing, so no cycle of waits can form, while an append-only record of a change is made in the same step as the change; a guard there would wait while the entry is held, instead of admitting guarded statements and a deadlock no rule excludes.

Decision: A keyed statement whose guard and block write nothing through its binding, and whose block runs at most one object statement (language/waiting/shared-objects), holds its entry beside the other such statements on its key, and nothing in the source marks it, because those statements' reads take effect at one point each in one order whichever of them runs first [SHARE-3], so sharing changes no outcome, while every client of the benchmark's four `LRANGE` tests reads one list, which firn answered at 0.44 to 0.61 of Garnet on 4 to 16 server CPUs with exclusive holds and at 1.14 to 1.22 of it with shared ones ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores), [shared reads](../../../../research/investigations/concurrent-map/DESIGN.md#shared-reads-of-one-key)), instead of a read form the writer marks, which asks the writer to choose for a difference no program observes, or reads that check a version afterwards, which a block that runs once cannot redo after a torn read.

Decision: The handle is `SharedMap<V>` and its state `SharedMapState<V>`, because `SharedMap` parallels `Shared<T>` for the one-object case and a prelude name always displaces a source declaration of the same spelling [PRE-1], so the state takes a spelling no program is likely to declare: the first name, `Keyed`, displaced a declaration in firn, instead of `Keyed<V>`, or `ConcurrentMap` or `ShardedMap`, which name an implementation.

Rejected:
- Every keyed statement holding its entry exclusively whether its block reads or writes: rejected because readers of one list then take turns, firn's `LRANGE_100` staying at 1.24 to 1.55 million a second on 2 to 16 server CPUs while Garnet grew to 2.83 million ([many cores](../../../../research/investigations/concurrent-map/DESIGN.md#many-cores)).
- A read form the writer marks: rejected because the outcome is the same either way [SHARE-3] and the checker already knows which paths the block writes.
- A key of any type with a `HashMapKey` binding: rejected because the runtime would call writer code under a cell's lock in the middle of a probe.
- A map sharded into `Shared` objects, each a lock and a table: rejected because the index the runtime keeps reads without locking and locks one entry per write, which led or tied every measured cell against the fastest comparators ([measured](../../../../research/investigations/concurrent-map/DESIGN.md#measured)), while shards serialize unrelated keys that share a shard.
- An object statement with a guard inside a keyed or whole-map block: rejected because it would wait for its guard while the entry or map stays held, which no rule could keep from deadlocking.
