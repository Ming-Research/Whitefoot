Decision: State that several contexts reach is a shared object held through `Shared<T>` handles and reached only inside an `atomic s = &h { ... }` statement, whose block runs with exclusive access to the object's state and takes effect at one point within the statement, while the order in which different contexts' statements take effect is an input of the execution, because the object then behaves like a host whose answers depend on others, so that order is one more input beside the host's [WAIT-2] and each context keeps its own in-order meaning, and a lexical block reaches the context's locals directly and shows the atomicity boundary in the source ([design](../../../research/investigations/io-model/SHARED.md#the-idea)), instead of a transaction function that takes a callback and an environment.

Decision: An atomic statement counts as a waiting call, and its guard and block contain no call to a waiting function and no atomic statement, because the waiting-function rule [WAIT-1] then makes holding a state across a host wait and taking a state inside another statement's block unrepresentable, so a statement holds parts of one state only, which its lowering takes in one fixed order before it releases any (compiler/waiting-contexts/state-locks) and which therefore never wait for each other in a cycle, instead of statements nested by kind with an order between the kinds, which the first design adopted when a map's blocks needed an object and which one statement holding both now replaces ([shared state](../../../research/investigations/shared-state/DESIGN.md#locking-order-taking-and-release)).

Decision: A handle is `nocopy`, `shared_share` makes another, and the state is released with the last handle, because contexts finish in an order the program does not know, so no one binding can own the state, instead of an owner context whose end releases the object while others may still hold it; [STOR-3] leaves the state's release to [SHARE-1], since no binding owns it.

Decision: The object's state is a path of no effect row, so a function that changes it declares `waits` and a read of the handle place it reaches the object through, because the state belongs to no binding and no caller and its changes take effect in the atomic order, an input of the execution like a host's effects, instead of a row entry naming the object.

Decision: The object stays live until the statement completes whatever its block does with the target place, because the statement holds a handle of its own, instead of reading the target again when the block ends, which would refuse a block that moves or replaces the handle it was reached through.

Decision: An optional `when` guard, a `Bool` expression that writes nothing, makes the statement take effect at a point where the guard holds, and the block may use the guard as a proved fact [ENT-3], because blocking pops and subscriptions are waits on the shared state itself and the block's operations need the guard's condition as their requirement ([evidence](../../../research/investigations/io-model/SHARED.md#the-first-version)), instead of a condition variable the writer signals.

Decision: A begun atomic statement with no guard, or whose guard is true in its object's state from some point on, eventually takes effect while every context keeps reaching its completion or a wait [WAIT-2], because a waiting guard can become true only through another context's statement, so a consumer and its producer must not finish only on a schedule the implementation happened to choose, and the handoff bound of the context runtime keeps that promise without a measured cost ([model](../../../research/investigations/io-model/CONCURRENCY-MODEL.md#103-progress-and-a-program-that-stops)), instead of withholding weak fairness and letting a statement whose guard stays true lose the object to others forever.

Decision: An atomic statement's guard and block have exclusive access to the whole state its target names, and an implementation may hold less of that state, or hold it together with other statements, wherever the program's outcomes are those it has when every statement's block has exclusive access to its state, because the meaning, one point and one order, is then the same while the compiler knows which parts a block reaches, so holding only those is an optimization with the same effect as holding the whole state ([shared state](../../../research/investigations/shared-state/DESIGN.md#meaning-a-block-owns-the-whole-state-at-one-point)), instead of a statement form for each part a block may hold, which the first design grew for maps.

Decision: An atomic statement whose guard and block reach nothing of its state through its binding or a table binding, or leave a table binding unused, is refused [SHARE-2], because a statement holds what its header names, so such a statement would hold its state, a table or an entry, for nothing the writer can have meant, while every lock it takes still makes other statements wait, instead of accepting it and holding what it names anyway, which would let a mistyped or forgotten binding pass silently, or dropping what nothing uses, which would make what a statement holds differ from what its header says.

Rejected:
- Replaced decision beginning "Provisionally, every atomic statement acquires its object exclusively and nothing marks a statement that only reads": rejected because its reopening condition was met by the `LRANGE` and `MSET` tests of the many-core runs, where readers of one list and statements on different keys of one map took turns.
- Replaced decision beginning "An atomic statement counts as a waiting call, except that one on an entry of a map state its enclosing statement holds counts as no call": rejected because no statement contains another now, so neither the exception nor an order between the kinds of nested statements is needed.
- Replaced decision beginning "An atomic statement's source says what it holds and what its block does": rejected because it named what a statement holds by statement forms, an object, a map's state or an entry, while a statement now owns its whole state and its parts are the implementation's.
- Replaced decision beginning "A block that can run two statements on shared objects is a section": rejected because no statement contains another, so a block holds every part it reaches until it ends and no other statement falls between two of its accesses.
- A transaction function with a callback (`transact`, `inspect`, `transact_when`): rejected because the language has no closures, so every transaction needs a top-level function and an environment struct, and read, guarded and multi-object transactions each need another function.
- An implicit scope that acquires the object for the life of a reference formed through a handle: rejected because whether two adjacent statements form one transaction could not be read from the source.
- Asynchronous messages to the object (actors, channels): rejected because a sender that does not wait for the effect cannot know the order its messages take effect in, and a bounded channel whose send waits is a `Shared<Ring<T, n>>` with two guarded statements, so it needs no construct of its own while an owner context that serves requests would serialize every change through one context and two messages.
- Shards each owned by one context and reached by messages: rejected because every command pays two hand-offs, a command over keys of two shards needs a protocol between their owners, and the queue between contexts is the same exclusion established at run time, moved rather than removed.
- Atomic fields and lock-free cells: rejected because they expose interleavings of single reads and writes inside what the context meaning makes one atomic step.
- Transactions that read optimistically and retry: rejected because a block runs once, moves values and writes its context's locals, so it cannot be repeated.
- Spawns taking references to a state the starter owns, with no handle or count: rejected because the state's content is still reached only under an exclusion established at run time, an effect row cannot state it as written without forbidding a second spawn, since a row entry excludes others for the whole call, and the same state reached through two names has its identity checked at run time either way, which handles serve as well ([shared state](../../../research/investigations/shared-state/DESIGN.md#sharing-owned-handles-and-a-count)).
- Taking some of a statement's parts later than others by an order of kinds the language fixes, maps before objects: rejected because it prescribes an order for one optimization, while the fields of the one state a statement holds already give one.
- An order of store types inferred from every atomic statement of the program: rejected because it needs every function body.
- Lock levels declared in the types of shared stores: rejected because a statement holds one state, whose fields already order its parts.
- Separate handles placed as fields of one struct and ordered by field order: rejected because the same two handles can sit in two structs in opposite orders, which sharing the struct whole removes.
- Ordering transactions by stamps of the host completions that produced them: rejected because it orders nothing a program can observe beyond the single point at which each statement takes effect.
- Starting, while a guard waits, every call around it that the overlap permission covers, so that its starter proceeds: rejected because `spawn` now states where a context starts and a call that is not spawned runs in order, so the promise holds for spawned contexts without a start the writer cannot see.
- Strong fairness, a statement whose guard is true only now and then taking effect: rejected because a guard true only between two of its evaluations can be missed on every schedule without the runtime observing it, and a writer can make the guard stay true instead.
