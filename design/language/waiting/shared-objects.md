Decision: General mutable state that several contexts reach is a shared object held through `Shared<T>` or `SharedRead<T>` handles and reached only inside an `atomic s = &h { ... }` statement, whose block runs with exclusive access to the object's state and takes effect at one point within the statement, while the order in which different contexts' statements take effect is an input of the execution, because the object then behaves like a host whose answers depend on others, so that order is one more input beside the host's [WAIT-2] and each context keeps its own in-order meaning, and a lexical block reaches the context's locals directly and shows the atomicity boundary in the source ([design](../../../research/investigations/io-model/SHARED.md#the-idea)), instead of a transaction function that takes a callback and an environment.

Decision: A one-shot decision cell exposes only an Open, Written or Killed verdict through nonwaiting read and competing claims, each with its own shared effect point and an absorbing winner, because deciding cancellation against an irrevocable step while that step holds shared keys requires the verdict to become visible before the enclosing statement ends, without exposing any intermediate contents of the held state, instead of publishing the verdict only at statement exit or exposing general atomic fields.

Decision: A decision cell is an opaque owning handle shared explicitly by retaining another handle, using the existing shared-object lifetime and ordinary value transfer into contexts, because putting its only handle behind the same held object would make a competing context wait for that object before observing the verdict, instead of new reference-sharing permissions or a source-addressable atomic field.

Decision: Guard admission and optional overlap use a declaration-derived decision-cell-free callable boundary, including contained types and callable parameters, because a helper must not hide a changing verdict from guard wake dependencies or from source-order preservation and module checking cannot depend on another module's body, instead of recognizing only direct prelude calls or inferring effects from implementation bodies.

Decision: An atomic statement counts as a waiting call, and its guard and block contain no call to a waiting function and no atomic statement, because the waiting-function rule [WAIT-1] then makes holding a state across a host wait and taking a state inside another statement's block unrepresentable. Every lock a statement takes then belongs to its one object and is taken in the one order of that object's lock units before it releases any (compiler/waiting-contexts/state-locks), and a cancellation flag read holds nothing, so such statements never wait for each other in a cycle, instead of statements nested by kind with an order between the kinds, which the first design adopted when a map's blocks needed an object, and which one statement holding one object, whose maps are parts of its state, now replaces ([lock units](../../../research/investigations/shared-state/DESIGN.md#lock-units)).

Decision: An atomic statement holds exactly one shared object, `atomic s = &h when g { ... }`, whose binding `s` is a reference to the object's whole state, and state that changes together is one state, its parts reached by ordinary paths from that one root and told apart by OWN-7 as the parts of any value are [SHARE-2], because whether two handles name one object is known only at run time, since `shared_share` makes handles there, so a statement over several objects had to judge every two targets whose state types unify as paths from one root and refused writes a program meant to be apart, two databases of one store chosen by number among them, while two maps of one state chosen by number are told apart by their indices as two elements of any array are ([one object per statement](../../../research/investigations/shared-state/DESIGN.md#one-object-per-statement)), instead of several targets per statement, a handle identity that exists only in proofs, or other shared-state classes derived from that identity (owner's ruling on the board card shared-object-model-adopt). This re-proposes one object per statement, which the tree had refused because unrelated state then shares a lock and maps beside other fields needed lock units derived from the layout and a header grant: a map is now reached by an ordinary path and needs no grant, its lock units follow from the equivalence below (compiler/waiting-contexts/state-locks), and state that does not change together stays in an object of its own.

Decision: A handle is `nocopy`, `shared_share` or `shared_read_share` makes another handle of its kind, and a handle ends by its release or by `shared_close`, the handles of one object ending in one order whose last end takes the state, a close returning it and a release releasing it, that order being an input of the execution as the atomic order is, because contexts finish in an order the program does not know, so no one binding can own the state, instead of an owner context whose end releases the object while others may still hold it; [STOR-3] leaves the state's release to [SHARE-1], since no binding owns it.

Decision: A handle to a linear state is itself linear (`language/ownership/linearity`) and ends only in `shared_close`, a waiting call that returns the state to the last handle to end and `None` to every other, because a linear value must be consumed explicitly on every path while which context ends last is known only at run time, so the obligation falls on each handle and the object's handle count decides who receives the state, as Rust's `Arc::into_inner` does where it is optional, instead of an owner handle whose waiting reclaim returns the state while the other handles stay droppable, which waits forever while the owner itself holds another handle, or a handoff channel alone, which cannot let contexts share one linear state (owner's ruling on the board item firn-wf-linear-share, option A).

Decision: A linear state type has no part that is its own handle type, through fields, payload fields, elements, `Box` content and the state behind each `Shared` handle, judged at a generic function's symbolic instance and again at each concrete instance, because a handle its own object held would keep the count from reaching the last close, and every cycle of objects through linear states reaches each of their state types, since a state holding a linear handle is linear, instead of refusing every linear-state handle inside a linear state, which also refuses passing one object's handle to a running context through another object.

Decision: Contexts that take turns with a resource that must be closed explicitly use a linear shared state and ordinary code, with no lease construct: the resource sits in a one-slot window that is the object's state, a guarded atomic statement moves it out to a local window, the context uses it as an ordinary linear local across waiting calls, a second guarded atomic statement puts it back on every path, and the handle that ends last receives it and closes it, because a linear local must be consumed on every path and cannot be copied, so one context holds it at a time, a context that wants it waits in its guard until it is put back, and the last close receives it exactly once, which is every guarantee a lease would give except that the resource goes back to the window it came from, instead of a lease construct. That it goes back to its window, and that a context holding it does not take it again, stay the program's to keep, and neither lease form would check the second.

Decision: The object's state is a path of no effect row, so a function that changes it declares `waits` and a read of the handle place it reaches the object through, because the state belongs to no binding and no caller and its changes take effect in the atomic order, an input of the execution like a host's effects, instead of a row entry naming the object.

Decision: The object stays live until the statement completes whatever its block does with the handle place, because the statement holds a handle of its own, or, for a linear state, because every handle the block may move away still names the object, a linear handle ending only in a close that no block contains, instead of reading the handle place again when the block ends, which would refuse a block that moves or replaces the handle it was reached through.

Decision: An optional `when` guard, a `Bool` expression that writes nothing, makes the statement take effect at a point where the guard holds, and the block may use the guard as a proved fact [ENT-3], because blocking pops and subscriptions are waits on the shared state itself and the block's operations need the guard's condition as their requirement ([evidence](../../../research/investigations/io-model/SHARED.md#the-first-version)), instead of a condition variable the writer signals.

Decision: An atomic statement's guard reads or writes no path whose type is, or has as a part, a self-changing host handle, and PRE-2 lists those handles in one table: the monotonic `Clock`, the calendar `WallClock`, the process `MemoryMeter` and the `HandleFactory`, through which the open-files limit is read. A guard that reaches one is refused, with a repair that waits for the time outside the guard, through a deadline or through a cancellation source that a context waiting for the deadline fires. This is because a waiting guard is woken only by a write to its object's state or by the firing of a cancellation flag it reads, so a guard whose value the host changes with no write may never wake, the progress promise [WAIT-2] does not hold for it, and the runtime's wake tests assume that only writes change a guard (owner's ruling on the guard-clock card, option A). It is instead of accepting such a guard, which can wait forever on a true condition, or of refusing every guard call that receives a struct holding a clock, since a row that reads only another field of that struct reads no clock. The handles are a table rather than a marker on their declarations, because the host modules' records are the specification's text and a marker would add a declaration modifier for a handful of structs.

Decision: A begun atomic statement with no guard, or whose guard is true from some point on, eventually takes effect while every context keeps reaching its completion or a wait [WAIT-2], because a waiting guard can become true only through another context's statement or cancellation firing, so a consumer and its producer must not finish only on a schedule the implementation happened to choose, and the handoff bound of the context runtime keeps that promise without a measured cost ([model](../../../research/investigations/io-model/CONCURRENCY-MODEL.md#103-progress-and-a-program-that-stops)), instead of withholding weak fairness and letting a statement whose guard stays true lose the object to others forever.

Decision: An atomic statement's guard and block have exclusive access to the whole state of its object, and an implementation may hold less of that state, or hold it together with other statements, wherever the program's outcomes are those it has when every statement's guard and block have exclusive access to the whole state, a part that a fact used in checking the statement names counting as accessed whether or not its code reads it [SHARE-3], because the meaning, one point and one order, is then the same while the compiler knows which parts a block reaches, so holding only those is an optimization with the same effect as holding the whole state ([shared state](../../../research/investigations/shared-state/DESIGN.md#meaning-a-block-owns-the-whole-state-at-one-point)), and a fact the block relies on, a type invariant or a proof step, may name parts its code never reads, which another statement must not change meanwhile, instead of a statement form for each part a block may hold, which the first design grew for maps.

Decision: An atomic statement whose guard and block leave its binding unnamed is refused [SHARE-2], because a statement holds the state its binding names. Such a statement would hold a state for nothing the writer can have meant, while every lock it takes still makes other statements wait. This is instead of accepting it and holding the state anyway, which would let a mistyped or forgotten statement pass silently, or holding nothing, which would make what a statement holds differ from what its header says.

Decision: SharedRead<T> is a general retaining read-only handle made from Shared<T> by shared_read and shared through shared_read_share, usable in the same atomic statements, with the same state identity and lifetime as mutable handles, because callers need to observe a protected state without acquiring authority to replace its root, exchange it or consume it, instead of readonly fields alone, which protect neither whole replacement nor exchange (owner's board card firn-cancel-guard-shape, option A; [study](../../../research/investigations/context-cancellation/guards.md#3-the-stacked-pr-needs-a-small-semantic-core-followed-by-explicit-compiler-and-runtime-support)).

Decision: Read-only authority follows the resolved state root through aliases, descendants and call effects while references keep their ordinary spelling, because a helper or alias must not recover write authority to a read-only state and existing effect substitution already identifies each affected path, instead of a new reference qualifier or an operation-name exception.

Rejected:
- Replaced decision beginning "A handle is `nocopy`, `shared_share` or `shared_read_share` makes another handle of its kind, and the state is released with the last handle": rejected because a linear state cannot be released implicitly, so a handle now also ends in `shared_close`, which gives the state to the last handle to end.
- Replaced decision beginning "Provisionally, every atomic statement acquires its object exclusively and nothing marks a statement that only reads": rejected because its reopening condition was met by the `LRANGE` and `MSET` tests of the many-core runs, where readers of one list and statements on different keys of one map took turns.
- Replaced decision beginning "An atomic statement counts as a waiting call, except that one on an entry of a map state its enclosing statement holds counts as no call": rejected because no statement contains another now, so neither the exception nor an order between the kinds of nested statements is needed.
- Replaced decision beginning "An atomic statement's source says what it holds and what its block does": rejected because it named what a statement holds by statement forms, an object, a map's state or an entry, while a statement now owns its whole state and its parts are the implementation's.
- Replaced decision beginning "A block that can run two statements on shared objects is a section": rejected because no statement contains another, so a block holds every part it reaches until it ends and no other statement falls between two of its accesses.
- A transaction function with a callback (`transact`, `inspect`, `transact_when`): rejected because the language has no closures, so every transaction needs a top-level function and an environment struct, and read, guarded and multi-object transactions each need another function.
- An implicit scope that acquires the object for the life of a reference formed through a handle: rejected because whether two adjacent statements form one transaction could not be read from the source.
- Asynchronous messages to the object (actors, channels): rejected because a sender that does not wait for the effect cannot know the order its messages take effect in, and a bounded channel whose send waits is a `Shared<Ring<T, n>>` with two guarded statements, so it needs no construct of its own while an owner context that serves requests would serialize every change through one context and two messages.
- Shards each owned by one context and reached by messages: rejected because every command pays two hand-offs, a command over keys of two shards needs a protocol between their owners, and the queue between contexts is the same exclusion established at run time, moved rather than removed.
- General atomic fields and general lock-free cells: rejected because they expose interleavings of single reads and writes inside what the context meaning makes one atomic step; the separately decided one-shot control verdict exposes no intermediate contents of that step's held state, and a watch's cancellation flag, read at its own point inside a statement, exposes only its one change from false to true and names no fact (language/system-interface/context-cancellation).
- Transactions that read optimistically and retry: rejected because a block runs once, moves values and writes its context's locals, so it cannot be repeated.
- Spawns taking references to a state the starter owns, with no handle or count: rejected because the state's content is still reached only under an exclusion established at run time, an effect row cannot state it as written without forbidding a second spawn, since a row entry excludes others for the whole call, and the same state reached through two names has its identity checked at run time either way, which handles serve as well ([shared state](../../../research/investigations/shared-state/DESIGN.md#sharing-owned-handles-and-a-count)).
- Taking some of a statement's parts later than others by an order of kinds the language fixes, maps before objects: rejected because it prescribes an order for one optimization, while the fields of the one state a statement holds already give one.
- An order of store types inferred from every atomic statement of the program: rejected because it needs every function body.
- Lock levels declared in shared-store types: rejected because a statement takes only the units of its one object, in the one order its state's fields give, so a writer-maintained level orders nothing left open.
- Separate handles ordered by their containing struct fields: rejected because the same two handles can occur in structs in opposite orders.
- Ordering transactions by stamps of the host completions that produced them: rejected because it orders nothing a program can observe beyond the single point at which each statement takes effect.
- Starting, while a guard waits, every call around it that the overlap permission covers, so that its starter proceeds: rejected because `spawn` now states where a context starts and a call that is not spawned runs in order, so the promise holds for spawned contexts without a start the writer cannot see.
- Strong fairness, a statement whose guard is true only now and then taking effect: rejected because a guard true only between two of its evaluations can be missed on every schedule without the runtime observing it, and a writer can make the guard stay true instead.
- Several targets per statement, whole objects, map entries under a key and entries under a key set, with two handles of one object held once and the states of two targets whose types unify compared as paths from one root (the replaced decision beginning "An atomic statement names each object it holds as a target"): rejected because whether two handles name one object is known only at run time, so every two unifiable targets had to be judged one storage and writes a program meant to be apart were refused, two databases of one store among them, while one state tells such parts apart by ordinary paths.
- Proving two handles distinct before one statement holds them together, through a handle identity that exists only in proofs, or deriving other shared-state classes from such an identity: rejected because `shared_share` makes handles at run time and none of these tells apart two databases a program chooses by number, while a statement that holds one object needs no such proof.
- Replaced single-state nesting prohibition: rejected because no block contains an atomic statement, and state a statement changes together is one state whose units it takes in one order, which supplies the same absence of lock cycles.
- Replaced unused-state or table-binding judgment: rejected because the header now names one object through one binding, which the guard or block must name.
- A cancellation-specific atomic target (option B): rejected because a statement holds one object, so a cancellation state held beside it, as a target of any kind, would bring back several objects per statement, while a watch's flag is read without holding the state (language/system-interface/context-cancellation).
- Cancellation independently interrupting a pending atomic statement (option C): rejected because it adds a nonexecuting outcome and result/edge rules instead of the selected guard disjunction and ordinary atomic body.
- A lexical lease block that lends the resource to a block and puts it back on every exit edge, with a reclaim protocol and a contract against swapping the file away: rejected because what it adds to a linear local in a linear shared state is the automatic put back and, through its contract against swapping the file away, the put back to the same window, and that contract would refuse the swap of a new file in for the old one that a log rewrite does.
- An explicit lease value that must be consumed by a return call, with the same reclaim protocol and contract: rejected because the resource is already a linear value that can be passed to another function to put back, so the extra type and protocol add only the same-window contract, which refuses the same swap.
