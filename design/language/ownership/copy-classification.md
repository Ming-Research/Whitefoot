Decision: A type has two capabilities, copy and drop, and the class names copy, affine and linear are prose terms defined once over them, a type with both capabilities being copy, a type with drop alone affine, and a type with neither linear, no type having copy without drop, while a reference carries no class at all because it names a path and is not a value, because what a generic bound asks of its argument (`language/generics`) and what a declaration modifier removes are these two capabilities, so the keywords name capabilities, `copy`, `drop`, `nocopy` and `nodrop`, and none names the affine or the linear class, while the specification's prose still uses the three class names in several hundred places, which one definition keeps exact until a specification pass can afford the review that rewrites them in capability words, instead of three classes as the primitive notion with a keyword for each, or a class assigned to a reference so that copying one is a language question.

Decision: Copy is structural in the manner of Rust's auto traits, exactly as drop is: primitives have both capabilities, and every other type has a capability exactly when every part it owns has it, its fields, its variant payload fields, its heap cell content and the elements of a storage shape, and its declaration does not remove it, so a struct of copy fields and a tag-only enum are copy, `Bool` being the canonical case, the prelude's `Box`, `Slots`, `Ring`, `Segments` and `Paged` declarations and the standard library's host handle declarations remove copy with `nocopy` or `nodrop` so that a type owning one of them is not copy, an `Array` has the capabilities of its element type, and a generic nominal's class is decided at each instance from its arguments, because small value structs must be copyable, because the rule this replaces, under which only primitives and tag-only enums were copy, had been chosen at the start for simplicity and left an unprincipled asymmetry in which a declaration could remove drop while copy could be neither removed nor obtained, and because structural copy hides no cost, a move of an inline value being the same byte copy, instead of copy confined to primitives and tag-only enums with every other owned composite affine.

Decision: A declaration removes a capability with a modifier built on the same word root as the bound that asks for that capability, `nocopy` making a type's values non-duplicable although every part could be copied, and `nodrop` stating the must-consume obligation (`language/ownership/linearity`) and removing copy together with drop, a struct or enum declaration carrying at most one of the two, including fieldless structs and tag-only enums, because a reader who has met the bounds `T: copy` and `T: drop` then reads `nocopy` and `nodrop` with no second vocabulary, and the owner chose the root `drop` over `discard` because it parallels Rust, `nodrop` reading at once as a type for which nothing is destroyed by default and a consuming function must be written, instead of the modifier `linear`, a class name that shares no root with the bound asking for the capability it removes and that had no counterpart removing copy.

Decision: `move` written on a copy value is a hard error and a copy value is used bare, because `move` then marks in the source exactly the objects that are not copyable, and one meaning keeps one spelling (`language/surface-form`), instead of admitting `move` on a copy value as a redundant spelling of the bare use.

Decision: A generic body's consuming spelling is checked once against its type parameter's bound, written or absent, and not rejected again when a concrete argument is copy, a `move` of a value whose parameter was bounded `drop` or left unbounded denoting a copy at such an instance, because rechecking the spelling per concrete type would contradict authoring a generic body once against its bound, instead of per-instance rechecking.

Rejected:
- Replaced decision, that only resource-free primitives and tag-only enums copy on use while every other owned composite is affine: rejected because it was a starting simplification rather than a principle, it made a small value struct of copy fields uncopyable, and it let a declaration remove drop while copy could be neither removed nor obtained; its successor is the structural decision above.
- Every enum affine regardless of payload, including Bool: rejected because it bought zero safety and forced integer-flag workarounds that cost a measured 1.6 to 1.8 times on scanner kernels, an owned Bool being unable to be loop-carried state or to flow through boolean dataflow, so that the recurrence vectorized at width two by four instead of sixteen.
- Give references a value class so that one can be duplicated, stored or returned: rejected because a reference names a path rather than owning storage, so there is nothing for a class to govern, and a stored one would outlive the path it names.
- The word pair `discard` and `nodiscard` for the drop capability and the modifier removing it: rejected because `drop` parallels Rust, whose reader already knows that word for the compiler-derived end of a value, while `discard` would be a second word for the same event.
- The word pair `release` and `norelease`: rejected because `norelease` reads as a value that is never released, the opposite of a value the program must release explicitly.
- The word `forget`: rejected because in Rust it means leaking a value without running its release.
- Requiring a noncopy payload before a declaration may remove drop: rejected because a consumption token would then need a dummy resource field, although capability removal is independent of its structural defaults.
