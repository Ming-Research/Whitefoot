Decision: Parallel permission derives from checked ownership, effects, dataflow, control flow and domain proofs; a denied permission leaves an accepted program sequential, because overlap is an implementation liberty that must preserve sequential meaning, instead of a source parallel keyword that grants overlap.

Decision: Computation keeps its sequential meaning, while a `spawn` of a waiting call starts a context that runs concurrently with its starter, contexts affecting one another only at host operations, atomic statements and joins, whose order is an input of the execution, and a call that is not spawned executes in order in its caller's context, because concurrent I/O has programs with no sequential schedule, such as a bounded buffer between two contexts, and a sequentially correct poll loop can hang when an implementation overlaps it unasked, so concurrency must be a choice the writer makes visibly ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#41-contexts-are-concurrent-sequential-processes)), instead of a sequential meaning under which an implementation may overlap any permitted waiting call, which with shared objects adds executions the in-order meaning excludes.

Decision: A spawn stands as the call of an expression statement or of an ordinary `let` right-hand side, takes only value parameters, and is joined when its activation leaves by any edge or, for a `let`, at the beginning of the first later statement of its block that names the binding or leaves the block, because the binding is then the context's only other footprint, and a join is a wait whose place is observable, so the rule fixes it where the lowering places it ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#102-the-meaning-and-its-join-points)), instead of join handles or a gather primitive that the language would have to type and consume, or a join at the use inside a statement, which leaves later code a joined and an unjoined path to merge.

Decision: Permission and actualization are separate judgments, because a permission is a proved program property while scheduling is a cost choice, instead of making acceptance depend on a lowering or runtime decision.

Decision: A counted loop is a parallel-permission site in its own right, because iteration independence must not depend on rewriting the loop as sibling calls, instead of treating loop permission as a special case of the sibling-call rule.

Decision: A statement or counted loop that contains a waiting call has no overlap permission, because an overlapped member runs as a compute task and a compute task never waits, instead of overlapping waiting statements on the compute scheduler.

Rejected:
- Source staged-loop permission selected by suspension or native-operation classifications: rejected because a call's declared effect row covers, for the whole of the call, every place the callee may reach through its arguments, and where an operation happens to be implemented cannot authorize overlap that row does not; the loss of pipeline permission is established, but its separate runtime cost has not been measured.
- Unstructured tasks with join handles: rejected because a handle needs a new type and consuming rule, while joining at the activation's exit needs neither.
- Reference parameters for a call run as a context: rejected because a reference cannot outlive its statement [REF-3] and such a call does.
- `mustpar` as a checked assertion of a permission, on a counted loop or a call: rejected because only two conformance cases, and no program, experiment or compiler test, wrote its computation forms, the permission ledger reports a denial where a program's test can check it, and beside `spawn` a second call prefix would read as a weaker start; reopen with a program whose parallelism was lost silently and mattered ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#44-what-becomes-of-mustpar)).
- A sequential meaning in which an implementation may run any permitted waiting call as a context, with a progress promise for calls near a waiting guard: rejected because which calls run concurrently then followed a compiler analysis the writer could not see, and a guard that only a later statement satisfies made termination depend on that analysis ([model](../../research/investigations/io-model/CONCURRENCY-MODEL.md#2-why-compute-parallelism-is-sequentially-equivalent-and-io-is-not)).
- A spawn of a callee that does not wait, run in order: rejected because such a callee cannot interleave with anything, so the word would have two meanings.
