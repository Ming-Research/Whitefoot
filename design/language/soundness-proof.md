Decision: The specification's soundness is evidenced by a machine-checked Lean 4 proof over an executable model that formalizes the covered rules' own sentences for a fragment of the constructs, proving that every program the model's checker accepts runs without reaching a state the specification gives no meaning, because the rule-level defects found so far were details of the rules, such as which reads a call's overlap check compares, which types a release list names and where a fact's origin ends, that an idealized calculus abstracts away, and an executable model lets the conformance cases test that the model says what the specification says ([study](../../research/investigations/spec-proof/DESIGN.md)), instead of an idealized core calculus, a model of every rule before any proof, or a tested model with no proof.

Decision: A change to the specification or the model is checked in the same work by `proof.yml`, a merge precondition for both: every line of every covered rule is marked as modeled beside the Lean definition that formalizes it or listed as outside the fragment, each with the hash of the line's bytes, every rule of a covered family is classified, and every theorem checks with no axiom beyond Lean's standard three, because a formal model kept on its own cadence drifts and then freezes, as every precedent in the [specification-representation study](../../research/investigations/spec-representation/DOSSIER.md) did, instead of a proof brought up to date before releases or from time to time.

Decision: Once the model parses programs, the same check runs every conformance case written in the fragment's constructs, requiring the model to accept each accepted case, to run each run case to its expected status, and to reject each rejected case whose expected rule is covered, because a model that disagrees with a case is either unfaithful or has found a gap in the rules, instead of a model tested only by its own examples.

Decision: The model's runtime semantics takes no step wherever the specification gives an operation no meaning, and each step it takes cites the rule sentence that gives it meaning, because a step that supplied meaning the specification does not give would make the safety theorem hold by construction at that point, instead of a total semantics with default results.

Decision: The model is evidence about the specification and never a definition of the language: a disagreement between the model and the specification is a defect of one of them, settled as a disagreement between the specification and the compiler is, because the specification states every normative fact once, instead of making the model normative.

Decision: The model and its proofs are the Lean package `proof/` in this repository, outside `research/`, with a pinned toolchain and no dependency beyond Lean's own library, because the check that runs them gates changes to the specification and a gate may not depend on research material, instead of a separate repository whose checks would see a specification change only after it merged.

Rejected:
- A formal model kept on its own cadence, the sibling model the specification-representation study refused, or one brought up to date before each release: rejected because a defect admitted by a changed rule would reach downstream pins before the proof saw it, and the catch-up is the separate cadence that drifted and froze in every precedent.
- An idealized core calculus in the manner of RustBelt's lambda-Rust: rejected because the proof would hold of the calculus while the defects found so far lived in rule details the calculus leaves out.
- Modeling every rule before proving anything: rejected because 693 KB of rules changing several times a day is not a first target, while a fragment grows into the whole.
- One source in a domain language that generates both the prose and the model, as SpecTec does for WebAssembly: rejected for now because it rewrites the specification in a new language, and WebAssembly's precondition, rules that were formal before they were prose, is absent here.
- Rocq with Iris: rejected for the sequential fragments because the model must run on the conformance cases on every change and extraction adds a translation step, and agents, who write and maintain the proofs, prove most in Lean; Iris remains the logic to reopen for interference if Lean's port proves too weak.
- Isabelle/HOL: rejected because its model would run through generated code in another language, and its strength, counterexample search before proving, is matched by running the executable model on generated programs.
- An SMT-backed verifier such as Dafny or F*: rejected because a verdict that can change with solver version or resource limits cannot gate, the same instability the language refuses for program acceptance.
- Random testing of an executable model with no proof: rejected as the end state because it finds counterexamples without establishing their absence; it remains a tool inside the model.
- Comparing the model with every rejecting conformance case: rejected because the model would have to reproduce rejections with no safety meaning, such as canonical form and diagnostics, growing without strengthening the theorem.
