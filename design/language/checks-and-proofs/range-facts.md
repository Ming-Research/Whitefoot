Decision: A range fact binds one or two variables and states guarded affine relations over literals, consts, bound variables, live integer values, measures, segment lengths and integer element reads, because the facts the level cascade and the scatter producers need are pointwise or pairwise, as a left inverse `positions[order[k]] == k` or `depth[parent[e]] + 1 == depth[e]`, and every further binder multiplies the instances a derivation forms ([derivation](../../../research/investigations/unique-keys/POINTWISE.md)), instead of arbitrary nesting or alternation of quantifiers.

Decision: A range fact is proved where it is owed, at every call of a function requiring it, at its loop's entry, on every backedge and at every exit that selects a postcondition stating it, by one fixed derivation: active facts are instantiated at the values the problem's own element reads select through the fact's reads, a read of a written version splits into the written element and the old one, a joined value into the arm taken, and two reads of one version into the same element and different ones, over equalities solved over the integers, read congruence and Fourier-Motzkin elimination of integer-tightened inequalities, because those are the steps a pointwise invariant's preservation takes after one element write, a frontier element's case and a certificate's separation, and each is bounded by what the problem already holds, so the judgment searches nothing and always terminates, instead of an SMT solver with quantifier instantiation or written instances for every obligation.

Decision: The derivation runs every branch to completion over exact arithmetic, and only the problem's size is bounded: a problem of more than 4096 atoms, or more than 256 formed instances of one fact, rejects the site naming the ceiling, because acceptance must not depend on a work budget, and a ceiling on branches or on one elimination's inequalities counts work whose amount depends on the order the derivation splits and eliminates, which the specification does not fix, while the problem's atoms and instances are the same in every order; the numbers are provisional and reopen when a program reaches either, instead of branch and elimination ceilings, an unproved verdict at a ceiling, or no size ceiling.

Decision: The theory tightens each inequality a literal forms over the integers and then asks only for a rational solution, because Fourier-Motzkin elimination that also tightens what it derives refutes some integer-infeasible sets in one elimination order and not in another, so its verdict would depend on an order the specification does not state, instead of tightening at every elimination step or fixing an elimination order in the specification; the cost is that an integer-infeasible set whose infeasibility needs a tightened derived inequality, such as `a + b <= 1, a <= b, 2a >= 1 + e, e >= 0`, stays open, and the choice reopens when a program needs such a refutation.

Decision: The theory solves a set's equalities over the integers, renaming an atom by an integer change of variables until an equality has a unit coefficient, and tightens each inequality over the resulting free atoms, so its verdict depends only on the set of literals and a contradiction stays one as literals are added, because solving only the equalities that already had a unit coefficient left the others to rational elimination, and which had one depended on the order of solving: `x == 3z, x == -2y, x == 3` was refuted with `x == -2y` solved first and open with `x == 3z` first ([order-free derivation](../../../research/investigations/unique-keys/POINTWISE.md#an-order-free-derivation)), instead of stating an order of solving, which would make a verdict depend on where the walk places each literal and let an added literal undo a refutation, or solving equalities rationally with each literal tightened in the problem's own atoms, which loses refutations such as `i == 2k, j == 2m + 1, i == j`.

Decision: A branch is split on any open item into all of its cases, where an open item is a definition without a case, a disequality the solutions do not fix, or two reads of one version neither at one index tuple nor held apart at a differing position, and two reads the literals keep from being one element are split over their differing positions, so with the theory above the clause's verdict is the same in every split order and a search that skips branches already shown refuted keeps it, because a pair kept apart at two positions was left unsplit, so a refutation that orients a position was found for a pair that differs at one position and not for one that differs at two, and a pair at strided indices tried equal stayed open and was split again without end ([order-free derivation](../../../research/investigations/unique-keys/POINTWISE.md#an-order-free-derivation)), instead of a split order stated in the specification, which would fix the checker's search and keep these differences.

Decision: An aggregate copied out of storage is new storage whose contents the judgment does not know, because a fact is bound to the storage it was stated over and a copy is other storage, so carrying the source's facts over would need every copy site, a `let`, a `set`, a `give`, a construction field and a match binder, to map the source's storage onto the copy's; reopen when a program must keep a fact across a copy, instead of carrying the source's contents and facts to the copy or treating the copy as its source, which took a write to the copy for a write to the source.

Decision: A range fact crosses a call both ways: as the callee's requirement, owed at the call, and as its postcondition, owed at each exit that selects it and taken by the caller after the call at the result ordinals it names as [FN-9]'s relations name them, one routed through `when V(value: r)` in the arm of a `match` that takes V, because a pass that validates a structure and derives its index arrays must hand the facts it establishes to the code that consumes them, which without postconditions had to contain the producer's loops itself, so a validating walk could not be one function several passes call, and a fill constructor's contents, every element v of `box_array_filled(count, v)` and under `Some` each segment's length and every element of `box_segments_filled(lengths, v)`, are then range postconditions of its [PRE-1] row instead of a rule of their own, instead of facts that cross a call only as requirements beside the fill constructors' contents as a separate source.

Decision: After a call the caller also takes each of the callee's [FN-9] relations whose two sides are range terms, as a clause without bound variables, because such a relation, as `box_segments_filled`'s `made.inner.len == lengths^.len`, bounds the facts the same row promises and ordinary entailment already proves it at the callee, so the range judgment only consumes it, instead of restating each such relation as a range clause, which would admit clauses without bound variables to the writer's language to say one fact twice, or letting the range judgment read every fact ordinary entailment holds after a call, which would couple the two judgments at every statement.

Decision: A range postcondition routed through `when V(value: r)` is skipped at a return whose value at the routed ordinal is a construction of another variant or is known in the range walk's state to hold another variant, where that state knows a location's variant from a construction stored there or a `match` arm taken on it and keeps it across a join only where every arm knows it, and is owed at every other return the walk reaches, because the walk already tracks variants that way, so the selection is decided by state the specification defines for the range judgment, while [FN-9]'s selection of ordinary relations reads the constructor tags ordinary entailment transports, which the range judgment does not hold, instead of [FN-9]'s transported tags, which would couple the two judgments, or skipping only a construction of another variant, which would owe a payload fact at a return of a value the walk knows holds no payload of V.

Decision: An inhabited instance must select each of its range postconditions at some exit the walk reaches, as [FN-9] requires of an ordinary relation, because a postcondition no exit selects promises a caller nothing and is a writer's mistake, such as a route that names the wrong variant, instead of accepting it as vacuous.

Decision: A range postcondition names an `own` parameter only as an integer value at entry, and a place rooted at an `own` aggregate parameter, a measure included, is refused, so an [FN-9] relation naming such a measure, which [FN-9] reads at entry, is not among the relations a caller's range walk takes, because the call consumes that storage, so the caller holds nothing a fact about its exit state could describe, and the walk keeps no entry version of the storage a callee may change, instead of reading such a place at entry, which would need that entry version for every consumed parameter; reopen when a program must relate a result to a by-value argument's measure or contents in a range proof.

Decision: Live storage carries no range fact across passes, so each pass establishes the facts it uses over the storage it builds or receives, because a renderer's document is changed by scripts between passes, so a fact kept with it would be owed again by every mutation while a pass already walks what it styles in O(n) and can check the structure it reads ([plan](../../../research/investigations/unique-keys/POINTWISE.md#the-architecture-rule-each-pass-derives-its-facts)); a postcondition hands a fact over one call and no further, instead of facts maintained by every document mutation.

Decision: In a generic function a range clause is formed at the function's symbolic instance, with each value and element of a type parameter's type taken as an integer, and again at each concrete instance, where it states nothing, neither a fact nor owed, if such a type is not an integer, because a range relation compares integers while a generic container's elements need not be integers, as `box_array_filled<T>`'s content fact must hold for `u64` and say nothing for a struct, and checking the clause's form at the symbolic instance keeps a misformed clause an error, instead of refusing range clauses over a type parameter's values, which would leave the fill constructors' contents a rule of their own, or a bound that admits only integer types.

Rejected:
- Ceilings on the branches one derivation opens and the inequalities one elimination holds: rejected because both count work that depends on the split and elimination order, so two checkers following the specification could accept differently at the ceiling.
- Three or more bound variables, such as distinctness within each segment of a `Segments` as `(d, a, b)`: rejected because a left inverse over two variables states the same distinctness, `positions[s[d][k]] == k`, at a fraction of the instances.
- Written instances for every obligation, as a certificate gives a loop: rejected because a preservation proof would then restate, at every write, instances the problem's own reads already select.
- Range facts that cross a call only as requirements, with the fill constructors' contents as a separate fact source: rejected because a producer's facts then never leave the function that establishes them, so the validating walk and the grouping had to sit in the function that consumes their facts, and the constructors' contents were an exception that a postcondition of their rows states as an ordinary clause.
