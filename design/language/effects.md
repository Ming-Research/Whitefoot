Decision: An effect row is checked for exactness in both directions, an exhibited but undeclared effect and a declared but unexhibited effect are both errors, and a row stays exact even where a later proof could remove the effect, because an exact row is a statement a reader and the checker can rely on without reading the body, padding a row would be a place to smuggle effects, and the later-proof clause keeps acceptance decidable from the signature alone, instead of rows as upper bounds.

Decision: An effect row is declared only on reference parameters and carries only `reads` and `writes`, where `writes` covers writing, replacing, moving out of, and freeing the storage at the named path and everything below it, while a by-value parameter carries no entry at all and its consumption or its copy is recorded at the call site from the argument's own place, because a row exists to tell a caller which storage it still owns a callee may reach, and the fate of an owned argument is already visible where it is written, instead of rows over owned parameters, separate external categories, or effect roots recovered from an owner's value history.

Decision: An effect path starts at the bare name of a reference parameter, that name standing for the storage the parameter refers to, and continues through fields, measure and window-part names, enum payload steps, and whole-index or range positions supplied as arguments, with no dereference step written anywhere in it, so an operation that replaces the content of a cell parameter writes the parameter itself and one that reads a length inside that cell reads the parameter followed by the field steps down to it, and a signature never contains an index expression, because every effect path is rooted at a reference parameter by this same rule, so a dereference step separates nothing from anything and gives one meaning a second spelling, while a callee reaches heap content and the one element its caller selected, and an index evaluated once at the call is a fixed object the overlap judgment can compare, instead of writing the parameter's referent as a dereference inside the row, a struct-field-only path grammar that cannot name heap content or one element, or signatures carrying index expressions a checker would have to re-evaluate in the callee's state.

Decision: A row lists no entry that another of its entries covers, a `writes` entry covering every entry at or below its path and a `reads` entry every `reads` entry below its path, so `reads(p.x)` beside `reads(p)`, and `reads(p)`, `reads(p.x)` and `writes(p.x)` beside `writes(p)`, are each an EFF-1 rejection at that entry, carrying the entry that covers it, because the covering entry already states every access the covered one states, so the covered entry is a second spelling of that statement and would give one body two admitted rows, and once a call no longer compares two entries one argument supplies that overlap whatever their positions are, only the declaration can refuse the redundant row, instead of refusing only entries at or below a `writes` entry, or admitting the redundant entry.

Decision: Contracts and invariants are erased proof syntax and introduce no effect, because a proof-only statement that changed a row would be observable, instead of proof statements contributing effects.

Decision: `pure` states that a function has no state effects and promises nothing about termination, because the language has no termination checker, and a promise the checker cannot verify would be a trusted theorem, instead of `pure` as totality.

Decision: Allocation and release carry no effect entry, no provider parameter, and no category of their own, because there is one heap supplied by the trusted base and its addresses are not observable, so an allocation tells a caller nothing about storage the caller can reach and constrains no ordering, instead of provider parameters named in an `allocates` category or an ambient-heap exemption beside branded stores.

Decision: A callee's declared `writes`, after its paths are substituted with the actual argument paths at the call, kills exactly the caller facts whose storage support overlaps those paths and applies the ordinary storage-validity rule to every live reference, including actual arguments, before the callee's verified `ensures` publishes replacement facts, because preserving a fact across a write to its support is unsound and argument membership cannot keep removed storage alive, while killing anything the write cannot reach destroys modular proofs, instead of killing by the syntax of an actual argument, killing the whole argument, exempting every actual reference, or leaving an unknown replacement unchanged.

Decision: Effect rows in public declarations, in function-kind formals and in code outside the declaring module name only accessible paths, and a public operation whose body writes private state declares the nearest accessible path covering it, with EFF-2 exactness unchanged, because one visibility rule serves every role and EFF-2 already counts a declared entry as exhibited by any access at or below its path, while an interface that needs finer independence publishes the finer field, instead of rows naming private fields, named footprint regions or upper-bound rows.

Decision: Mentioning a field in a proof or effect annotation grants no exhibited runtime access and creates no scheduling edge, because proof support determines fact validity while body operations determine effects, instead of using proof mentions to justify a padded row or treating permission to describe a path as permission to execute it; the existing pure and no-termination-promise decision remains unchanged.

Rejected:
- Rows as upper bounds that a padded declaration may overstate: rejected because a row a caller cannot read exactly is not a boundary, and unexhibited entries are a place to smuggle effects.
- Separate external, blocks, and traps effect categories: rejected because system resources are ordinary state under ownership and scheduling belongs to lowering, so the categories described mechanisms rather than state.
- Following owned values through locals, results, or replacements to derive additional effect roots: rejected because a by-value parameter carries no entry at all and reference paths with explicit contracts supply the complete callable boundary, while ancestry makes that boundary depend on implementation bodies.
- A dereference step inside an effect path, the form a row used to write when it named the storage a reference parameter refers to rather than the parameter: rejected because the root of every effect path is a reference parameter by rule, so the step told a reader nothing the root had not already told them, and one quantity may have only one spelling.
- A permission marker on a reference parameter, such as an exclusive or mutable mode, as the statement of whether a callee writes through it: rejected because the effect row already states that path by path, and a second statement of one fact can disagree with the first.
- Restrict call invalidation to live references outside the call: rejected because one actual's destructive ancestor write can remove the storage selected by another unused actual, as tests/conformance/cases/ref2-neg-wildcard-ancestor-call.wf demonstrates; content writes at or below the captured target retain ordinary preservation under spec/kernel-spec.md REF-2 and EFF-5.
- The named footprint proposal: rejected because the published field states the precise path directly; a named region would only keep client rows unchanged when a published representation changes, which the module goals do not require.
- Refusing only the same-path pair `reads(p), writes(p)`: rejected because `reads(p.x)` and `writes(p.x)` beside `writes(p)` are just as redundant, and after the call-site exemption for one argument's always-overlapping entries nothing else refuses them, so one body would have several admitted rows.
- Admitting a read below another read, such as `reads(stats), reads(stats.count)`: rejected because the body then has two admitted rows, the longer one and `reads(stats)`, where FORM-1 asks for one spelling, even though the redundant read costs callers nothing.
- Placing the rejection at the covering entry or at the whole row: rejected because the redundant entry is the one the writer deletes, so its own position together with the entry that covers it locates the repair in one step.
