Decision: Every required source fact is machine-checked before acceptance and erased before lowering, with no writer-accessible unsafe, trusted theorem, or runtime trap of any kind, because any writer-reachable escape becomes an unauditable failure edge in generated code, instead of Rust-style unsafe policed by convention or panics admitted as a language feature.

Decision: Compilation and proof checking never require work that grows exponentially with program or written-proof size, because the target projects must stay practical to iterate on and guaranteed termination alone does not make a checker usable, instead of admitting exponential families and relying on timeouts or budgets to keep them practical.

Decision: An accepted program has one observable behavior, fixed by the language: no build mode, compiler flag, optimization choice, or backend changes what it does, and whatever the compiler hands its backend, such as aliasing attributes or inlining, is an implementation detail the language never sees, because a source that behaves one way when checked and another way when built, as a debug build and a release build that differ on integer overflow do, means the program that was checked is not the program that runs, instead of build modes or switches that trade behavior for speed.

Decision: Every fact the checker has proved may be supplied to the backend, as target attributes, instruction flags, metadata, or assumptions, namely the places one call's substituted effect row proves disjoint, the places a permitted adjacency or loop proves independent, a reference's validity and extent, a discharged subscript bound, and a discharged integer-domain obligation, the last being what licenses a no-wrap flag on an exact operation, while a supplied fact adds no runtime branch, no lock, no dependency, and no scheduling edge to the emitted program, its absence changes no source verdict and no emitted behavior, only a fact the checker has actually discharged may be supplied, never one a writer states, and the supply authorizes no second lowering path and no alternate acceptance, which of the permitted facts a compiler emits and in what form being that compiler's own decision, because correctness comes first and performance is pursued on top of it, and a fact the checker has proved is correct to state in whatever form the backend reads, instead of confining the supply to disjointness and independence facts stated as attributes and metadata and forbidding an assumption, which withheld from the optimizer facts whose truth the checker had already established.

Decision: The specification stands on its own and the design tree carries the reasons, with no index or ledger connecting rules to their grounds, because the tree already records each decision with its reason and refused alternatives, and a second record that nothing consumes drifts, instead of a rule-to-ground ledger the specification requires.

Decision: A language choice is made on its merits and not on cost, on the current corpus, or on how writers fare today: before real project adoption the cost of migrating existing designs is not a ground, the tests and small programs on hand are not evidence of how often anything occurs in real use, the effort a change would take is not a reason to make or refuse it, and a trial in which a model writes programs under some assistance describes that model and that assistance rather than a ceiling on the language, because there are no users to migrate, the corpus was written to exercise the compiler rather than to represent real programs, and the language deliberately trades human writing convenience for performance and checked correctness, instead of compatibility-driven, corpus-driven, or convenience-driven design.

Decision: A program is a closed, explicitly selected graph of interface-defined source modules with independently checked components, and final composition requires a verified implementation for every imported claim and required concrete instance while preserving the ordinary ownership, effect, contract and finite-proof rules, because large projects need separately checked modules with incremental and parallel builds, the planned workflow has an architect agent writing module interfaces while implementer agents write module bodies in parallel, and the [modular-compilation design](../research/investigations/modular-compilation/DESIGN.md) separates a checked callable boundary from its current implementation evidence so that unchanged proof work is reusable without introducing an assumed contract, instead of requiring every source file and derivation to belong to one freshly checked compilation unit.

Decision: A module's source verdict depends only on its own interface and implementation files, the graph, the prelude and the interfaces of its dependencies, while the judgments that read other modules' bodies, concrete instances of their templates and target requirements such as no-heap, belong to composition and are reported at the source that causes the failure, because an implementer must be able to verify a module while its dependencies are still being implemented, and an edit to one module's implementation must not change another module's verdict or hand its failure to another module's implementer, instead of checking each module only together with its dependencies' bodies.

Decision: One project-root graph file is the sole source of declared module dependencies, with each canonical module appearing once and listing only earlier modules as direct dependencies for both its interface and implementation, because explicit adjacency plus strict declaration-position descent makes the DAG inspectable and locally checkable while graph edits leave namespace paths unchanged, instead of ordered namespace subtrees, distributed ranks, repeated source import lists or unordered edges followed by cycle detection.

Decision: The sole active graph file's directory is the primary source root, and named entries, written with the existing entry and no_heap words, pair a public ordinary entry function with its environment requirements including optional no-heap, while all entries share one namespace inventory and dependency architecture, because a heap-free kernel and heap-using tools must reuse libraries without duplicating their graph or imposing one program's environment on another, the graph already locates its own root, and reusing existing words keeps common binding names such as target available, instead of a user-named local root binding, a graph-wide heap mode, one graph per executable, working-directory root search, implicit main selection or a new graph-only keyword.

Decision: Cached and fresh compilation establish the same specified judgments through one checker, with modular proof publication retaining the existing recursive-component restrictions and complete current dependency validation, because an implementation edit can change summary availability without changing a signature and a cache must not authorize a circular proof, instead of treating imported declarations or previously successful cache entries as independent fact sources.

Decision: A recoverable failure is an ordinary Result or Option value dispatched by match and forwarded by propagate, with no exception, unwinding, panic, or resumable effect handler, because a second control mechanism would duplicate what those values already express and add non-local control flow the proof system would have to model, while the language's effect rows describe state and not control, instead of exceptions or algebraic effect handlers that resume.

Decision: The specification's worked example is normative, byte-exact canonical form, because everything that appears in the specification is part of the specification, instead of an informative illustration beside the rules.

Decision: The specification states every normative fact exactly once, every other mention being a cross-reference by rule id, and no rule carries an exception clause, because an exception clause or a restated fact is a second statement of one thing that can drift from the first, and one statement per fact is what lets a reader and a checker hold the specification as one record, instead of except-when carve-outs and local restatements for standalone readability.

Decision: The specification fixes a rejection's rule, location and payload, states which rejections carry a repair (those whose rule says so, including every goal consumer of [MSR-4] and the reject-when-unsure rejections of [OWN-8]), and requires of every alternative a repair names that, carried out as it directs, it lets the rejected judgment succeed at that construct in a state that is not contradictory, that it states any condition the checker has neither established nor refuted on which that success depends, and that it writes nothing a rule rejects where it is written or at any use of it, leaving the words to the toolchain [DIAG-1], because a repair's words change no acceptance, because on main the prescribed and printed repairs differed at twenty-two of the forty-two reachable prescriptions while no check reads either, because a goal over computed values has proof routes (a certificate of `use` steps, a callee relation) that succeed only when facts the checker cannot guess exist, so an unconditional success requirement would forbid the routes a writer needs most, and because in the probes of the [repair-wording investigation](../research/investigations/repair-wording/DESIGN.md#2-disposition-and-literal-application) the repairs that compiled in one round were the ones fitted to the case in hand, which a fixed sentence cannot name; that last ground is provisional, observed on minimal programs with one compiler, and reopens if the investigation's writer trial shows fixed words repairing faster, instead of prescribing each rule's repair sentence.
