Node: compiler/waiting-contexts/deadlines

Decision: Each driver keeps the contexts waiting on it with a deadline in a binary heap on the deadline's instant, bounds every park and poll by the earliest one, and looks at the heap when it reaps: it completes a sleep, completes a readiness wait it polls itself with nothing transferred, and asks the route that holds any other operation to cancel it, because a parked context's operation belongs to its driver and only that driver's thread touches its parked contexts, so the heap needs no lock ([design](../../../research/investigations/io-model/TIME-AND-FILES.md#one-timer-queue-per-driver)), instead of one timer thread for the program or a linked timeout on each ring entry.

Decision: A cancellation goes through the route that holds the operation: an asynchronous cancel on the Linux ring, `CancelIoEx` on the Windows port, and an interruption of the helper executing it, a signal installed without restart on POSIX and `CancelSynchronousIo` on Windows, repeated each millisecond until the operation completes, with a helper's Windows accept instead waiting for its listener in bounded polls, which `CancelSynchronousIo` does not end; an operation whose own outcome came first completes with it, because each route already reports a cancelled operation as a completion that transferred nothing, instead of polling for readiness before every blocking call, which a standard stream shared with other processes can defeat by being read between the poll and the call.

Decision: A body hands its deadline to the submit, and an operation with a deadline is never made on the driver thread: a socket transfer or accept waits for readiness even before any other context runs, and any other operation goes to the helpers, because the driver thread is the one that must end it, instead of arming the deadline after the operation was routed, which left such an operation blocking the only thread that could cancel it.

Rejected:
- One timer thread for the whole program: rejected because every expiry would cross to the driver that owns the waiting context, whose own loop already wakes at the earliest instant it is given.
- A linked timeout on each ring entry: rejected because the readiness and helper routes need the driver's bound anyway, so the ring would carry a second mechanism for the same deadline.
- Polling for readiness before each blocking helper call: rejected because a standard stream shared with other processes can be ready at the poll and empty at the call, which then blocks past the deadline.
