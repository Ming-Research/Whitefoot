Node: compiler/payload-enum-layout

Decision: An enum with at least two payload-carrying variants whose product representation does not return in registers under compiler/result-registers is laid out as a union: an `i32` tag, and each variant laid out on its own as the sequence of that tag and its fields in declaration order, the value sized and aligned for the largest and most aligned variant, because the specification fixes only an upper layout ceiling [OP-9] and already treats payloads of different variants as one storage [OWN-7], this layout never exceeds the product layout, and the product layout multiplies storage by the number of payload variants, 168 against 40 bytes for Snowghost's `Component` and 228 against 12 for `IoError` in the [enum union layout investigation](../../research/investigations/enum-union-layout/DESIGN.md#3-measurements), instead of the product layout for every enum or one layout rule for every multi-payload enum. Tag-only enums keep compiler/tag-only-lowering, and an enum with one payload variant is unchanged because its product layout already is that variant's layout.

Decision: A union-laid-out enum is a memory-only value in the backend: its payload fields are read and written with their own types through per-variant view types, whole values of it and of any aggregate containing it move by memmove, calls pass it by address and return it through the destination, and its release helper takes its address, because LLVM has no union type and every first-class carrier copies element by element, moves pointers and padding through integers, or reads a one-bit leaf through a type it was not stored with, instead of a byte or word carrier aggregate.

Rejected:
- A payload area at one offset after the tag, as a C union of payload structs places it: rejected because aligning every payload to the most aligned one can exceed the product layout and the OP-9 ceiling, so target qualification would fail on accepted programs.
- Union layout with a first-class word carrier for enums that return in registers: rejected because it saves at most 8 bytes on the register-sized instances of the maintained programs while packing leaves into integer words, which compiler/result-registers refused; reconsider for a workload that stores many small two-payload enums.
- Union layout with a destination for every multi-payload enum: rejected because it would return today's register-returned results through memory, undoing the measured gain of compiler/result-registers.
- Boxing large variants or restructuring interfaces in the writer's source as the general remedy: rejected because under the product layout every variant keeps its own storage, so boxing still sums one pointer per variant, and a per-library restructure cannot serve a component list, a DOM and an error enum with different payloads. This differs from the HashMap's refused universal compact-enum ABI, which was inferred from result timings; this choice rests on storage size in a consumer where layout dominates memory.
