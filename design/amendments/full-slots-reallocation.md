Decision: Reevaluate payload `realloc` for `grow` when an inline runtime-capacity Slots owner is full and has positive element extent, retaining initialized-prefix allocation/copy/free for partial positive-extent windows, because the direct append comparison exposes material growth costs and the Rust control can resize its allocation without an explicit old-prefix copy, instead of applying whole-block reallocation to partly filled storage and potentially copying unused capacity. The live storage-representation node records this provisional work-branch choice; it remains unapproved. The inline descriptor and payload-only allocation differ from the previously rejected header-first candidate, so that result remains adverse evidence without deciding the new layout.

Boundary: OP-10 already permits in-place reallocation and STOR-7 permits byte relocation. The resize policy does not change source acceptance, target size/alignment obligations, the length and capacity contract, or reference invalidation. The separate representation amendment selects an inline three-word owner and payload-only allocation. Zero physical extent follows the uniform allocation-free representation in STOR-1; growth to a positive extent allocates fresh storage, while zero-to-zero growth changes only owner metadata. Failure reaches the existing resource-exhaustion floor before a null pointer can be published. Success uses the returned block, preserves initialized values without releasing them, updates capacity and the owner slot, and leaves their eventual cleanup unchanged. Every producer of this representation must use the compatible target allocator family.

Ground: The [single-append growth comparison](../../research/experiments/container-representation/vector-library/RESULTS.md#append-that-triggers-growth-correctness-and-native-checkpoint) inspects actual optimized native code and independently checks contents, capacities and allocation accounting. WF grows by allocating a header-first block, copying the initialized payload and freeing the old block; Rust uses its allocator's reallocation path. Both construct the offered value in its final slot. Two retained baseline launches expose large WF losses at the larger matched capacities. One Rust cell exceeds the registered drift threshold, so the baseline is not a globally qualified performance conclusion. These observations motivate testing the allocator path; they do not prove that reallocation, header layout or any single factor explains the entire gap.

Criterion: Before timing, native code must show the full path reaching reallocation without a separate prefix copy/free, while the partial path retains the previous route. Independent allocator tests must force both same-address and moved reallocation, verify the complete preserved values and cleanup, and exercise the failure publication boundary and partial fallback. Keep zero-size and nested-owner behavior correct. Compare actual compiler outputs with the retained API harness, identical capacities, payloads and fixed work budgets, both peers, both cohorts and paired before/after launches; retain all adverse samples and raw controls. Report duration and stability qualification before claiming a gain. A candidate is not completion of append: all meaningful append cells, including the spare path under the repaired clock, must satisfy the owner's peer target before append is qualified. Other APIs require their own comparisons; whole-Vector qualification requires every API to pass. A loss or inconclusive cell remains visible and requires further work, not a changed workload or threshold.
