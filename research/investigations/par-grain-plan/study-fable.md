# How `--par` should decide what to hand out, and how much

Checkout read: `wfmain` at `81010e578da238a231cc790ee57c2883620545ff`. Literature is cited from memory; where I am unsure of a detail I say so. "Inference" marks my own conclusions.

## 1. Recommended direction, and the alternatives rejected

### The direction: demand-gated lazy actualization with a learned per-site price

One decision procedure, applied at every *promotion-ready point* (a PAR-1 group fork site, a slice boundary of a PAR-2 range, the entry and the cut of a budgeted recursion), with four gates in order of cost:

1. **Shape (compile time).** The static price stays, but it is used in two ways it is not used today: as an *upper bound* for pruning, and as the *initial* price for the runtime. A site whose provable maximum work is below the floor emits no decision at all: constant or checker-bounded spans times a loop-free, call-free body (the checker's OP-4/REF-4 extent facts are what make this provable more often than in other compilers). Every other site gets a pure, hoistable floor test `span * weight * scale >= kappa` (arithmetic on a compile-time constant and one loaded word, no call), so LLVM can fold or hoist it. This replaces the opaque `wf__par_split_budget` call at loop entry (`compiler/src/backend/emitter/parallel.rs:829-835`) and the call-grain threshold's role as a point estimate (`compiler/src/lowering/builder/call_grain.rs:27,146`).
2. **Price (runtime, learned).** Each site owns one cache line of protocol-private state: `scale` (measured nanoseconds per estimated work unit, a word), a sampling countdown, and the last measured task size. The *shape* comes from the compiler; the *constant* comes from measurement: a thief that runs a stolen task brackets it with two clock reads (it is otherwise idle, so this costs no wall time) and writes the ratio; the owner samples an inline run with exponential backoff (entry 1, 2, 4, ... up to one in 1,024). The floor is in real time: kappa, nominally 20-50 microseconds, one process-wide constant.
3. **Demand (runtime, cheap).** Work is handed out only when an idle lane has asked for it. A thief whose scan found nothing writes a request hint into the victim lane (write only if zero, so the owner's line is invalidated at most once per outstanding request); the owner reads its own hint word at promotion-ready points (one load and branch, normally an L1 hit). No idle lane, no hand-out, no deque traffic. This is receiver-initiated stealing in the sense of Acar, Chargueraud and Rainey (PPoPP 2013, private deques) and lazy task creation (Mohr, Kranz, Halstead 1990), but the transfer itself keeps today's Chase-Lev deque (`design/compiler/parallel-lowering/parallel-runtime.md:1`): the owner's response to a request is an ordinary publish, and any thief may take it. Java fork/join's "surplus queued task count" rule (Lea) and the current runtime's own "zero budget when the lane already has local work" test (`compiler/src/backend/sched/core.c:1408-1415`) are weaker versions of the same gate.
4. **Rate (runtime, rare).** For the two events whose cost is not bounded by the price gate, a per-lane clock rule: a *cut refresh* in a recursion and a *wake* of a parked worker happen at most once per H per lane (H nominally 50-100 microseconds). The clock is read only at those events, never on the inline path.

Loops change from recursive bisection with a log2 allowance (`core.c:1398-1437`, `compiler/src/lowering/builder/split.rs:1085-1296`) to an **iterative slice driver**: the leaf is still the unchanged chunk loop (keeping `design/compiler/parallel-lowering.md:1`), called on successive slices of about kappa_slice (nominally 5 microseconds, converted to iterations by `weight * scale`); at each slice boundary the driver polls the hint and, when asked and `remaining * weight * scale >= kappa`, hands out the far half of what remains as another driver task. Slices grow geometrically while `scale` is still unknown, so a first execution with a wrong static price wastes O(log(error)) tiny slices and nothing more. When a site passes the floor and an idle lane exists at entry, the driver may also seed ceil(log2(P)) far halves eagerly before slicing ("demand-gated eager seeding"), which keeps today's ramp at a cost of about log2(P) * 10 ns per qualifying entry. This is lazy binary splitting (Tzannes, Caragea, Barua, Vishkin, PPoPP 2010) with Rayon's "split further only when stolen" adaptivity and TBB's auto_partitioner geometric growth, gated by the price.

Recursion keeps the budget-carrying variant and the sequential clone below the cut (`design/compiler/parallel-lowering/two-worlds.md:7,9`), because a compare per node above the cut and nothing below is the only known way to hold fine recursion (fib-like nodes of a few nanoseconds) inside 2 percent. Three changes: a group call hands out only on request (the refused edge, an ordinary call, is already emitted; `parallel.rs:683-715`); a stolen task starts with a *fresh* budget (the thunk already carries a budget field, `parallel.rs:643-668`, so this is a value change), so depth follows where work actually moved; and at a cut node with a request pending the budget is refreshed instead of entering the clone, at most once per H per lane, clock sampled one node in 64. The component's root entry is a site like any other, so a recursion whose whole entry measures below kappa enters the clone directly on later entries (this is what the 13,600-node directory descents of `research/investigations/recursive-offer-grain` needed).

Topology: default lanes = physical cores, not logical CPUs (new primitive beside `wf_prim_online_cpus`, `compiler/src/backend/sched/prim_host.c:89`); the idle window's admission test uses the same count; compute lanes above online CPUs are clamped (compute tasks never wait, `spec/kernel-spec.md:2236`, so oversubscription buys nothing); efficiency cores stay lanes, because fixed-time slices bound what a slow lane can hold to one slice and lazy splitting leaves its remainder stealable.

All of this is protocol-private state in the sense of `parallel-lowering.md:3`; the schedule is unobservable by `spec/kernel-spec.md:2164,2216`, and PAR-2 admits any combination tree (`spec/kernel-spec.md:2209`), so cutting a range at arbitrary points, any number of times, in any order is semantically free. Nothing is added to the sequential world. One IR actualization pass should own all four gates and the ledger (the backlog's own proposal, `docs/todo.md` "Parallel actualization is decided during translation"), which is what criterion 5 asks for.

### Alternatives seriously considered

**A. Heartbeat scheduling** (Acar, Chargueraud, Muller, Rainey, PLDI 2018; TPAL, Rainey et al., PLDI 2021; the software-polled compiler variant, Su, Rainey et al., ASPLOS 2024, title and author list from memory). Its theorem is exactly what H1 asks for: promotions at most once per H of *measured* work, so overhead at most tau/H with no dependence on any estimate. Rejected as the primary mechanism for three reasons. (i) The interrupt-based form needs a timer and a signal into the running thread, which the weak-target criterion excludes and which would land inside I/O driver code in firn-shaped processes. (ii) The software-polled form pays a decrement and branch at every fork; on a fine recursion that is 10-20 percent of a 5 ns node, so H1 fails where the two-worlds cut succeeds today. (iii) Its span inflation (a parallel task waits up to H before promotion, and a doubling ramp takes log2(P) * H) costs H2 for regions of 100 microseconds to a few milliseconds at 24-32 lanes. The idea survives in gate 4: the two events whose cost is not price-bounded are amortized against the lane's measured time. This also answers the earlier rejection of a heartbeat gate in `parallel-runtime.md:22`: that gate rate-limited *promotion*; mine rate-limits only cut refreshes and wakes, and leaves the coarse ceiling to the price gate and the skew shape to lazy splitting.

**B. A stronger static or profile-guided cost model** (captured extents as today, plus PGO from recorded runs, `docs/ideas.md` "Parallel grain policies and runtime profiles"). Rejected because H1 is stated over *every input* and a profile is a statement about the inputs it saw; the chain-pull regression (price 168 -> 60, affordable chunks 4 -> 1, W2 51 percent slower, history row of September 13) is what happens when a more literal estimate removes a split. Static shape stays, but only as an upper bound for pruning and as the first guess for the learned constant.

**C. Oracle-guided granularity control in full** (Acar, Chargueraud, Rainey, OOPSLA 2011; Acar, Aksenov, Chargueraud, Rainey, PPoPP 2019, "Provably and practically efficient granularity control"). Largely *adopted* as gate 2: the compiler supplies the cost function's shape and the runtime learns its constant per site against a kappa in real time. Not adopted as the whole, because it has no answer for a busy host or for nested parallelism (it hands out whenever predicted size exceeds kappa whether anyone is idle or not), and because at a site whose body is a nanosecond it still charges a prediction per entry; the demand gate and compile-time pruning cover both.

Also considered and rejected as a whole: heartbeat-free eager work-first (Cilk-5, Frigo, Leiserson, Randall 1998) with a 5 ns fork, which fails H1 on fine recursion without a cut; and "stop publishing from a site judged unprofitable at run time", rejected at `parallel-lowering.md:56`. What changed for the latter: it charged every offer a site lookup (here the site state is a static cell, one load), it learned a publish/suppress toggle rather than a size (here the learned quantity is a scale that composes with the static shape), and it ran before any demand gate (here the common case of no idle lane never reaches the price). Run-to-run dependence of *which* offers are published already exists today through the lane-state test at `core.c:1408-1415`, and the specification makes the schedule unobservable.

## 2. H1: the bound

Costs below are per dynamic execution; constants from the repository where it has them.

- **Site statically pruned:** 0 instructions in both worlds. Covers constant-span loops below the floor (the 200M-call three-iteration loop of the October 9 attribution: emitted 108.1 ms at W1 and 1,074.7 at W4, direct chunk 108.0/108.0) and calls to loop-free, call-free callees of bounded weight.
- **Site below the learned floor** (the common tiny site with a runtime span): one load of `scale`, a multiply into the already-emitted static price, compare, branch; about 1-2 ns, hoistable when the span is invariant in the enclosing loop. Plus the sampling countdown, under 1 ns. For comparison the removed query plus splitter entry measured about 4.8 ns per call (2.2 query, 2.7 splitter) and was not hoistable.
- **Site above the floor, nobody idle:** loops pay one slice-boundary poll (hint load, branch, chunk call) per kappa_slice of real work, about 5 ns per 5 microseconds, 0.1 percent; groups pay one hint load and branch and then run both members as ordinary calls (the existing refused edge); budgeted recursions pay the existing compare per node above the cut plus the hint load.
- **A hand-out:** owner side, acquire plus frame stores plus publish, about 10-20 ns (the deque's measured per-fork excess is 4.80 ns, `research/investigations/proof-derived-parallelism/gap-hunt-findings.md`, plus the capture stores of a 256-byte frame at most), and at the join either a pop (task not taken) or a wait of at most steal latency plus the task's remaining time. Thief side, about 0.2-1 microsecond including cache misses and the 50 ns timing pair, which is not wall time.
- **The rule that keeps hand-outs rare:** a hand-out needs (a) a pending request, so the taker is idle and its cost is off the critical path; (b) `remaining * weight * scale >= kappa`, so the piece moved is about half the remainder, at least kappa/2 of measured-average work; (c) at most one per promotion-ready point. For loops, the owner keeps slicing, so the join wait is at most one slice. Count: hand-outs are at most requests served, at most steals, and the Blumofe-Leiserson bound (JACM 1999) puts expected steals at O(P * T_infinity / tau); for a flat range T_infinity is a slice times log2(n), so a 10^8-element loop at P=32 hands out on the order of a thousand pieces, about 20 microseconds of owner time against at least 100 ms of work.
- **Waste ratio, independent of the static estimate:** once a site's `scale` has converged (one to three samples), its hand-outs happen only when its *measured average* entry is at least kappa, so owner-side waste over a site's lifetime is at most (publish + steal latency) / kappa = (0.02 + 0.3) microseconds / 20 microseconds = 1.6 percent in the worst mixture of tiny and large entries, falling with larger kappa (0.6 percent at 50). This is the central H1 argument: the bound is on the ratio of a constant per-event cost to a *measured* floor, not to an estimated one.
- **When the static estimate is wrong by a factor F:** the upper bound used for pruning is never wrong (a loop with an unknown extent is unbounded and is not pruned). The initial price is wrong by F for at most the first sampled executions of that site in a process: an over-estimate causes at most a few bad hand-outs (each at most 0.3 microseconds) and, during a first entry with unknown scale, O(log2 F) tiny slices; an under-estimate costs no time at all, only speedup on the first entry until a sample corrects it. After that F is absorbed into `scale`. What the learned scale cannot absorb is variance *within* a site (the 10^4:1 spread); that is exactly the case the waste-ratio bound above covers, because the average is what is learned. Residual: a host with no monotonic clock keeps `scale` at its nominal value, and the bound degrades to F times the ratio above; this is the weak-target residual and must be stated in the design node.
- **Rate-bounded events:** a cut refresh costs up to 2^b node polls (about 0.25 microseconds at b = 8) plus one hand-out, at most once per H per lane: at H = 50 microseconds under 2.5 percent, at 100 under 1.3. A wake costs the owner one signal (1-2 microseconds) and burns one lane's idle window; at most once per H_wake = 1 ms per lane, so under 0.2 percent of wall and at most one spinning lane-millisecond per wake (criterion 2).
- **Fixed cost d:** pool start (lazy helpers, unchanged) and one cache line of site state per actualization site (tens of kilobytes for hundreds of sites).

## 3. H2: where near-reference speedup is reached, and where not

- **Flat counted loops** (mandelbrot, fir, records, prefix, histogram, stencil): the slice driver with demand-gated seeding is the same mechanism as the hand-tuned Rayon/OpenMP-guided reference, with the grain found by measurement instead of by hand; stragglers hold one slice; indexed reductions get one private slab per hand-out instead of per power-of-two leaf, so fewer traversals (`parallel-lowering.md:27`). Expect 0.9 or better at sizes of at least P * kappa. Below that size the speedup is capped at about (region time)/kappa: at kappa = 20 microseconds and 24 lanes on the 14900K, regions under about 0.5 ms do not reach full width, and a reference tuned to a 1-microsecond grain will beat the 0.8 line there. This is the honest H2 cost of the H1 floor; kappa is the knob and the suite should sweep it once.
- **Balanced recursion** (quadrature, merge sort, quicksort): unchanged mechanism, where the budget variant already read 1.017 of the best reference at budget 8 (`core.c` comment above `WF_PAR_RECURSION_LEAVES_PER_LANE`); per-steal refresh removes the end-of-run imbalance of a fixed leaf count at wide pools.
- **Skewed recursion** (apollo11 shape B, 1.14x at W4 today against 3.7-3.8 with the budget off): a stolen heavy child gets a fresh budget, and the owner's inline descent into a heavy child refreshes at the cut when a lane is asking. Expect most of the frontier-off gain without scatter's 30-37 percent loss, because refreshes happen only on demand and at a bounded rate. Inference, to be measured: the remaining gap is the H delay before the owner's own heavy path splits, negligible at millisecond scale.
- **Deep spine with side leaves** (`tests/programs/parallel/spine.wf`): parallel only if leaves are heavy. Inference from `call_grain.rs:137-155`: today `leafval` is pruned by weight, the group dissolves, and the spine's component stops counting as offering, so nothing is offered. Under the direction a loop-free leaf is still pruned statically (correctly), while a leaf whose body has unknown extents becomes a measured site and is handed out when it measures heavy. Near-reference for heavy leaves; sequential for light ones, as the reference would be.
- **Bounded DAGs:** the round-join structure of PAR-1 groups is a lowering exposure question (bridges were withdrawn, `parallel-lowering.md:47`); the direction does not change it and will trail a futures-based reference. Classify as permission/lowering, not grain.
- **Data-dependent cost within a site:** lazy slicing is the known good answer (a straggler holds one slice; its remainder is stealable); the average-scale floor may leave a site sequential when most entries are tiny and a few are huge (99 tiny of 10 ns, 1 of 100 microseconds averages under kappa). That is a bounded H2 loss, not an H1 failure.
- **Memory-bandwidth-bound work:** speedup saturates at the bandwidth, and more lanes can be slower; the policy cannot see bandwidth. **Allocation-bound work** (`docs/todo.md` "Small allocations in a parallel loop slow down with more workers", 0.71 s sequential against 1.15 at W2): no grain decision fixes allocator contention; the only policy-side answer is a per-site learned *gain* (thief ns/unit versus owner ns/unit), which I propose as a later stage, with the allocator itself as the real fix.
- **Real programs:** Snowghost setup, style and edits are tiny-site-dominated and SMT-sensitive; gates 1 and 3 and the physical-core default address exactly those two findings (504/506/728 microseconds at W1/W2/W4 on the hosted runner). Halo stays sequential at no cost beyond gate 1's compare per site. firn's compute lanes beside I/O drivers: the demand gate means no hand-out when drivers hold the cores, but spinning lanes still compete; the lane default should subtract driver threads, a suite question.

## 4. Risks, and the first refuting experiment

Risks, in order of my concern:

1. **Ramp.** Lazy hand-out at slice boundaries may lose to today's eager log2(16P) bisection on mid-size regions; demand-gated seeding is meant to remove that, and the experiment below measures it.
2. **Request-hint traffic** at 24-64 lanes: thieves writing hints into victims' lines. Bounded by write-if-zero and by requesting one victim at a time; measure cache-miss counts on the 14900K.
3. **Learned-scale instability** under bimodal or shifting data; bounded for H1 by the waste-ratio argument, costs H2.
4. **Clock cost and availability**: 20-30 ns per `clock_gettime` via vDSO on Linux x86, cheaper on arm64; only on hand-outs and samples; weak targets without a clock fall back to the static price.
5. **Oversubscription and busy hosts:** a descheduled lane holding a private remainder blocks it until rescheduled; clamping lanes to CPUs removes the self-inflicted case, a busy host remains the worst class for any work-stealing runtime.
6. **Measurement confounds:** placement changed conclusions four times in the history; every cell needs its identical-image twin and the padding control already in `tests/performance/README.md`.
7. **Complexity:** more runtime state and a third kind of decision point. Mitigated by making the actualization pass the single owner and by a runtime ledger (`WF_SCHED_REPORT` extended to a per-site table: entries, inline, handed out, scale, measured bad hand-outs).

**First experiment** (refutes the direction's two premises, that demand gating costs nothing where it hands out nothing and that lazy hand-out matches eager bisection where it does). Build only: the request hint and demand gate at group fork sites and at split entry; static pruning of constant-span below-floor sites; a pure floor test using the *static* price (no learning yet); the slice driver with demand-gated seeding to log2(P). Leave the recursion budget and call grain as they are. Cells, each with its identical-image twin, interleaved rounds, on the 14900K at W1/2/4/8/16/24 and the hosted two-core SMT runner at W1/2/4: (a) the 200M-call three-iteration loop; (b) a synthetic group site of two 100 ns calls executed 10^6 times; (c) the six formal loop kernels against oneTBB and Rayon references at their recorded sizes; (d) a flat loop at region lengths 100 microseconds, 1 ms, 10 ms at W8 and W24; (e) a loop with 10^4:1 per-iteration spread; (f) quadrature as the null arm. Pass/fail fixed now: (a), (b) at every W within 1.02 of W1 plus twin spread; (c) no kernel at any W slower than the current runtime by more than twin spread, and at least 0.8 of the better reference at W8 and W24; (d) at 1 ms and 10 ms at least 0.8 of min(W, work/critical path), 100 microseconds reported not gated; (e) at W8 at least 0.8 of the reference; (f) within twin spread. Any failing gated cell after one rerun refutes the direction as built; a (c) failure specifically refutes the ramp premise and would send me to keep eager bisection to depth log2(16P) under the demand gate instead.

## 6. Keep, change, remove; backlog disposition

Keep: permission and lowering exposure as they are; two worlds and the sequential clone; the budget-carrying variant and its group-only spending; the Chase-Lev deques, 64 slots, 256-byte frames, join helping, newest-first joins; the leaf-is-the-loop decision; the static price machinery (`split.rs:1572-1619`, `work.rs`) as shape and upper bound; `--par-ledger`.

Change: the split-site query into a pure floor test plus the slice driver; the recursion budget's initial value per stolen task and its behaviour at the cut; the call grain from a point threshold into upper-bound pruning plus measured sites; the lane default and idle-window admission to physical cores; `WF_SCHED_REPORT` into a per-site table; `WF_SPLIT_WORK` into a diagnostic-build-only override, because a pure, foldable floor cannot read a process setting.

Remove: the power-of-two chunk allowance and the 16-per-lane cap; `--par-sequential-refusal` (the demand gate makes refusal-to-clone pointless, since a refused offer is now the common, free path); the October 9 direct-chunk candidate as a separate change (subsumed by pruning and the pure floor).

Backlog: **resolved by the direction** — coord-wfbl-03-27 (this is the dedicated study), 03-59 (call grain provisional), 03-58 (fixed budget on unbalanced trees), 03-54 (tiny loops pay the query), 03-60 (SMT spinning, by the lane default and the demand gate; attribution still to be measured), 03-28 and the point-estimate half of 03-29 (learned scale replaces missing extents on average). **Reduced but left** — the per-task heterogeneous-cost half of 03-29 (lazy slicing bounds stragglers; a per-task price is still not known at the split point), 03-30 (placement attribution becomes a suite rule rather than a code question), 03-61 (unbudgeted waiting components now cost one poll per node when nobody asks; the clone-less component mystery remains). **Left as separate lines** — 03-22, 03-25, 03-31, 03-55 (construction, DAG executor, packing, allocator), 03-23, 03-34 (chunk codegen), 03-32, 03-35, 03-48 (measurement), and every P item. **Moot** — further sweeps of the work unit or chunk cap, and the rejected 10,000 global floor (`parallel-runtime.md:20`): the floor is now a time learned per site.

## 7. What in `criteria.md` is wrong, missing or unmeasurable

1. **H1's 2 percent cannot be met by any runtime decision at a free loop.** A site with a runtime span whose body is a nanosecond cannot carry even one compare inside 2 percent of itself; the 200M-call case runs at about 0.5 ns per call. Either H1 allows a per-decision-point constant c (I propose T_W <= (1+e) T_seq + d + c * N, with N the dynamic count of decision points that hand nothing out and c <= 2 ns, measured), or it requires that every site with a provable static bound below the floor cost zero and admits c only for sites with unbounded spans. Otherwise every direction is refuted by the grid's "hundreds of millions of times, a few iterations each" row.
2. **"Counts above the number of cores" at 2 percent** is not a grain property; it is a scheduler property that no work-stealing runtime meets. Either clamp compute lanes to CPUs by design (then the clause is met by construction and should say so) or state a separate, softer bound for oversubscribed pools.
3. **"A busy host"** is unmeasurable at 2 percent: the competitor's own scheduling noise exceeds it. Define the load (for example half the cores pinned under a fixed burner), compare against the sequential build under the same load, and set e for that class from the twin spread.
4. **H2's hand-tuned reference** must be tuned once per kernel, not per input size, or it is an oracle that no automatic policy can approach at small sizes; say so, and add a *region-length* axis (100 microseconds, 1 ms, 10 ms) because that is where lazy and heartbeat designs lose and eager ones win.
5. **"Without a point where adding workers makes the program slower"** is false for bandwidth-bound kernels on some hosts; qualify it by twin spread and exclude bandwidth-saturated cells.
6. **Allocation-bound work** under H1 is an allocator question; a direction can only learn not to parallelize such a site. Make that an explicit allowed outcome, or the class refutes every direction.
7. **Secondary 3, "no timers":** distinguish a monotonic clock *read* at a hand-out (allowed, and needed for any estimate-independent bound) from a timer interrupt (excluded); and state the clockless fallback as a measured class on the one-core affinity stand-in.
8. **Secondary 1, "one set of constants":** online-learned state is not a per-program constant; the rule should say constants are fixed before the held-out half while learned state may vary per run, otherwise the owner's own asymmetric-core guard (`core.c:1232`) already violates it.
9. **Missing:** CPU efficiency for parallel work (CPU/wall against speedup), not only for programs without parallel work; memory for frames and private slabs; the noise floor per host recorded with each cell, with cells whose twin spread exceeds e marked inconclusive rather than passed; and a *regime-change* row in the grid (the same site alternating between tiny and large entries), which is the one data-dependence pattern that defeats a learned average.
10. **The suite as prerequisite is right**, and S1 above is deliberately runnable on the existing kernels before the generator exists, so the first refutation does not wait for the suite.
