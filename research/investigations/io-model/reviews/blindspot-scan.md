# I/O foundation completeness audit

Assume two future monotonic clock samples. The following is illustrative, not a currently compilable interface:

```wf
let t1 = clock_sample(clock: &'c clock);
let t2 = clock_sample(clock: &'c clock);
```

The design classifies clock as an ordinary world read, and is prepared to allow `read/read` overlap. [DESIGN §3b](</research/investigations/io-model/DESIGN.md:123>). If the world services the second request first, the program can get `t2 < t1`, a result that does not correspond to source-order sequential execution on a single monotonic timeline.

This exposes a core gap: the current design has found a runtime shape for submission and completion, but has not yet defined external history, dynamic capability, process lifecycle, and failure boundaries. The conclusion is 10 `BLOCKING`, 18 `STRUCTURAL`, and 4 `DISTANT` items.

I did not recount the cancellation, partial completion, timeout, backpressure, and own-mode region representation already registered in §9. The clock section discusses only clock domains and event ordering; the termination section discusses process death, not writer cancellation. The capability alias, cross-region fence, and 10k server limit already mentioned by the design are likewise not recounted as new findings.

## BLOCKING: must be answered before any spec batch

| ID | Specific question | Why it bites | Existing design under pressure | Compatible direction |
|---|---|---|---|---|
| B1 | Must every completion correspond to a prior submit? | `SIGTERM`, device hot-unplug, and file-change notifications can arrive with no frame pre-armed; a child process can also exit before `wait`. | §1 compresses the world into submit/complete, while §4 assumes the SQE carries a pre-allocated frame pointer. [DESIGN §1](</research/investigations/io-model/DESIGN.md:28>) [DESIGN §4](</research/investigations/io-model/DESIGN.md:162>) | Add a compiler-owned event-source contract that specifies arm, pending, coalescing, drop, and fatal behavior. The writer still only calls ordinary operations and gains no async handler or scheduling construct. |
| B2 | What is the equivalence relation for world `reads`? | Two stdin, clock, entropy, or listener reads can consume order, sampling order, or a dynamic set. `read/read` is not guaranteed to be commutative. | "moving world races sequential execution too" is not enough to justify overlap; the current spec instead explicitly treats a read that advances the file cursor as a state write. [DESIGN §3c](</research/investigations/io-model/DESIGN.md:136>) [SYS-11](</spec/kernel-spec.md:2602>) | Each family declares external history and a linearization rule. By default, consuming, sampling, and mint operations write to a hidden sequence region; only snapshot reads formally proved idempotent and commutative use shared `reads`. |
| B3 | How should capability output express fresh, alias, subregion, and multi-parent origin? | `accept` dynamically produces a connection; `rename` modifies two directories at once; two opens can point at the same object; stdout and stderr are two owners that can nonetheless be redirected to the same sink. [SYS-12](</spec/kernel-spec.md:2613>) | "one world-region identity per capability" covers only one-to-one relations. Even once §9's own-mode representation is settled, there is still no fresh or composite-origin relation. | The system declaration records a hidden origin graph: `fresh`, `aliases`, resource projections, multi-input footprints. Unproven separateness conflicts conservatively by default, and the writer does not see these identities. |
| B4 | What is the precise state machine for frame and completion? | A late or duplicate CQE can hit an already-reused frame, producing ABA; DMA has written memory but the CPU can still read a stale cache line after the flag; two completers might publish results at the same time. | §4 only writes "frame pointer" and "completion is a flag flip". [DESIGN §4](</research/investigations/io-model/DESIGN.md:162>) | Fix a `created → published → world-owned → completed → joined → reusable` state machine, adding a generation-tagged operation ID, an exactly-once terminal transition, and release/acquire publication. Target qualification must prove this protocol. |
| B5 | What exactly does "completion" complete? | When a write completes, the buffer may already be safely reusable, yet the data is not yet visible to third parties, let alone durable; the implicit release from a pipe's last writer produces EOF; a queued connect is not the same as an established connection. | The design merges result, loan return, and flag flip into a single word; the current spec already requires a release policy for every resource, but the foundation has not folded release into the completion protocol. [SYS-5](</spec/kernel-spec.md:2434>) | Each semantic ID spells out submission linearization, world visibility, loan-release, terminal outcome, durability, and compiler-derived release. Implicit release also goes through the same operation contract. |
| B6 | How should world failure, program defect, TCB exhaustion, and target defect be triaged? | `ENOSPC` and `ECONNRESET` should be typed world outcomes; a local allocator refusal belongs to resource death; `EBADF` under an error state should be unrepresentable; a completion backend should not accidentally leak `WouldBlock` or `EINTR`. | The active spec has world values such as `IoError::ResourceExhausted` and `NoSpace`, [SYS-7](</spec/kernel-spec.md:2506>); 0079 is also preparing to define TCB exhaustion as a fourth class of fail-stop death. [0079 ERR-4 recipe](</docs/ongoing/0079-exhaustion-floor.md:894>) | Each operation row fixes a failure disposition: typed outcome, static obligation rejection, claim trap, TCB resource death, target/start failure. Classification follows semantic origin, not host errno names. |
| B7 | When a process dies, what happens to already-submitted external work and diagnostic records? | An async stderr write has already been submitted when another lane OOMs. Disk or terminal output can keep writing after the resource record, even interleaving with it. This conflict already exists without any cancellation API. | The 0079 recipe requires that no further program-external effect occur after exhaustion, [0079 SCOPE-3 recipe](</docs/ongoing/0079-exhaustion-floor.md:793>); yet the current `TRAP-1` allows already-started external work to keep its own semantics. [TRAP-1](</spec/kernel-spec.md:2395>) | Define a termination cut: nothing is submitted after the cut; operations already linearized before the cut either count as an accomplished effect or are isolated by the arbiter and confirmed quiescent. Trap/resource records use a control channel serialized with writer stderr. |
| B8 | Which root capabilities does a program kind get from the world, and how does it end? | The current `command` has no stdin; bare metal has no args, cwd, OS process status, or OS teardown; service additionally needs listener, clock, entropy, credentials. | The spec has only one `command main` and four inputs. [FN-7](</spec/kernel-spec.md:1180>) yet the design simultaneously claims the bare-metal contract has no OS dependency. [DESIGN §4](</research/investigations/io-model/DESIGN.md:183>) | First define program-kind-specific root capability tables and lifecycle contracts. `command.stdin` should be an explicit stateful capability; future firmware/service kinds use different closed tables, while still keeping one entry point and no ambient authority. |
| B9 | Before a Whitefoot OS exists, who guarantees capability authenticity, alias tracking, and revocation? | A POSIX descriptor can be aliased through duplication, inheritance, or redirection; at revocation the kernel can still hold DMA buffers and frames; an integer descriptor can also be reused. | §7 only says affine capability makes reclaim tractable, [DESIGN §7](</research/investigations/io-model/DESIGN.md:230>), but affine only constrains the Whitefoot value, not aliases and in-flight references inside the host. | Target qualification must declare a protection mechanism. Near-term options include process isolation, a generation-tagged handle table, or a globally conservative alias group; revocation first blocks new submits, then drains or quarantines late completions. |
| B10 | How should compiler-independent I/O conformance be written? | Live DNS, network, and clock make the verdict unstable; permission is also never an obligation, so a test cannot require "overlap to actually happen". | PAR-1 can only use annotation plus compiler/runtime evidence, because there is no source-to-verdict case. [0074 conformance boundary](</docs/done/0074-proof-derived-parallelism.md:94>) I/O additionally adds external results and ordering. | Establish three layers of evidence: a scripted deterministic world checks semantics and multiple completion schedules; target qualification checks the real backend; performance tests measure only actualization and are not language conformance. |

## STRUCTURAL: will shape the design, but can land family by family once the foundation is bounded

| ID | Specific question | Why it bites | Point under pressure | Compatible direction |
|---|---|---|---|---|
| S1 | What is each class of signal, respectively? | `SIGPIPE` is a write outcome, `SIGCHLD` is child lifecycle, `SIGINT` can be an event or a forced termination, `SIGSEGV/SIGBUS` is a TCB/floor issue. Unifying them into an interrupt completion would blur the semantics. | The design only says the ISR does not run writer code; the current spec concretely handles only SIGPIPE. [SYS-12](</spec/kernel-spec.md:2628>) | Build a signal classification table. A raw handler never enters the writer; SIGPIPE continues to belong to the operation result, SIGCHLD is absorbed by the Child capability, fatal faults stay in containment. |
| S2 | What is the ownership of `fork`, `exec`, spawn, wait, and exit code? | `fork` duplicates the affine Output, runtime locks, and in-flight frames; an in-place `exec` bypasses compiler-derived release; the child can exit normally, be killed by a signal, or undergo resource-death. | The current entry produces only a normal `ExitStatus`; abnormal termination has no status. [PROG-3](</spec/kernel-spec.md:1489>) | Do not offer a writer `fork` or in-place `exec`. Offer an atomic `spawn` that explicitly moves the child's inputs and returns a completion-required `Child`; `wait` is a completion and produces an independent `ChildOutcome`. |
| S3 | Who owns the two ends of a pipe, capability transfer, and cross-program ordering? | When two WF programs are connected, neither the producer nor the consumer owns the pipe's internal queue; the last writer's release produces EOF; bytes from multiple writers can interleave. | Per-program world regions cannot define cross-process ordering on their own. | The arbiter owns the pipe history; the programs separately own `PipeRx` and `PipeTx`. The resource contract fixes FIFO, EOF, and atomic-message boundaries; a cap transfer consumes the owner, and a failure outcome must return it. |
| S4 | Which region do create, rename, unlink, and delete write to? | `rename(A/x, B/y)` changes two directory namespaces at once, and can change the target object's link state; an already-open handle can survive after its name is deleted. | One capability per region cannot express a multi-directory namespace mutation. | Introduce a `DirectoryMut` or rights facet; create writes the parent directory and mints an object capability, rename writes the source and target namespaces, unlink writes the parent namespace. Each operation row lists the complete multi-region footprint. |
| S5 | Are file object, cursor, byte ranges, and metadata the same world region? | Four parallel `read_at` calls should not be serialized because of one cursor; yet two cursors can also point at the same file; the atomicity of parallel writes to different byte ranges varies by target. | The current `ReadFile` merges object and cursor into one stateful resource. [SYS-11](</spec/kernel-spec.md:2602>) | Distinguish the shared file object from the affine cursor. Positioned I/O gets a fine-grained footprint only when the target can prove byte-range semantics; otherwise it orders conservatively. |
| S6 | Can mmap, shared memory, and MMIO become ordinary Whitefoot memory? | After another process modifies a shared page, or a device modifies a status register, an ordinary load can be cached or hoisted by the optimizer, directly breaking T1 and the optimizer facts. | "external contact only through system operation" fails to hold for mapped memory; existing storage reserves `foreign_shared` only for gated FFI. [STOR-1](</spec/kernel-spec.md:638>) | An ordinary borrow never points at externally mutable storage. Initially allow only snapshot/read-only or arbiter-proved exclusive mapping; shared/MMIO goes through typed volatile/atomic operations or a D17-checked representation lane. |
| S7 | Which domains do monotonic clock, wall clock, timer, and deadline belong to? | NTP or manual clock adjustment can move the wall clock backward; instants from two different clocks are not comparable; when an operation and a deadline complete at the same time there must be a determinate winner. | §9 only names timeout as a completion, without defining clock identity or a comparison law. | Independent `MonotonicClock` and `WallClock` capabilities. A deadline accepts only an opaque instant from the same monotonic origin; the race winner is decided by arbiter linearization, not by worker scheduling. |
| S8 | How should entropy be separated from deterministic PRNG? | Two entropy draws cannot be freely commuted as shared reads; bare metal may have no qualified TRNG; record/replay turns the seed into sensitive material. | `external` already counts a random sequence as external state, but the foundation has not modeled it at all. [EFF-1](</spec/kernel-spec.md:1355>) | `Entropy` is an explicit stateful capability; a single seed acquisition is a world operation. Afterward, use owned local PRNG state, with ordinary ownership handling order. A target with no qualified entropy source fails at the qualification stage. |
| S9 | What are the state transitions and authority for bind, listen, connect, and accept? | accept consumes the listener backlog and dynamically mints a connection; bind modifies the network namespace; connect may need to return a builder state after failure. | "network writes across connections" only handles connections that already exist, and does not say where a connection comes from. [DESIGN §3c](</research/investigations/io-model/DESIGN.md:136>) | Use explicit `NetworkAuthority`, `Listener`, and connection type states. accept writes the listener sequence region and returns a fresh connection origin; every state transition of bind/listen/connect is fully expressed by the outcome type. |
| S10 | Do stream, full duplex, half-close, and datagram share one operation family? | A single socket region unnecessarily serializes read/write; allowing full overlap can instead scramble same-direction FIFO. Datagram also needs to preserve message boundary, source address, and truncation outcome. | Per-connection FIFO is too coarse. | Split stream into associated Rx/Tx facets, each direction ordered separately, with half-close as a consuming transition. Datagram uses an independent message outcome and never reuses the byte-stream cursor contract. |
| S11 | What are the authority, cache, and result ordering for DNS and service discovery? | A resolver reads configuration, network, clock, and cache; results contain multiple addresses and a TTL, and can change between two calls. | The design writes only network, with no resolver capability or variable-result ownership. | An explicit `Resolver` capability fixes configuration and authority; result ordering, TTL, and cache observation are written into the family contract. No ambient libc resolver. |
| S12 | Who owns the backing for variable-sized external results? | A DNS address set, peer identity, environment, and certificate chain cannot all fit into a fixed inline outcome. The current `HostString` also only allows argv-lifetime backing. | System operation currently declares "no allocation"; a new producer must adopt a new owned-backing type. [SYS-2](</spec/kernel-spec.md:2266>) [HOST-3](</spec/kernel-spec.md:2338>) | Uniformly choose either caller-provided buffers/cursors or an explicit owned backing resource. The backend must not implicitly allocate and hide the lifetime inside an opaque result. |
| S13 | How does the writer see an in-flight operation and overlap denial? | When a program hangs at join, all it currently sees is "not finished", with no way to know whether the operation was not yet submitted, is held by the world, lost its completion, or was conservatively denied by aliasing. | Compute already has `--par-ledger`; I/O has no sibling. | Add a compile-time `--io-ledger` that records site, origin graph, world footprints, grant/denial, and join. Also provide an opt-in runtime trace that uses a generation ID, records only metadata, uses an independent channel, and has zero semantic effect when off. |
| S14 | Is it worth naming deterministic record/replay now? | `WF_WORKERS=0` still reads live files, network, clock, and entropy, so it is not a complete deterministic reproduction anchor. [DESIGN §5](</research/investigations/io-model/DESIGN.md:193>) | "sequential/overlapped two worlds" conflates execution order with external world provenance. | Worth naming now as a recorded-world backend, but not as a third language-lowering path. The execution axis is sequential/overlapped; the world-provider axis is live/recorded; replay checks the submit trace and replays results, the mint graph, and completion order. |
| S15 | How do bare-metal ISR priority, nested interrupts, and an allocator-free mailbox satisfy the frame protocol? | A high-priority IRQ can interrupt a low-priority enqueue; an ISR cannot malloc or take an ordinary lock; the design simultaneously says bare metal needs an executor, and says `WF_WORKERS=0` is a zero-runtime embedded build. | Terminology conflict between [DESIGN bare metal](</research/investigations/io-model/DESIGN.md:183>) and [two worlds](</research/investigations/io-model/DESIGN.md:201>). | The target contract fixes ISR-safe acknowledgement, priority rules, an allocation-free intrusive mailbox, and atomics. `WF_WORKERS=0` should mean no overlap/worker pool, and should not mean there is no minimal I/O driver substrate. |
| S16 | Who is responsible for DMA buffer pinning, IOMMU, and cache coherency? | After the device completes a descriptor, if the cache has not yet been invalidated, join can still read stale bytes; moving a descriptor must not change the DMA address; a device may require alignment or contiguous pages. | "buffer on loan" only solves source ownership, not physical address and cache visibility. | Use a `DmaBuffer` family or a target-qualified hidden pin lease. Completion only release-publishes after DMA sync and cache maintenance finish; an ordinary buffer may be lent to a device only when the target can map it. |
| S17 | Is an operation guaranteed to eventually complete? | A peer that never sends is a legitimate wait; device removal should return a typed failure; a lost interrupt is a TCB defect. Without this distinction, a permanently stuck join cannot be attributed to a cause. | The scheduler only explains how to wait, with no progress contract. | Each family declares whether it may wait forever or eventually completes under stated environmental conditions. Device removal forces completion of all outstanding operations; lost completion is a target qualification/runtime defect. |
| S18 | How should visibility, durability, and crash consistency compose? | Data can be lost to a power loss after a file write succeeds; the directory entry can still be non-durable after `fsync(file)`; atomic replacement needs a stronger protocol than a cross-region fence during a crash. | The design treats fsync as an ordinary fence; the current Output already admits that a late writeback error can be lost. [SYS-12](</spec/kernel-spec.md:2623>) | Separate buffered, durable, and atomic-replacement resource families. The durability transition uses a completion-required owner and makes file versus directory durability explicit, without letting release imply commit. |

## DISTANT: name now and give re-entry conditions

| ID | Specific question | Why it bites | Point under pressure | Compatible direction |
|---|---|---|---|---|
| D1 | Should TLS sit in the system family or in an ordinary library? | A handshake simultaneously needs stream, entropy, wall time, trust store, credentials, and multi-round protocol state; making it a socket flag would hide all authority. | The existing single-capability, single-operation completion shape is insufficient. | Stop at the naming level for now. Once stream facets, clock, entropy, and owned bytes have landed, first try an ordinary checked library; leave only hardware keys or the OS credential store as a capability-backed primitive. |
| D2 | How should terminal, console mode, and device control avoid a generic `ioctl` escape hatch? | Resize, raw mode, color, serial baud, and device-private commands are not ordinary byte streams; a generic integer opcode would bypass semantic-ID review. | The spec already states that terminal control is an undeclared, independent capability. [SYS-12](</spec/kernel-spec.md:2630>) | Establish a typed capability and closed semantic IDs for each control plane. No generic ioctl, untyped property bag, or raw descriptor. |
| D3 | Are cross-program lock, lease, and coordination memory ownership or I/O? | Two programs need a leader lease or a file lock; after the holder dies, the arbiter must reclaim it, and an ordinary `&uniq` cannot express an external competitor. | Local ownership does not cover another program. | Treat acquire as a world completion whose success mints an affine lease capability; release, expiry, revocation, and owner death are defined by the arbiter contract, without exposing shared mutex memory. |
| D4 | How should zero-copy operations such as `sendfile`, `splice`, and storage-to-NIC be expressed? | The operation borrows no ordinary buffer, yet simultaneously reads a file object, advances an offset, and writes a socket; this is a real path P0 is quite likely to need. | Buffer-loan is not a common representation for all data movement. | Once B3's multi-region footprints have landed, add a dual-capability semantic ID that precisely declares source read, cursor mutation, target write, and completion point, with no new writer scheduling syntax. |

## Minimum closure

The first I/O spec batch must, at minimum, fix seven items of compiler-owned data for every semantic ID:

1. authority inputs and capability mint/alias relations;
2. world footprint and commutativity;
3. submit, linearization, loan release, and completion points;
4. the boundary between typed outcome, resource death, and TCB defect;
5. progress and compiler-derived release policy;
6. the protection, memory ordering, and lifetime guarantees required for target qualification;
7. the stable operation identity used by ledger/conformance.

None of these records require `async`, task, thread, priority, or queue depth to enter the language. The writer still writes a sequential program; the compiler only gains overlap permission when the above facts are sufficient to prove it.

This was a purely read-only audit; the branch remains `io/model`, and no file was modified.
