## 1. Where compute parallelism stands

Landed on `main` (all merged, owner-approved):

- **#43** — idle window (`WF_PAR_IDLE_WINDOW_US`, 1 ms, only when lanes fit
  the online CPUs), publish epoch, a real spin hint, split work unit 150,000
  (was 1,200,000), affinity-aware online-CPU count, width set to 32.
- **#49** — the asymmetric-core rule: the window is withheld when the online
  CPUs are not all one performance level (`wf_prim_cpu_levels`; Darwin
  `hw.nperflevels`, Linux `cpu_capacity`, Windows `EfficiencyClass`; x86 Linux
  hybrid parts are not detected — stated gap). Validated on the owner's
  Apple M1 Pro at W=8: quadrature 1.296, records 1.239, fir 1.116 (wf-b/wf,
  new rule ahead), mandelbrot neutral.
- **#44** — Darwin process-CPU source `task_info` (the earlier
  `CLOCK_PROCESS_CPUTIME_ID` counted terminated threads only).
- **#45/#47** — sparse call cadence mode `WFB_GAP_US` in the bench, the
  hosted A/B twin evidence, and the gated `WF_PAR_TRACE` lane trace
  (default objects byte-identical).
- **#46/#48** — the compute regression gate: a baseline twin built from the
  merge-base runtime and merge-base `whitefootc`, paired in one run; FAIL
  when a block at W in {1,2,4} reads `A/B wf-b/wf wall < 0.97` with
  `lower >= 4/5`; runs on every PR, measures only when a measured path
  changed; required check on `main`. A false-positive class is known:
  two images from identical sources can differ by ~6% at W=1 from code
  placement (PR #50 first attempt, `records W=1 0.938 5/5`; run
  34671025894 `records` A/B 0.912 at W=1). The fix in flight on branch
  `ci/gate-placement`: alignment flags on both twins, and a kernel fails
  only when two recorded widths cross the line (one crossing prints
  `suspect`).

Measured state, back-to-back cadence, `wf` against the best of
Rayon/oneTBB/ParlayLib/static (`research/investigations/compute-runtime/RESULTS.md`,
sections dated 2026-09-11/12): at W<=4 the plain program is fastest or within
1–3% on the three map kernels and on quadrature (0.969–1.073); W=1 tax on
the recursive kernel 1.4%. Open and recorded: M1 Pro quadrature W=8 still
1.35 behind parlay with the window withheld (does not scale from four lanes
to eight under either wait policy); mandelbrot W=4 1–2.5% behind (fixed-chunk
tail); W=1 quadrature/records 6% behind serial on some CPU classes (no
`-march`); Intel hybrid on Linux undetected; the hosted-VM sparse-cadence
loss (8–18% at W=4 on two of three runner instances) is closed as
unresolvable on that runner class and does not appear on real hardware.

## 2. The concurrency model, as the owner accepts it

Restated operationally (the catalog's §0 has the long form):

- Source is one sequential control flow. No threads, locks, atomics, queues,
  channels, futures, callbacks.
- Parallel execution is checker-derived overlap only: [PAR-1] independent
  calls in one block; [PAR-2] counted-loop iterations writing their own
  bindings, proved-disjoint affine elements, or one commutative accumulator.
  All of it fork-join.
- State that persists across parallel phases is data (rows in arrays), never
  a thread.
- **[PAR-3] is set aside.** The owner said to treat that rule as
  nonexistent for this design line. Do not derive anything from it.

The owner accepts what this model cannot express — dynamic mutual
exclusion, futures with independent lifetimes, actors that respond at any
moment — **on one condition: the program can be written in another
structure with no performance loss.** The catalog
(`CONCURRENCY-CATALOG.md`) prices that condition architecture by
architecture; its §22 table and §24 weakest-four are the owner's reading
list.

What the catalog found that changes the plan: five common compute shapes
(histogram, prefix sum, 2-D stencil rows, hash-map build, per-shard work)
are "bounded loss, W written as a source constant" only because [PAR-2]
hands out affine *elements* and not affine *ranges*. With range loans (below)
and a [PAR-2] extension admitting an iteration-exclusive loan on
`[c*i, c*(i+1))` with `c` loop-invariant, all five become "restructure, no
loss". The I/O model below stands on the same rule.

## 3. What was rejected in the I/O discussion, and why

In the order they came up. Each is closed unless the owner reopens it.

1. **Compiler-derived continuations (LLVM state machines from derived
   `may_suspend`, PR #26).** Rejected by the owner: the effect is implicit
   and derived, so a leaf change silently changes a boundary function's
   calling convention. Evidence from the branch is kept in
   `SCHEDULER-FINDINGS.md` (correctness-qualified, executor-negative,
   repaired executor exceeds Go 1.27 at 64/1024 peers).
2. **Stack switching (park-on-miss, stackful handlers).** The switch itself
   is 10 ns; the cost that retired it was the unified scheduler around it
   (park+publish 4.4–6.2 µs, compute joins parking, cross-thread wake). A
   later proposal to run stackful handlers on a per-ring executor separate
   from the compute pool was set aside together with [PAR-3].
3. **Explicit ticket/ring with whole-buffer `move`.** Zero-copy for whole
   heap buffers (a move is a three-word descriptor), but a buffer cannot be
   split across concurrent operations — scatter reads, chunked sends,
   streaming parse all need pieces of one buffer. Rejected for that.
4. **A runtime `Group` with fixed pieces, then `take_range`/`join`/`split`/
   `give_back`/`Busy`.** Rejected by the owner as feature accretion: each
   new case added a primitive. The diagnosis: every one of those was a
   substitute for the checker not knowing ranges.

## 4. The converged model, with code

Notation: `[existing]` compiles today; `[new]` does not exist and is
proposed; abstract device `dev`, buffer `buf`; syntax follows the tree's
programs (named arguments, `region`, `match`, `set`, `&uniq`, `move`).

**4.1 Non-blocking is a pure call; blocking is one statement.** Every
operation exists as `op_start` (never waits; returns a `Pending`) and the
Pending is completed by `op_finish` (waits). Blocking blocks the whole
program; nothing else needs that thread (in-flight I/O progresses in the
kernel, [PAR-2] lanes on other threads, both joined by the program's own
order). A deep function either blocks in place (`start` then `finish`) or
returns the operation it wants as data for an outer loop.

```
let p = op_start(device: &uniq dev, at: 0_u64,
                 destination: mut_slice_of(&uniq buf, start: 0_u64, end: 4096_u64));
    // [new] op_start: never waits; Pending holds the range loan until finish
    // [new] mut_slice_of with a range: an &uniq loan covering [0,4096) only
    //       (today mut_slice_of(&uniq buf) loans the whole buffer)
let r = op_finish(pending: move p);          // [new] waits; the loan ends here
```

**4.2 Range loans are the one language rule.** Two loans conflict iff their
ranges overlap; disjointness is a proof obligation discharged by the
existing linear-arithmetic engine (the one behind bounds obligations and
[PAR-2]'s affine refinement). The owner: "肯定是要加的，即使是计算也可能会
遇到这个问题". Streaming parse, read and parse overlapped, no copy, no
extra primitive:

```
let p = op_start(device: &uniq dev, at: 0_u64,
                 destination: mut_slice_of(&uniq buf, start: 0_u64, end: want));
loop @parse {
  match op_finish(pending: move p) {
    Done(result: n) => {
      let next = op_start(device: &uniq dev, at: filled +wrap n,
                          destination: mut_slice_of(&uniq buf, start: filled +wrap n,
                                                    end: filled +wrap n +wrap want));
      let consumed = parse_some(view: slice_of(&buf, start: used, end: filled +wrap n));
          // obligation: [used, filled+n) disjoint from [filled+n, ..): right end = left end
      set used = used +wrap consumed;       // a token spanning the boundary stays in place
      set filled = filled +wrap n;
      set p = move next;
    }
  }
}
```

**4.3 Waiting for any of N.** Two shapes, both needed.

Shape A, N operations each with its own buffer (tasks, connections): the
Pending owns its buffer by `move`; N Pendings are ordinary owned values in
an array of an enum; nothing new beyond the Pending and its operations.

```
// slots: [Slot; N], Slot = Empty() | Busy(pending: Pending)      [existing enum-in-array]
let i = op_finish_any(set: &uniq slots);           // [new] waits; reads slots, changes nothing
match replace(slots[i], Empty()) {                 // [existing] replace by runtime index
  Busy(pending: p) => {
    match op_finish(pending: move p) {             // already complete: returns at once
      Done(result: r, buffer: back) => {
        set slots[i] = Busy(pending: op_start(device: &uniq devs[i], buffer: move back));
      }
    }
  }
  Empty() => { }
}
```

Why this does not race: `op_finish_any` takes `&uniq slots` and only reads
it; the runtime's own in-flight table is private; the two agree because each
Pending is affine and lives in exactly one place. The kernel writes only
buffers the program holds no access to.

Shape B, one buffer scattered over N in-flight pieces: N range loans in a
container. Static route (the owner chose static over runtime bookkeeping):
`[new]` values in arrays/enums may hold loans (the holding binding is the
loan holder, confined to the buffer's region); `[new]` a contract operation
`partition(&'b uniq buf, size)` yields the N disjoint pieces at once so no
loop invariant over loans is needed; pieces move out by `replace` and back
in through `op_start`.

**4.4 The batch loop is the only new control shape.** Event-driven programs
become: wait for a batch of completions, handle the batch as a [PAR-2] loop
over rows (each iteration writes its own row and its own buffer), then issue
the next operations in a sequential pass. Per-connection state is a row.
Memory per idle connection is a row plus a poolable buffer. The catalog's
§17–20 derive thread-pool servers, reactors, async runtimes and the
responsive loop under this shape; the expectation is 0.95–1.0 of the
bundle's batched native io_uring reference (the Whitefoot program becomes
the same loop), estimate, not measured.

**4.5 What the model deletes from the current spec.** The `may-suspend`
contract machinery — three milestones (`result-ready`, `loan-released`,
`terminal`) and three submission outcomes — existed for the stackless
two-slot staged driver and is not needed: a call holds its loans until it
returns. Delete it; each system operation becomes "returns when its outcome
is ready; retains its argument loans until it returns". Whether one bit per
operation ("waits") survives is open (§5).

## 5. Open decisions (the owner has not decided these)

1. **The "waits" bit.** [PAR-2]'s admission and the runtime's routing need
   to know whether a loop body can wait. Options: a declared effect `waits`
   in signatures (consistent with `reads/writes/allocates`, visible, no ABI
   effect) or a derived summary bit used only by the checker. The owner
   questioned whether it should exist at all.
2. **Linearity of `Pending`** (a Pending dropped while in flight leaves the
   kernel writing a buffer whose loan ended). Needs a must-consume rule;
   [SYS-5]'s reserved `completion-required` policy is the slot. The owner
   deferred it ("2 不是问题，暂时先不讨论").
3. **Shape B's container-of-loans rule** vs runtime bookkeeping: the owner
   chose static; the exact rule (loans in array/enum elements; the
   `partition` contract) is not written.
4. **`wait_batch` forms**: deadline/poll variants are required by the
   catalog's §16 (periodic duties) and §20 (responsive loop); a `cancel` on
   a Pending by §19.
5. **The operation-request value**: a deep function that cannot issue I/O
   returns what it wants as data; that value's shape must be settled or
   every library signature is cut in two (catalog §24.4, §25.3).
6. **[PAR-2] range extension**: admit an iteration-exclusive loan on
   `[c*i+b, c*(i+1)+b)` with `c` loop-invariant; whether the same rule
   covers 2-D rows `[y*w, y*w+w)` (catalog §14′ says yes if `c` may be
   symbolic).
7. **Documentation debt**: `docs/roadmap.md` BOUND-1 still says v0.45/v0.46
   (the I/O amendment merged as v0.50); `compiler/README.md`'s inventory
   bullet omits streams and TCP; `NETWORK.md` §5 says the hand-out form
   "landed" (retired 2026-09-10); PR #35 proposes retiring `compiler/README.md`
   and `mcts_mem/` and collides with PR #30 on v0.53.

## 6. Recommended order

Given to the owner on 2026-09-13; not yet confirmed.

1. **Range loans + the [PAR-2] range extension** (spec amendment, checker,
   proof discharge on the existing engine). Validate by adding histogram,
   prefix sum and a 2-D stencil to the compute scoreboard as kernels; the
   regression gate protects the four existing ones. This is the piece both
   compute expressiveness and the I/O buffer story need.
2. **I/O API on top**: `Pending`, `op_start`/`op_finish`/`op_finish_any`/
   `wait_batch`/`cancel`, deadline form, file write and create, the
   `may-suspend` machinery deleted, a batch-model echo server back in the
   TCP benchmark against the native batched reference (with the four
   measurement controls recorded in [mcts_mem/whitefoot/system-interface.md](https://github.com/mbbill/Whitefoot/blob/0f22b026b062c36ef2f8ce9c725ee4307e1fda64/mcts_mem/whitefoot/system-interface.md):
   TCP packet policy, generator width, reference storage policy, glibc
   arena).
3. **Deferred**: M1 Pro quadrature W=8, sort/BFS algorithmic shapes, actor
   patterns, Intel hybrid detection on Linux.
