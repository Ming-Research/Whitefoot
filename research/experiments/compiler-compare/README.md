# Two-compiler comparison

This manual experiment answers one question for a change to the compiler:
does it make programs slower or faster, and by how much, on the owner's
i9-14900K? `.github/workflows/compiler-compare.yml` runs it on request, on that
runner or on a hosted one; it is never a gate. `hash-map-bench.yml` compares
two library revisions under one compiler; this compares two whole compilers
(each with the standard library and runtime of its own commit) on the same
programs. Keep these files while a compiler change still needs this
comparison; remove them with the workflow when none does.

## What is compared

The candidate and the base are two commits. `arms.sh` builds each in its own
worktree with `make -C compiler build`, so the arms differ in everything the
two commits differ in. The base defaults to the candidate's merge base with
`main`, which isolates a branch's own change from what `main` gained since.
The same commit twice is the null run: both compilers are the same, and the
comparison shows only this run's noise.

The programs are the instrument's, not the commits': this checkout (the ref
the workflow is dispatched on) holds `compare.py`, `bench.wf` and `interp.py`,
and the inputs below come from pinned revisions, so that both arms compile
the same source. The source must be accepted by both compilers. The wasm
interpreter's generator is the candidate tree's own
(`research/experiments/match-dispatch/wasm/gen.py`), and the Halo revision is
the workflow input `halo`; a language change that makes either unacceptable
to one of the compilers fails the build step with that compiler's diagnostic
rather than comparing different programs. Each group builds its own twin: a
byte copy of the base image, whose difference from the base measures nothing
but this run's noise.

| Group | Programs | Judged by |
| --- | --- | --- |
| `hash_map` | the seven `HashMap` operations at three sizes, memory cells and the candidate's scan hold times of [hash-map-compare](../hash-map-compare/README.md) | its decision rule, unchanged |
| `interpreters` | Halo (Lua) running `fib(32)`, and the wasm interpreter v2h running CoreMark, 2000 iterations | the same rule, below |
| `perf` (in the `interpreters` stage, 14900K only) | the same two programs under `perf stat` | not judged: counts and ratios |

`hash_map`: `compare.py build` takes the base's own runtime for the memory
cell's observed image (`--base-runtime-root`) and accepts equal images
(`--allow-identical-images`) because a compiler change need not reach a
program, and the null run never does; the manifest then says `bench images
identical`. Everything else is `hash-map-compare`'s.

`interpreters`: Halo is built with `whitefootc --graph tests/halo-bench/modules.wfg
--entry bench --full-lto` from a checkout of Ming-Research/Halo-wf (the graph
was under `research/` in older revisions; `interp.py` takes the one that
exists), reading Halo's `fib.lua` with its size set to 32 on standard input;
its output must be `2178309`. The wasm interpreter is generated by `gen.py` and
compiled with a fresh cache per arm, and runs the CoreMark module of
mbbill/Silverfir-nano (the git blob `70b4d2165e7f` of
`benchmarks/wasi/coremark/coremark.wasm`, checked) as the match-dispatch
investigation did; the component CRCs of the 2K performance run and the final
CRC that investigation recorded for 2000 iterations must all match. A
mismatch is invalid data, not a measurement. Both are native programs, so the
timed quantity is the wall time of the whole process, pinned to one CPU with
`taskset`, after one untimed run of each image. The wasm interpreter opens its
module relative to its working directory and rejects an absolute path, so each
run starts in the directory that holds the inputs.

## Criterion

The decision rule is the engineering standard's paired rule, as
`hash-map-compare` applies it, and `interp.py` calls its functions instead of
restating them:

- A round runs each workload's three images once, in a rotating arm order.
  A workload's per-round ratios are candidate over base and twin over base.
- The interval is the distribution-free 95% interval of the median of the
  per-round ratios; it needs at least six rounds.
- A workload is judged once the twin's interval contains 1 and its half-width
  is below the resolution, 2% (the default of `hash-map-compare`; the
  resolution is the smallest difference to resolve, not an acceptance
  threshold). Then a candidate interval wholly above 1 is a regression of any
  size, wholly below 1 an improvement, and across 1 no detected change only
  when it also lies within 1 plus or minus the resolution. Rounds continue
  until both workloads are judged or the round limit (30) leaves one
  unresolved.
- The floor: a workload's spread is the median over rounds of
  |twin/base - 1|. A run given no floor only measures it and prints a `floor`
  line; a later run on the same machine is given it (`interp_floor`, and
  `floor` for the hash-map cells), and a workload whose spread is above its
  floor is not counted, whatever its verdict, and is rerun. The first run on a
  machine measures the floor, which is recorded with its run on the board; the
  comparison that decides is a second run given it, and the floor is measured
  again when the machine, its settings or the toolchain change.

`perf stat` counts user-mode instructions, cycles, branches, branch misses, L1
data-cache loads and misses and backend-stalled cycles (an event the host does
not support is dropped, named in the output and, if it is instructions or
cycles, fails the run). Five rounds, in the rotating order, give no 95%
interval, so nothing is judged: the table shows the medians, the IPC and the
miss and stall rates per image, then each event's candidate/base and
twin/base ratio with its range over the rounds. On a hybrid CPU a generic
event is one row per PMU; the rows of a PMU whose CPUs exclude the pinned CPU
are ignored and the rest summed.

## Controls

The twin is the null control in every run, and the null run (the same commit
as candidate and base) checks the instrument end to end: a rate of false
verdicts near the 95% intervals' (about 2% of workloads or cells per tail)
is expected, so a few cells judged a regression or an improvement are not by
themselves a defect.

In the null run the base and candidate images of the programs compiled
without `--full-lto` are two files, not one. Four compiles of one source by
one compiler, each from an empty cache or with none, wrote four images of
equal size that differ from each other, and from a fifth compile, in about 24
bytes each (a run of 20 consecutive bytes near the start of the file, and a
few more); a compile that reads the warm cache of the same source returns the
same bytes as the compile that filled it. Halo, built with `--full-lto`, came
out byte for byte equal in both arms. So the null run's images differ in
those bytes only, and the acceptance of equal images above is not reached
today. The cause is not identified.

`interp.py self-test` and `compare.py self-test` exercise
the reducers on synthetic rows, including a slowdown and an improvement the
reducer must find, a noisy or offset twin that must leave the workload
unresolved, a floor, and every output check. The interpreters group has no
slow control like `hash-map-compare`'s, which injects extra work inside the
timed interval; its sensitivity is what the synthetic rows show.

## Running and outputs

```sh
# the null run, then a comparison, on the 14900K
gh workflow run compiler-compare.yml --ref main -f runner=14900k \
  -f candidate=BRANCH -f base=BRANCH
gh workflow run compiler-compare.yml --ref main -f runner=14900k \
  -f candidate=BRANCH -f floor="..." -f interp_floor="..."
```

`groups` selects `hash_map`, `interpreters` and `perf` (a comma-separated
list; `perf` runs inside the `interpreters` stage, on the 14900K only). The
job summary holds each group's `summary.txt`; the artifact holds the raw rows
(`raw.tsv`, `memory.tsv`, `hold.tsv`, `time.tsv`, `perf.json` and the
`perf stat` CSV files) and the manifests with the resolved commits, compiler
and image digests, CPU, rounds and host. On the 14900K the default CPU is 2,
one hyperthread of a P core other than CPU 0. A hosted runner shares its
host, so its runs show the instrument working and decide nothing.

## Limits

The programs are two interpreters and one library at one key and value type,
one CPU and one input size each; a compiler change that matters elsewhere is
not measured. The interpreters' timing is whole-process wall time: it includes
process start-up, which is the same for the arms. The wasm interpreter's
source was edited to compile under the specification of 2026-10-23: a field
and a local named with a reserved word (`held`, now `held_local`) and seven
conditions the compiler proves always true (`if i < v^.inner.len` inside a
loop over that length, or after a guard that returns) are removed. The
edits keep what the program computes.
